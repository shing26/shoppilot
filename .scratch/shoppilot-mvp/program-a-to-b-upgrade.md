# 从 A 到 B：升级到「准备真的投用」需要哪几件事

> 状态：**已定（2026-10-04，所有者裁定）**。
> 当前身份：**A —— 系统样品**：形状正确、证据充分、随时能演示。
> 下一段 program：**B —— 准备真的投入使用**（接真实客户）。**本文件就是 B 的入口清单**，不是承诺书。
> 依据：ADR 0052（定位改写，本段不改它）、[ADR 0060](../../docs/adr/0060-im-platform-line-contract-first.md)（IM 主线的 A/B 分段）。

## 0. 这一段决定的分界

**A 身份允许**：补证据、收窄形态、修在架上的洞、加 0 token 的录放门类门禁。
**A 身份禁止**（以「反正要上线」为理由的放宽）：动判据 / gold / 阈值 / 覆盖率门槛；
把「未实跑」写成「已验证」；往仓库里放默认凭据。

**这不是保守，是因为 A 的全部价值就是「它说的每句话都能被复现」。**
一旦为上线而放宽这条，B 段还没开始，A 段攒下的资产已经先折价了。

## 1. 现状里三件「是选择而不是疏漏」的事（写清楚，免得日后被当成 bug）

| 事 | A 身份下它是 | B 身份下它变成 |
|---|---|---|
| 业务数据全在内存 H2（`jdbc:h2:mem:`），重启即清 | **可接受的**——演示每次都从同一份种子开始，行为可复现 | **第一优先级的阻塞**：订单、工单、账号全部抹掉 |
| Redis 不挂卷（缓存/会话/幂等随之丢） | 同上 | 同上，且需要一个「丢得起」的语义界定 |
| 零真连（IM / 邮件 / 真实 Redis Streams） | **明确对外不宣称**（ADR 0052 的「不宣称上线」） | 每一条都是 B 的入口条件 |

## 2. B 的入口清单（按依赖顺序，不按重要性）

### B1 · 数据活过一次重启 ⛔ 阻塞其余全部

> **换代指针（2026-10-06）：B1 已收口**——round28（票 100-103，[ADR 0061](../../docs/adr/0061-b1-persistence-postgres-profile.md)）。
> 落点与原文的一处刻意偏差：没有「把默认档换掉」，而是**双档并存**（默认档 H2 内存不动保演示可复现，
> 新增 `postgres` 持久档 + Redis AOF，容器档 full 默认走持久档）；活体重启验证与 LOB 取舍（`@Lob`/oid）
> 见该 ADR 与 EVIDENCE 的 B1 节。**B2 起照原文继续。**

- **要做**：`biz-mock` 与 `ticket` 的 H2 换真实库（Postgres/MySQL）；
  Flyway 迁移改写成真实方言；seed 拆成「初始化」与「演示数据」两段（现在是一次全量）；
  Redis 挂卷。
- **为什么先做**：账号（round25）、工单（round23-27）、退款状态全在内存里。
  **IM 接得越多，一次重启丢得越多。**
- **做完会第一次出现的问题**（现在就写，省得当成新 bug）：
  ① 唯一约束在并发下才真正生效（H2 内存库掩盖了很多）；
  ② `@TenantId` 的过滤在真实库上要逐条复核（这个仓被咬过三次：`findById` 不拼 `@TenantId` 两次、分流规则跨店劫持一次）；
  ③ 幂等键的 6 小时窗口在真实库上会变成「表会涨」的问题，需要清理策略。
- **触发**：所有者决定这个仓开始接真实客户的那一刻。**没有它，B2-B5 做了也白做。**

### B2 · 凭据与部署

> **换代指针（2026-10-06）：B2 已收口**——round29（票 104-107，[ADR 0062](../../docs/adr/0062-b2-credential-posture-and-backup-restore.md)）。
> 落点：姿势守卫下沉共享库并接入数据侧（内部令牌 + 持久档 DB 口令，非回环拒启）、按库用户隔离
> （bizmock_app / ticket_app，PUBLIC 收 CONNECT）、备份恢复演练 14/14（pg_dump -Fc 含大对象 →
> DROP FORCE → restore → API/LOB/授权三层验证）；Redis 不备份、监控 R5、TLS 三项带触发条件登记。

- 真库连接串、`SHOPPILOT_INTERNAL_TOKEN` / `JWT_SECRET` 的**生产态管理**（现在只有回环下的默认兜底，ADR 0029）；
  部署形态（容器档已存在，但它是**自用档**，没有备份/监控/回滚）；
  备份与恢复演练。
- **触发**：B1 完成。

### B3 · 审计的不可抵赖性

- 现在审计事件的 actor 可能是「未认证」（ADR 0058 决策 4 的照登：只有 ops 凭证在场时）。
  面向真实客户时，**退款放行的责任人不可抵赖**是产品底线，不是可选项。
- **触发**：B1 完成 + 有真实资金动作之前。

### B4 · IM 真连（[ADR 0060](im-platform-line-spec.md) 的 B 段）

- 票 98 那次可行性考察的结论决定它开不开；结论可能是「不成立」，那时的替代路径是 A 段留在交付里。
- **暴露面红线不变**：隧道/公网只能放行回调路径 + 强制平台签名校验，ops 端点一律不对外。
- **触发**：票 98 出结论 + B1 完成。

### B5 · 跨平台身份统一

- 平台用户 id → `customerId` 的映射表。**这是数据模型级改动**，且做错就是跨租户泄露。
  所以它排在最后，而且要求 B1 已经在真实库上跑过一轮。
- **触发**：B4 真连成立 + 确实出现了「同一个人要跨平台」的诉求。

## 3. A 段现在该做什么（按投入产出比）

1. **清场日**（需要所有者授权，因为它要停掉另外三套项目的容器）：
   **一次能关掉四笔欠账**——三个浏览器门禁（`verify-workspace` / `verify-outbound` / `verify-buyer`）实跑、
   票 84 的修前红/修后绿读数、真实 Redis Streams 的 ACK/pending/MAXLEN 行为、
   以及一次带全新浏览器断言的 full 档矩阵。
   **本轮三张票（round26 / round27）各留了一条「本轮未实跑」，清场日是它们的唯一出路。**
2. **票 96**（`NormalizedChat` 补 `conversationId` + 适配器派生 `clientToken`）：
   它修的是一个**现在就在架上的洞**（不传会话头就断追问），与 B 无关，A 身份下就该做。
3. **IM 主线 A 段**（票 97）：录放门，0 token。它的定位要改写——不是「为接 IM 做准备」，
   而是「证明适配器契约可复现」。
4. **票 91**（知识服务化做不做）：随时可领，它在 A 身份的判断框架下已经答完了（不做 + 登记偏离）。

## 4. 一条纪律

**A 段每收口一次，都要把「B 的清单少了哪几件」写进 tracker。**
否则半年后回头看，会以为 B 从来没被规划过——而它现在有了。
