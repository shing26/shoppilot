## 0. 顺序，以及为什么不是别的那样

**【默认】顺序：结果回流买家（round26）→ 买家端前端（round27）→ 知识服务化（round28 或不做）。**

理由不是「先做简单的」，而是**先做能让买家看见的那两格**。第一格是 program 主线第 3 节写的最后一句，
而今天它是断的：`resolve` 之后除了工单表多一行 `RESOLVED`，买家侧什么都收不到。第二格让买家有地方看见它。

先做知识服务化的理由只有「架构纯度」，而它对买家可感知的价值是零，代价是第五个 JVM 约 500 MB
加一次高风险迁移——所以它排在最后，且**第一步就是一张决策票**。

## 1. 查证过程中改掉的一个判断（这一条最要紧）

我原以为「渠道出站」要补的洞是**邮件没发出去**。读代码的结果相反：

- `web` / `app` / `miniapp` 的答案是**同步 HTTP 返回**的（`ChannelController` 把 `answer` 放进响应体）；
- `email` 按 ADR 0035 **本来就没有实时回包通道**，交付物是回执工单（`EmailReceiptWriter` → `reason=EMAIL_REPLY`）。

**今天每个渠道都已经有交付路径**，所以 `channel.outbound` 没有生产者不是缺陷，
是**还没有一个真的异步答复**。而「坐席处理完之后结论怎么送回买家」正好就是 program 主线的最后一格，
也正好是这个异步答复。

这决定了出站这一块的主体不是「加一个邮件发送器」，而是**「工单结单 → 结果回流」这条链**。

## 2. 三块各自的形状

### 块一 · 结果回流买家（round26，票 86-90）

| 决策 | 内容 | 状态 |
|---|---|---|
| 第一生产者 | 工单服务在 `resolve` 时发 `channel.outbound` | 【默认】ADR 0059 |
| 消费端在哪 | **网关进程内**，不为它起第五个 JVM（ADR 0053 已把渠道出站适配划给网关） | 【默认】ADR 0059 |
| 工单要补的列 | `tickets` 加 `channel` + `contact`（今天只在 `transcript` 里存了一句字符串） | 【默认】ADR 0059 |
| webhook 回我哪儿 | 入站契约新增**可选** `callbackUrl`；没有就不发事件，照登 | 【默认】 |
| 投递失败 | 重试 3 次后**落一张 `CHANNEL_RECEIPT` 工单**，不丢 | 【默认】ADR 0059 |
| email 出站 | **只落投递口，不真发 SMTP**（无 SMTP 依赖、收件地址是假数据）；交付仍是回执工单 | 【默认】ADR 0059 |
| 幂等 | 至少一次投递，消费端按 `eventId` 去重（0054 已定） | 沿用 |

### 块二 · 买家端前端（round27）

第三个 Vite+Vue3 入口，落 `/buyer/`：SSE 会话页 + **「我的工单 / 售后进度」**列表。

- **买家只能看自己的**：服务端按 JWT 的 `customerId` 过滤，不接受路径或参数里的买家号（ADR 0005 防线一）。
- 产物入库（同 workspace 的裁定 E），CI 前端构建门禁不变。
- 新增浏览器门禁 `verify-buyer.mjs`；**与工作台一样，本轮按未达成登记**（资源账）。
- 【默认】**不做**买家自助注册以外的账号管理、不做多店铺切换。

### 块三 · 知识与业务服务化（round28 或不做）

现状与 ADR 0053 的差距已查清（网关直连 ES/Qdrant、ingest 只是网关的另一个 profile），
但**先答一个问题：这一格在本机值不值。**

| 选项 | 代价 | 收益 |
|---|---|---|
| 全拆（检索 + 入库都搬） | 第五个 JVM 约 500 MB；8 个类搬迁；`KbEpoch` 变跨进程（含一个写操作）；`HybridRetriever.Result` 等 DTO 要下沉到契约库；`EmbeddingClient` 与分诊共用的实时链路要重新分家 | ES/Qdrant 名义上「独占」 |
| 只拆 ingest | 几乎零成本（它本来就是独立进程的一次性作业） | 收益也几乎为零——检索仍在网关直连 |
| **不做，登记偏离** | 零 | 零；ADR 0053 的边界留成一条**写明触发条件**的登记项 |

**【默认】我的建议是第三个，并把触发条件写死**：出现「ES/Qdrant 只能被一个服务访问」这类硬要求、
或检索策略要由网关之外的团队改、或全栈档的资源账改善到能日常跑——三者任一成立即重开。
理由：它对买家可感知的价值是零，而本仓这三轮反复在处理的都是「买家能不能拿到答复」这条线。

**这条是最该由你拍的一条**，它不在代码里、只在钱和内存里。我按默认值往下写了票 91（决策票），
翻案的成本是改一张票，不是改一轮。
