# 88 出站消费端：按渠道投递 + 幂等 + 失败落回执工单

**Status:** implemented（2026-10-04）

## What to build

**消费端**（ADR 0059 第 3、5、6 条），落在**网关进程内**，不为它起第五个 JVM。

- **消费循环**：读 `shoppilot:channel-outbound`，消费组 + ACK，惰性或后台线程均可
  （本仓对审计选了惰性，对出站**建议后台线程**——回流晚几十秒无所谓，但「要有人点一下才投递」不对）。
- **按 channel 分派**：
  - `webhook` → 对 `target` 发一次真实 HTTP POST（**这是本轮唯一「真发出去」的渠道**）；
  - `email` → **不真发 SMTP**，落一张 `CHANNEL_RECEIPT` 工单（ADR 0035 不动，本轮照登）；
  - 其它渠道 → 记一条「无投递方式」的 warn，**不假装投递成功**。
- **幂等**：按 `eventId` 去重（至少一次投递），重投不产生第二次 POST。**去重集合要有界**，否则它是第二本账。
- **失败处置**：重试 **3 次**后落一张 `CHANNEL_RECEIPT` 工单（ADR 0059 第 6 条）。
  工单内容含工单号、渠道、失败原因与最后一次的响应码。
- **`callbackUrl` 入参**：`WebhookAdapter` 的归一契约新增**可选** `callbackUrl`；
  没有它就不发事件（票 86 那两列为空 → 87 不发 → 88 无从投递，三处口径一致）。

## Blocked by

[87](87-outbound-publish-on-resolve.md)。

## 口径

- **「投递成功」的定义必须写死**：目标返回 2xx 才算成功；连接失败、超时、非 2xx 都是失败（不许把「发出去了」当「送到了」）。
- **不引任何新的中间件或邮件库**。
- 判据面零改动。

## 验收

- JVM 用例覆盖（**用 JDK `com.sun.net.httpserver.HttpServer` 起一个本地回声端点**，不需要起全栈）：
  - 投递成功时**下游真的收到了 POST**，且 body 与 `ticketId` 对得上；
  - **重复投递同一条 `eventId` 只 POST 一次**；
  - 目标不可达 → 重试 3 次 → **回执工单存在且可查**，且失败计数 +1；
  - email 渠道 → 落回执工单，**且没有 SMTP 依赖**（构建期可查：全仓无 `javax.mail` / `spring-boot-starter-mail`）；
- **变异对照**：把去重去掉 → 第二条红；把「3 次后落单」改成「3 次后丢弃」→ 第三条红；
  把「2xx 才算成功」改成「发出去了就算成功」→ 第一条与第三条红。
- **这条门禁是本轮最承重的一格**：round23 抓到的假绿（「队列空也判过」「未触发也 PASS」）都在这一格附近。

## Handoff notes

### 落点

`gateway/channel/OutboundDeliveryService`（新增）：消费循环 + 按渠道投递 + 幂等 + 失败落回执工单。
一个后台单线程定时任务（默认 5 s），`@PreDestroy` 停。

### 门禁用 JDK 自带的 `com.sun.net.httpserver.HttpServer` 起**真的**回声端点

这是本轮最要紧的一处安排。mock 掉 HTTP 之后，「调用过 send」与「送到了」就分不开了——
而这一格要证明的正是后者。**因为它不需要起全栈，所以「投递真的发生过」不必等清场日。**

### 两条被自己的测试抓出来的错

1. **email 落回执工单原本被算成了「失败」**。第一版让 `landReceipt` 恒返回 false，
   于是 email 那条路径把 `failed_total` 加了、`delivered_total` 没加。
   按 ADR 0035，**落回执工单就是 email 的交付形态**，那一步是送达而不是失败。
   现在 `landReceipt(..., countsAsDelivered)`：email 传 true（送达），「没有投递方式」与 webhook 重试耗尽传 false。
2. **幂等那张表是实例状态**。测试里每轮都 `new` 一个服务，于是「同一个 eventId 两次投递」根本没测到幂等——
   第二次是另一个进程的「第一次」。改成跨两轮复用同一个实例。
   **顺带暴露出一条要登记的事实**：去重表在**进程内存**里，网关重启后重投会再投一次。
   见下面的登记项。

### 两条变异对照都实测为真

| 变异 | 结果 |
|---|---|
| 幂等查表改成「查但不记」（等于永不命中） | `redeliveryIsIdempotent` 红（对端收到 2 次） |
| 「重试耗尽后落单」的结果改成「算送达」 | **2 条红**（`nonSuccessStatusLandsAReceiptTicket`、`unreachableTargetLandsAReceiptTicket`） |

### 登记项（本轮明确不做，写在这里而不是省略）

- **去重表在进程内存里，网关重启会丢掉**：至少一次投递 + 内存去重 = 重启后可能重复投递一次。
  修法是像审计那样把 `event_id` 落到唯一索引上，但那是**跨进程的幂等存储**，
  本轮没有（ADR 0054 的消费端幂等要求是真的，只是这一格还没做）。触发 = 出站开始对外承诺「不重复」。
- **重试没有退避**：三次是紧挨着的。演示流量下够用，量产要加退避与熔断。
- **email 不真发**（ADR 0059 第 7 条），重复一遍以便在这一票里找得到。

### 现场三问

1. **为什么消费端放网关而不是第五个服务？** ADR 0053 已经把「渠道出站适配」划给网关；
   而一个只做发 HTTP 的消费者不值一台 JVM（本机全栈已约 6.6 GB）。
2. **为什么后台线程而不是惰性消费？** 审计那条流选了惰性（要有人读审计才收），但出站不行——
   「要有人点一下才投递」是 ADR 0059 明确否掉的形态。
3. **为什么坏消息也 ack？** 留着 pending 让人看是对的，但它不该无限重投；
   做法是**认领掉但不当成功**（不进业务分支、不计送达），同审计那条纪律。
