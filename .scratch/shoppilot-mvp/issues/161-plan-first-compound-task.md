## Handoff notes

**关键决策**

1. 计划由代码按意图生成，模型不参与；复合任务计划固定为“查询订单详情 → 查询实时物流 → 汇总”。
2. 复合任务只匹配 `ACTION_LOGISTICS + 订单号 + 物流 + 详情/状态` 的查询，避免影响普通物流查询。
3. 复合分支确定性执行两个读工具，再用结构化结果拼答案；不调用模型，因此不增加 token 成本。
4. 失败沿用既有出口：缺槽位走 `askSlot`，工具降级走 `fallback`，不新增错误路径。
5. Agent Run 把 `plan` 作为第一条，后续按真实工具执行追加；计划与执行分开可见。

**验证落点**

- 编译与全量 JVM verify 通过。
- 浏览器验证 **4/4**：汇总答案正确、执行前出现计划、两步工具都执行、无页面异常。
- 实测答案：“订单 90004：家居日用，¥199.00，当前待付款。物流：订单尚未发货，暂无物流轨迹。”
- 实测轨迹：接收请求 → 识别意图 → **计划：查询订单详情 → 查询实时物流 → 汇总订单与物流结果** → 组织回答 →
  调用业务系统/查询订单状态 → 成功 → 调用业务系统/查询物流 → 当前状态不允许。
- 截图：[复合任务 Agent Run](../../../docs/buyer-agent-run-compound.png)。
- 180 条 gold 零改动。

**未达成 / 边界**

- 只做了一个读场景；写动作复合任务（查物流 → 条件改址）尚未做，需要地址槽位与确认流程。
- 不是通用自治循环；计划仍由代码生成。

**三个现场追问**

1. **为什么复合任务不交给模型规划？** 路线 A 是低成本验证，先证明“多步执行 + 计划可见”有价值；模型规划属于路线 B。
2. **为什么答案是确定性拼接？** 两个读工具的结果已经结构化，拼接比再付一次模型调用更稳、更便宜。
3. **为什么只匹配一个场景？** 复合任务入口越窄，对通用链路与 180 gold 的扰动越小；验证成立后再扩写动作场景。
