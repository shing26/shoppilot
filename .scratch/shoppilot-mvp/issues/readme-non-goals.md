## Handoff notes

**关键决策**

- **只成文、不改判**：ADR 0040 的四项判断与触发条件一字不改地搬进 README；本票不新增第五条、不调整任何触发阈值——ADR 是结论源，README 是读者面。
- **与"已知限制"分节而非混排**：既有已知限制里已有几条是判断形态（如"ES 停在够用级是判断不是未完成"），但那是逐条叙述；本票用一个独立子节承载"范围边界"这一整类，读者一眼能分清"做不到"与"不做"。
- **README 的 round17 功能面描述不在本票**：票 39（Plan 有序步骤）未收口，README 的架构/主链路/验收对照章节在那之后还要再动一次；在票面登记为 round17 收口的既有任务，避免同一段文字改两遍。

**验证落点**

- `git diff --check` 与 `git status --short` 干净（本票纯文档，无 JVM/量具门禁）。
- 四行表与 ADR 0040 逐项一致：人工比对（本票的判据是文档一致性，无可机器断言的对象——不为了凑机器判据造一个）。

**现场追问**

1. "为什么"有意不做"也要写进 README？" —— 面试官看到对标架构图会问"十万级会话呢、多工具并行呢"；没有成文的边界，回答只能临场编，而编出来的口径最容易与实现脱节（ADR 0040 的立票理由）。写清"为什么不做 + 什么条件下做"，是比"做了"更难伪造的工程判断。
2. "触发条件为什么写得这么具体？" —— "出现第二实例部署"、"工具 P99 > 500ms"这类条件是可以被现实事件直接点亮的；写成"未来需要时"等于没有触发条件，ADR 0030/0031/0032 的冻结机制也就无从执行。
3. "这份清单会不会过期？" —— 会——触发条件满足时它就该被改写甚至删掉。这正是把它与"已知限制"分节的原因：那一节是长期事实，这一节是当前判断，修订成本低、修订信号明确。
