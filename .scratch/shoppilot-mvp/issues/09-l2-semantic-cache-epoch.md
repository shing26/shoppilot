# 09 — L2 语义缓存、纪元失效与跨实例合并

**What to build:** 口语化改写的政策问题在文本不同的情况下仍被语义缓存拦下；政策一改，旧答案整纪元作废；两个实例同时收到同一新问题时只穿透一次。

**Blocked by:** 06 — L1 精确缓存、写回资格与进程内 singleflight；07 — 意图三级级联判定补全

**Status:** done

**Verify:** 改写句二次提问 -> 命中 L2；推进知识库纪元后再问 -> 不命中；换租户身份问同一句 -> 不命中。

- [x] 精确缓存 miss 后才向量化，直接复用 ticket 07 落地的 embedding 客户端与已定案的 `intent`，零临时代码、零重复 embedding 调用
- [x] Qdrant 缓存集合检索带 payload filter：`tenant_id` + `scope` + `intent` + `kb_epoch`，cosine >= 0.95 判定命中；意图过滤缺失视为实现缺陷而非性能优化项
- [x] 缓存条目写入时同步落 Qdrant 向量与 Redis 正文，两处缺一即视为未写入（不得出现向量在、正文丢的半状态）
- [x] `kb_epoch` 推进后旧纪元条目不再被读取，且由后台清理任务删除，不靠 TTL 自然过期
- [x] 跨实例合并：Redis `SETNX` 短锁 + 结果回读，与进程内层组合成两层，锁必须有 TTL 不得死锁
- [x] 指标：L1 命中数、L2 命中数、准入数、穿透数分别上报，供 ticket 18 计算双口径拦截率
- [x] 用例：同意图改写句命中 L2；跨租户不命中；纪元推进后不命中

## Handoff notes

**关键决策**

1. **L2 只在 L1 精确 miss 之后触发**，且直接复用 ticket 07 已算好的 1024 维向量与已定案的 `intent`——零临时代码、零重复 embedding 调用。这是把 09 排在 07 之前的全部理由。
2. **Qdrant 缓存集合 `answer_cache` 检索强制带四条 must-filter**：`tenant_id`、`scope`、`intent`、`kb_epoch`，`score_threshold = 0.95`，`limit = 1`。意图过滤缺失视为实现缺陷而不是性能优化项——没有分桶的语义缓存就是串号发生器。
3. **向量条目只存定位信息不存正文**：payload 是 `tenant_id / scope / intent / kb_epoch / answer_key`，正文仍在 Redis L1。理由是 Qdrant 不是文档库，且正文单点存放避免两处内容漂移。
4. **写入顺序先 Redis 正文、再 Qdrant 向量**（`CacheService.writeBack`）。这样最坏的半状态是"正文在、向量丢"，只损失一次 L2 命中机会；反过来"向量在、正文丢"会让 L2 命中一个取不到答案的 key，那是正确性问题。顺序把不可能做对的事变成可以做错但不致命的事。
5. **`kb_epoch` 推进后旧纪元条目由后台清理任务按 `must_not: kb_epoch >= current` 删除**，不靠 TTL 自然过期。政策一改，旧答案整纪元作废，且不留下一堆"过期但还占内存"的向量。
6. **跨实例合并是第二层**：Redis `SETNX` 短锁（TTL 10 秒，绝不死锁）+ 结果暂存 30 秒 + 20ms 轮询回读，与 ticket 06 的进程内层组合成两层。单实例部署时第二层用不上，但两层都在——生产多实例时不需要再改代码。
7. **L1/L2 命中计数在 `CacheService` 统一记**，`L1Cache` 自己不记，因为两级都会读同一个 key，重复计数会污染拦截率分母。

**你需要能当场回答的三个追问**

- *Q：0.95 这个阈值是拍脑袋的吗？* A：不是，ticket 17 用 118 组对抗对做了 0.85-0.99 扫描。实测结论是 bge-m3 在短中文问句上同意图改写对的最大余弦只有 0.9435，**0.95 工作点上 L2 召回为 0**——这条已经写进 README 的已知限制，不藏。
- *Q：那 L2 还有什么存在价值？* A：它兜的是"同一政策、写法极近"这一小撮，以及为将来换更强的 embedding 模型预留位置。80% 级拦截实际由 L1 精确哈希与 SingleFlight 承担，这是实测归因，不是设计意图。
- *Q：反义问句会不会被 L2 复用？* A：会，而且实测确实会——有 4 组同桶反义对越过 0.95（0.9645-0.9802），两侧还都在同一个 `POLICY_*` 意图里，阈值和意图分区都拦不住。所以补了 ADR 0016 的 `PolarityGuard`：条目携带原始 `query`，判定肯定/否定极性不一致就拒绝复用并计数 `shoppilot_cache_l2_polarity_blocked_total`；条目缺 `query` 时 fail-closed。

**验证记录**

`scripts/verify-polarity.ps1` 9/9 PASS（覆盖 L2 读路径与两层防线分工：源问法写回后同桶探针的余弦确实越过 0.95、极性守卫把它拦下并计数、另一条探针由准入层兜住而非守卫兜住）；`PolarityGuardTest` 5 项。

这个脚本自己曾经红过一次，红的是它的**前提**而不是它的断言：那一刻向量化失败，答案只落了 L1（ADR 0018 的写回资格），L2 里根本没有可比的条目，守卫没有东西可判，脚本却会报"极性守卫 FAIL"，读起来像防线失效。现在它先问一句同极性近义问法确认 `meta.cacheLayer=L2` 真能命中，拿不到就把源问法重打三次，仍不成立就 `exit 3` 并写明"这一步红不代表防线失效，是 L2 前置不成立"。这条失败路径在 `local,no-ollama` 下实测过：exit 3 与提示都如期。**区分"防线没拦住"和"没东西可拦"值得单独记一笔**，否则门禁的红灯会把人引去改一个本来正确的守卫。

**必须说清楚的一点**：验收动作里"改写句二次提问命中 L2"在 0.95 工作点上**不成立**——ticket 17 实测 46 组同意图改写对的最大余弦 0.9435，够不到阈值，所以拿任何真实改写句去验都只会 miss。因此 L2 的正确性改为在存储层直证：`scripts/verify_l2_filters.py` 读出已落库缓存点的 payload 与向量，用同一向量分别把 `tenant_id` / `scope` / `intent` / `kb_epoch` 换成不同值再检索，断言四条 must-filter 各自都能把命中清零（等价于"纪元推进后不命中"与"跨租户不命中"，且不破坏线上纪元状态——`/ops/epoch/bump` 会连检索过滤一起改，不能拿来当清缓存用）。机制验证与生产工作点是两件事，README 分开写。
