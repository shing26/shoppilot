## Handoff notes

**关键决策**

1. 只消费已有 SSE 事件，不改后端与事件契约；这是路线 A 的边界。
2. 轨迹只展示面客可读步骤：状态标签（接收请求、识别意图、检索、组织回答、调用业务系统、生成回复、写入缓存）、
   工具执行文案、工具结果、转人工兜底；内部 `route=` / `toolSurface=` / `surfaceReason=` detail 不透传。
3. 连续同名状态去重，避免同一件事在界面上出现三次。
4. 工具结果状态中文化：`STATE_NOT_ALLOWED` → “当前状态不允许”等，不让买家读内部枚举。
5. 回答进行中轨迹自动展开，回答完成后默认折叠，用户可手动展开。

**验证落点**

- `npm run typecheck` / `build` 通过；`static/buyer/` 产物已重建。
- 浏览器活体验证 **5/5**：真实订单查询出现“Agent 运行 · 10 步”、步骤可读、连续状态去重、
  工具结果中文化、无页面异常。
- 真实轨迹：接收请求 → 识别意图 → 检索政策条款 → 组织回答 → 调用业务系统 →
  正在查询订单 90004 的实时物流轨迹 → 业务系统返回当前状态不允许 → 调用业务系统 → 生成回复 → 写入缓存。
- 截图：[Agent Run](../../../docs/buyer-agent-run.png)。
- 180 条 gold 零改动；全量 JVM verify 全绿。

**未达成 / 边界**

- 本轮没有做复合任务编排；轨迹证明的是“已有行为可见”，不是“自主规划”。
- 轨迹不包含内部推理文本或模型思考过程，只列可核验的执行步骤。

**三个现场追问**

1. **为什么不用后端新增 trace 接口？** SSE 已经带了完整事件；再开一个接口等于把同一事实存两遍。
2. **为什么默认折叠？** 轨迹是解释层，不是主回答；展开是主动行为，不抢聊天注意力。
3. **为什么这算 Agent 感？** 用户第一次能看见系统“判断 → 找政策 → 调工具 → 观察结果 → 回复”的完整链路，
   而不是只看到一句答案；这是路线 A 的最低成本验证。
