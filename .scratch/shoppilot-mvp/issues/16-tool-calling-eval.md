**What to build:** 一份人工校对的标注集，跑出"选对工具"与"填对参数"两个子指标的分意图报告，让 `>= 95%` 这个数字有出处。落实 ADR 0001。

**口径必须说清楚**：这一轮是"同一个 3B 模型换了一条传输层"，不是云端 qwen-plus 的成绩。dev 路径与 local 路径的差别在客户端（OpenAI 兼容 HTTP + 真 token 计费 + 非流式工具规划轮），所以它证明的是这条链路通、记账对、阈值判得准；模型能力那部分与 local 同源。要拿 ≥95% 那个数字，仍然需要 `.env` 里三个 DashScope 值（key / base-url / model），换完直接重跑同一条命令即可，脚本与判据一行都不用改。

**顺带修掉的一个真缺陷**：给 dev 路径补 JVM 测试（`OpenAiCompatibleLlmClientTest` 8 项 + `TokenBudgetTest` 6 项）时发现 `OpenAiCompatibleLlmClient.stream()` 把 `tool_calls` 增量整段丢掉（返回 `List.of()`），只留正文与 usage。当前接线还没被咬到——带工具的规划轮走 `complete()`（`AgentStateMachine:224`），两处 `stream()`（`:320`、`:498`）传的工具表都是空——但它是个静默陷阱：哪天把规划轮改成流式，工具调用会无声消失，表现成"模型就是不办业务"。现在流式路径按 index 归并 `tool_calls` 分片、把 `arguments` 片段拼完再解析，解析不出来时原文留在 `_unparsable` 里，与 `complete()` 共用同一个 `argumentsOf()`。

**转人工这条面的实测分层（2026-09-09，逐条打 SSE 看 TRIAGE 层级）**

18 条 ESC：T0 词表定案 4 条（`转人工` / `转个人` 这类字面表达）；T1 质心定案 10 条；T0 定案成了别的意图 3 条（ESC-03「我要真人给我答复」与 ESC-05「给我接一个能拍板的客服」因句里有「给我」落进 `ACTION_ORDER`，ESC-14「满减算错了我要求赔偿，机器人办不了就叫人」因「满减」落进**可缓存**的 `POLICY_PROMO`）；两级都不定案、交模型 1 条。另有 2 条本不该转人工的冷启动语（UNK-03「你好」、UNK-14「这个怎么弄」）被 T1 判成 ESCALATE——同一批在 09-08 那轮是走模型的：质心判定处在阈值边缘时，短语气句的归属会随 embedding 服务状态翻转。

两类残留都不在本轮范围内：ADR 0017 只承诺「字面显式表达」这条最低可用线，paraphrase 归 T1/T2；要给 ESCALATE 单设更高的定案门槛，得连换 embedding 模型一起标定，不适合在冲刺期拍脑袋改阈值。


## Handoff notes

**关键决策**

1. 语料分三个手写分片（policy / action / edge）合并成 `eval/tool-cases.jsonl`，180 条、10 意图各 18 条。口语变体由 local 的 qwen2.5:3b 生成，但 `expect`（该调哪个工具、参数填什么、该不该问槽）逐条人工校对。
2. 对抗样本实测 40%（72/180：colloquial 34 + missing_slot 12 + multi_intent 10 + order_not_found 8 + cross_tenant 8），高于票面 30% 下限，因为跨租户与订单不存在各多放了几条。
3. 指标从票面的两个拆成三个再加一列：选对工具、填对参数、缺槽时是否正确问槽（`slotask_accuracy`），外加 `fabricated_cases` 单列。合并成一个数字会把"没问槽但参数蒙对"和"凭空编了个订单号"混成一谈，而后者是最危险的失败模式。
4. `missing_slot` 用例的期望写成 `slotAsk: true` + `mustNotContainArgs: ["orderNo"]`，模型编造订单号时 `ToolDispatcher` 直接判 fabricated、不发起查询，即使工具选对也不算通过。
5. 熔断前置：跑前用样例估算单 case tokens × 样本数，与 `/ops/circuit` 的日预算剩余比较，超了 exit 2（要 `--force` 才继续），符合 ADR 0012。非 dev 模式额外打印"仅验证链路，不进入验收口径"。
6. **勾上这条之前，先分清两件事。** 2026-09-09 11:10 那一轮（见上）已经在 `dev` 模式下跑完并落盘，但端点是本机 OpenAI 兼容服务、模型仍是 qwen2.5:3b，所以它交的是「dev 路径可用 + 记账正确」，不是云端 qwen-plus 的能力数字。`HARD_FAIL_INTENT` / `ACCEPT_TOOL` 两条线只在 dev 模式参与红绿判定，这一轮因此判红——那正是这条判据该有的行为。
7. **默认日预算与本票的验收动作撞车，这件事要算出来给人看。** 完整集 180 条、单条实测约 1.1k token，一轮约 19 万，而 ADR 0012 的默认值是 20 万——也就是说默认配置刚好只够跑一次自己的验收动作，当天只要先前有过任何 dev 调用（哪怕一轮 24 条冒烟就是 2.5 万）就必然撞线。脚本的处置是对的：跑前用 `/ops/circuit` 的剩余额度做投影，不够就 `exit 2`，要 `--force` 才放行，所以不会出现"跑到第 120 条被熔断、只留下一堆半份数据"。缺的是**出路**：`daily-token-budget` 原先在 `application.yml` 里写死，而这个文件里每一个可调项都有 `SHOPPILOT_*` 环境变量的口子。现在改成 `${SHOPPILOT_LLM_DAILY_TOKEN_BUDGET:200000}`，跑评测当天显式抬高（`.env.example` 给了 260000 的示例），抬预算这件事留在配置里、有环境记录可查，而不是留在一次代码改动里。实测：把该变量设为 12345 起网关，`/ops/circuit` 回 `dailyTokenBudget=12345`；撤掉后回到 200000。
8. **dev 那一轮的前置手工活收成一条命令，但它不替人按回车。** 填三行配置、抬日预算、把网关切到 dev、跑完切回来——这四件少一件都会让那一轮变成半份数据，或者留下一笔没计划的账单。`scripts/run-dev-eval.ps1` 把它们串起来：自查 `.env`（缺哪项报哪项，真 key 连片段都不打印）→ 缺日预算就把那一行写进 `.env`（其余字节与换行风格原样保留）→ 切 dev 后**回读 `/ops/circuit` 确认真的是 `llmMode=dev` 才继续** → 然后停住，只有加 `-Run` 才发计费请求；`finally` 里无条件把网关放回 local，因为一个挂着真 key 的 dev 网关留在机器上，比一次失败的评测贵得多。自检是拿假 key 把端点指到本机 Ollama 的 `/v1` 跑两条：预算行写入、`mode=dev` 回读通过、产物名带 `-dev`、跑完回到 `local`、`.env` 按 SHA256 原样还原，自检产物已删。

**需要能当场回答的三个追问**

1. "任务书说工具调用准确率 ≥95%，你这里最高 88.9%？" —— 95% 是 dev 模式（qwen-plus）的验收线，本轮 local 用 3B 小模型跑，作用是自证链路与评分口径。分意图报就是为了让差距可见：POLICY_* 四个意图 100%，失败集中在 ACTION_* 的多参数抽取，指向模型能力而非编排契约。

**追加决策（2026-09-10，dev 模式全量首跑）**

9. **dev 全量 180 条首次真跑（DashScope `qwen-plus`）**：修复前 选对工具 157/180 = 87.2%、填对参数 46/63 = 73.0%；四组缺陷修完之后 168/180 = 93.3% 与 57/63 = 90.5%。分意图与逐条缺陷见 README 指标表，四条修复分别落在 ticket 11（工具集与纠偏轮）、ticket 03（可选参数默认值、部分更新、物流 NOT_FOUND）与 Prompt（可选参数不追问、非业务诉求不发工具、不得虚报"已提交"、不得对顾客说工具名）。
10. **明细新增两列：`answer_excerpt` 与 `corrective_round`。** 判据要求"任一意图 < 80% 判不通过并写明原因"，而原因只能从模型原话里取——网关日志不落回复正文，事后翻不回来。第一版跑测就是因为没有这一列，只能靠手打单条复现去定位（见下面的实测分层）。
11. **预算预检按"同样规模"的历史样本预测。** dev 调试习惯用 `--only-intent` 只跑 18 条，那批均值 3007 tokens/条（动作意图带全量工具描述），拿它预测 180 条全量会高一倍多、把预检直接卡死。改成优先匹配同规模样本（误差 25% 以内），找不到再退回最近一次，而**每请求的真实记账熔断一个字没动**——预测器失真是预测器的问题，不是绕预算的理由。
12. **日预算熔断在真实负载下触发过一次**：全量那一轮跑到第 137 条把当日额度用完，剩下 43 条全部 `LLM_BUDGET_EXCEEDED` 转人工并各自落工单（明细的 `fallback` 与工单号可查）。这 43 条不进统计，按意图补跑取齐；ACTION_ORDER 行在全量与补跑里逐格一致，顺手成了"分数不是抖动"的对照证据。
13. **额度口径照登**：这一轮合计约 102 万 tokens（冒烟 12 条 + 全量两轮 + 四次按意图补跑 + 若干单条复现），优先走 DashScope 的新用户免费额度；跑完把 `.env` 的 `SHOPPILOT_LLM_DAILY_TOKEN_BUDGET` 调回 260000，避免下一次误启动一个挂着真 key 的高额度网关。
14. **验收脚本自己动 `.env` 的那处补了残局提示**：ticket 14 那一步要把模型端点指向死地址，会先把 `.env` 整体挪到 `.env.plan-actions-backup`；若上次中断留下残备份，重跑现在直接给出对照与恢复命令，而不是让人猜哪一份才是带 key 的配置。

**追加追问**

- *Q：93.3% 离 95% 只差两个点，为什么不再调一调？* A：剩下的 miss 有明确归因：ACTION_ORDER 那 4 条是"到哪了"该查订单还是查物流的标注边界，收掉它要合并工具或改判据，两者都是在动口径；ESCALATE/UNKNOWN 那 5 条是转人工字面词表太窄加模型不肯听"别调工具"，扩词表要连着否定词窗口一起改。能靠 Prompt 收的（可选参数、已给信息不重复索要、不虚报已提交）已经收完，实测 ADDRESS 与 REFUND 都到了 94.4%。
- *Q：18 条一批，94.4% 和 95% 有区别吗？* A：没有统计上的区别（1/18 = 5.6 个百分点，94.4% 就是 17/18 对 18/18 的差别）。所以这格数字要按区间读，判据写 ≥95% 是分意图红线，真正过不了线的是 72.2% 那一行——它才是需要解释的。
- *Q：为什么不干脆用 `--force` 越过预算，省得补跑？* A：熔断是 ADR 0012 花血泪教训换来的防线，`--force` 是给人看错预算时的手动出口，不该是流程。缺额度的正确解法是补跑受影响的意图，同时把这一轮的真实消耗与不完整性一起写进报告。


**追加决策（2026-09-10，门禁 eval 冒烟反推）**

15. **冒烟步不是"链路通不通"的摆设，它一天之内抓到两个 dev 全量看不见的缺陷。** 第一个：3B 把用户明明说过的 `city` 留空，而地址四段改成可选之后留空 = 沿用旧值（防线见 ticket 03 追加决策 7 的修订与 README 已知限制）。第二个：三条 ACTION_ADDRESS 全部 `tool_status=IDEMPOTENT_REPLAY`，因为派生幂等 token 只含 orderNo + reason，同一笔订单的第二次改地址被当成重复提交回放第一次结果（见 ticket 12 追加决策 8）。共同点是它们只在"**客户端不带 token** + **弱模型** + **用例之间有业务状态传递**"的 local 形态下暴露；dev 全量用 qwen-plus、且评分只看模型发出的参数，恰好把这三点都遮掉了。
16. **修后的冒烟读数照登**：ACTION_ADDRESS 选对工具 3/3、填对参数 2/3。仍错的那条 `ACT-ADR-02` 漏了 `city`/`district`，而且它现在如实拿到 `STATE_NOT_ALLOWED`——同一批里 `ACT-RFD-01` 先把 90001 推进了退款中，改址被订单状态前置校验拒绝，模型回复"当前订单正在进行退款审核…需要先申请退款"。上一版这条被 REPLAY 掩盖，看起来"成功"，其实是假的。
17. **冒烟的用例顺序是有意保留的有状态形态**：同一 tenant/customer 下 24 条按 CSV 顺序跑，退款用例改变订单状态，后面的改址用例就会撞上状态门。真实会话本来就是这样，所以不为此重新 seed；代价是**冒烟的分数不能与"每条独立"的全量混读**，要读单条能力就按意图补跑。

**追加追问**

- *Q：24 条的冒烟凭什么抓得到 180 条全量抓不到的东西？* A：靠形态不靠样本量。冒烟跑的是不带幂等 token 的对话式入口 + 本地 3B + 用例间状态传递，全量那轮三样都被换掉了（显式 token、qwen-plus、按意图分组）。同一套判据在两种形态下看的是不同的失效面。

**追加决策（2026-09-10，四条否决项的 dev 复核）**

18. **`run-dev-eval.ps1` 末尾那句"顺手把否决项也在 dev 下复核"的提示是错的，它推荐的命令根本不会切模式。** 那句话写的是 `run-acceptance.ps1 -Profile dev -SkipBuild -SkipStack`，而 `-Profile` 只喂给 `stack` 一步，加了 `-SkipStack` 之后它谁也不影响——照着跑完拿到一张 7/7 绿，实际复核的还是 local 网关。这类错比红更糟：它长得像证据。现在换成分开的脚本 `scripts/run-dev-guardcheck.ps1`（自查配置 → 推导并临时抬日预算 → 切 dev 且**回读 `/ops/circuit` 确认 `llmMode=dev`** → 跑七道防线 → `finally` 无条件放回 local 并把预算原样写回），默认干跑不加 `-Run` 一个计费请求都不发，与 `run-dev-eval.ps1` 同一套纪律。
19. **临时预算必须按"当天已用 + 余量"推导，不能拍固定数。** 第一次 `-Run` 把预算写成 400000，而当天账上已经 1,030,471，于是七步全拿到"今日智能助手用量已达上限"的降级答案：那跑的是 ADR 0012 的熔断演练，不是防线复核，而且它本轮 token 增量为 0。真跑通的那一轮临时预算 1,293,128，实花 46,305。
20. **作废判定只看账，不看日志关键词。** 第一版扫 `LLM_BUDGET_EXCEEDED` 判"这轮被饿死"，可 `verify-fallback` 本来就要**注入**这个 reason 去验第七种降级形态——结果七步全绿的一轮被误判成作废。现在的规则是"整轮 token 增量为 0 才算饿"，关键词只留一行说明。这条与 `verify-polarity` 的 exit 3 同一个口径：前提不成立时既不判红也不判绿。
21. **复核结论**：`hitzero`/`action`/`idem`/`fallback`/`polarity`/`l2`/`demo -Which isolation` 七步在 `qwen-plus` 下全绿（`logs/dev-guardcheck-20260910-105633.log`），README 那条"判据写 dev、证据取 local"的口径差就此关掉。原来的理由（这四条不该依赖模型）依然成立，只是不再被当作"没测"的说法。

**追加追问（判据收口）**

- *Q：README 里现在同时留着 93.3% 和 95.6%，是不是留了两套真值？* A：是，而且是有意的。旧那套是当时口径下的真值、也是已经公开引用过的那个数，抹掉它读者就没法核对这轮改动到底动了哪几条；新那套是判据修订后对同一批明细的重算。8 个 id 钉在正文里，改动范围是可审计的，这比"只留一个好看的数"更难被追问倒。
- *Q：放开的资格为什么必须是「对偶矛盾」，而不是"这条看起来也该算对"？* A：后者是品味，一旦允许就没有边界（`ACT-ORD-13` 那条双诉求看起来也有几分道理，而三条真错就没有对偶可指）。前者可机器化：同租户、同订单、同一信息诉求的另一条 gold 标了不同工具，全表 180 条只有 4 组符合，且差异集合由 `--rescore-expected-diff` 锁死，多放开一条重算命令就非零退出。
- *Q：填对参数那一格为什么改报条数、不给一个比率了？* A：因为一个诚实的比率给不出来，就不硬凑。三分法是 57 条比对过且全对、3 条放开后合格工具已打出但明细当年没存它的实发参数（要重跑才判得了）、3 条工具仍未命中天然不可比对。把它们折算成 `57/60 = 95.0%` 是编一个不存在的读数，而本项目全部信用都在"数字怎么量的"这一句上。
