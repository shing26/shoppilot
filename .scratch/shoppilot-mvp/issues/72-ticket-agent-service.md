## What to build

按 ADR 0053 拆出第四个服务。新增 Maven 模块 **`shoppilot-ticket`**（端口 **8092**，本机只监听 loopback，同 biz-mock 的纪律）。

**数据归属由所有者裁定（2026-10-01，见 spec §0 的 B）**：`tickets` 表**随数据迁到工单服务自持**，不与 biz-mock 共库——本机用的是 H2 内存库，内存库是进程内的，两个进程物理上无法共享，共库这条路在当前技术栈下不存在。

因此本票含三件比「抽服务」更重的事：

1. **迁移**：`tickets` 与 `refunds.ticket_id` 相关的建表与数据搬进工单服务自有库（Flyway 基线从 V5 起，工单服务自己的迁移目录）。
2. **改三个生产者**：
   - 网关的降级/情绪升级单改投工单服务（`FallbackService` / `EmailReceiptWriter` 的目标地址）；
   - biz-mock 的退款审批（`applyRefund` 内建审批单）与反馈复核（`openReviewWorkItem`）改为调工单服务 API 落单，不再自持 `tickets` 实体。
3. **跨进程的一致性缺口要显式处置**：退款「受理 → 开单」跳进程后**不再同事务**。处置与边界：**审批的真源是 `refunds.PENDING_REVIEW`（审核队列读它），工单是受理侧的工作项**；开单失败 → 工单缺失但资金安全不受影响，且由审计事件可查。这是登记项，不是「已解决」。

坐席 API（经网关代理后暴露给工作台，浏览器不得直连）：

- `GET /api/tickets?queue=&status=` 队列列表（按优先级排序 + SLA 剩余时间；触发 SLA 超时打戳）
- `POST /api/tickets/{id}/claim` 领取（**乐观锁**：同一工单被两人同时领取必须只有一人成功）
- `POST /api/tickets/{id}/resolve` 处理完成（写 `payload` 与状态，发 `audit` 事件——票 71 的那条）
- `POST /api/tickets/{id}/release` 释放

`up.ps1` / `down.ps1` 加这个服务（`up.ps1` 已有可重入骨架），README 的端口表同步。网关加 `/ops/tickets` 代理（tenantScoped，与退款审核面板同一套门控）。

## 口径

- **不得直连数据库**（0053 禁止跨域直连 DB），跨域只走 API 与事件。
- 本服务是**演示口径**：坐席不写"处理人"以外的组织信息，不做排班。
- 领取用乐观锁，禁止"最后写入获胜"。

## 验收

- 并发领取同一工单，恰好一人 200、另一人 409（用例钉死）。
- 队列列表按优先级排序、且 SLA 剩余时间递减；超时打戳在读路径上生效。
- 租户隔离：跨租户读/领/处理全部拒绝。
- **三个生产者都改完了**：网关的降级单、biz-mock 的退款审批单与复核单，都经由工单服务落库——有用例钉住「biz-mock 不再持有 tickets 表的写入路径」。
- 跨进程一致性缺口按上面的边界处置，并有登记（不是「已解决」）。

## Handoff notes

### 关键决策

1. **`tickets` 与 `routing_rules` 随数据搬进新服务**（所有者裁定 B）。这是本仓第一条「数据随服务走」的迁移：biz-mock 的 `V6` 把那两张表删掉，`V3`/`V4` 是已应用的历史迁移、checksum 不能动，所以是「V1 建出过、V6 又删掉」而不是「V1 从没建过」。留在原地的 `refunds.ticket_id` / `feedback.ticket_id` 是**字符串引用不是外键**，跨库照样能用。
2. **`TicketSource` 进了共享库**（`tool-api` 的 `tool.workitem`）：四个服务都要说这个词，工单服务按它分派、网关按 reason 推它、业务侧落单时要指名它。跨进程共享的东西放契约库，是 ADR 0053「跨域只走 API 与事件」的另一半——连**枚举名**都不该有两个副本。
3. **跨进程契约保持原样，只加了可选字段**：网关那条老契约只发 `reason`，来源由工单服务推导；退款审批与复核单需要指名来源，所以加了可选的 `source`/`payload`。**指名了但解析不出来回 400，不悄悄退回 `DEGRADE`**——拼错的来源名落到默认队列上，正是本仓反复在防的那类静默降级。
4. **领取用一条条件更新而不是 `@Version`**：`update ... where assignee is null and status <> 'RESOLVED'` 正好就是「把没人领的、没结的收下」这个语义，而 `@Version` 会把「谁先改谁赢」泛化到所有字段上——那对别的字段是多余的约束。
5. **领取的三种结局给三种状态码**（204/409/404）：跨租户必须 404 而不是 409，共用一个答案等于告诉别人「这张单存在，只是你领不到」。
6. **工单出口做成端口**（`WorkItemClient` + HTTP 实现 + 测试替身）：本轮起不了全栈（裁定 A），而「退款受理要开一张审批单」必须继续被测到。测试替身**只替代传输**，单号、payload、回指全都照样产生，所以 `refunds.ticket_id` 的断言仍然是真的。
7. **审计发布在工单服务里是精简对偶**：同一个契约、同一条流，落表与查询仍在 biz-mock（审计表只有一份，不造第二本账）。没抽共享 client 模块——那是又一次跨模块重构，登记为后续项，触发条件是第三个服务也要发审计。

### 口径与顺带修掉的东西

- 判据面零改动：gold 180、阈值、`judge()`、`verify_eval_judge.py`、CI 八步。
- **新增 `SHOPPILOT_TICKET_URL` 占位符显式登记进 `ConfigValidationTest` 的钉住清单**（照 round19 票 50 的先例：扩大可配置面要登记，不绕过门禁）。
- **新模块进了覆盖率棘轮**（`shoppilot-ticket` LINE 门槛 68.0）：不进就是让它绕过门禁，而门禁的价值恰恰在于「新写的代码也要被量」。
- **round18 票 43 的慢查询证据跟着工单表搬到了工单服务**（`TicketQueryPlanTest`）：当年被否决的 `(tenant_id, created_at)` 索引照旧被否决，而**新索引 `(queue, priority, created_at)` 站得住**——因为搬家顺带让主查询变成了有上界的按队列取件。两条断言合起来是同一件事：**有上界才有资格要索引**。

### 跨进程一致性缺口（登记，不是「已解决」）

退款「受理 → 开单」跳进程后**不再同事务**。边界写清楚了：**审批的真源是 `refunds.PENDING_REVIEW`（审核队列读它），工单是受理侧的工作项**。所以开单失败不动资金状态，只留下一张没人处理的退款；为此本次受理按已受理继续推进并 warn——宁可让队列里多一张单，也不要让买家的退款卡住。回指拿不到工单号就不写：指向一个不存在的号比空着更糟。

- `\.\mvnw.cmd -B -ntp verify` → **`5 + 59 + 308 + 17 = 389`** 绿（**首次四模块**；biz-mock 38 → 59，工单服务新增 17）。
- 覆盖率：ticket **69.34%**（新门槛 68.0）、biz-mock 77.03%、gateway 62.88%、tool-api 41.67%，`COVERAGE OK modules=4`。

### 未达成（照登不摘红）

- **四服务起栈、端到端活体验收**：全栈约 7 GB，本机只剩 0.5 GB（裁定 A）。所以「网关落单 → 工单服务分派 → 坐席领取」这条真实链路**本轮一次都没跑过**，全部证据都是单模块 JVM 层。
- **`X-Agent` 是自报身份**（身份域是下一轮，ADR 0056）：进审计不进权限。
- 网关的两处改造（`FallbackService`、`EmailReceiptWriter` 改投）只有 JVM 层证据，没有真实 HTTP 到 :8092 的验证。

### 现场三问

1. **为什么数据必须搬，而不能两个服务连同一个库？** H2 内存库在**进程内**，两个进程物理上无法共享；而换共享数据库要动数据库工程，代价远大于搬两张表。
2. **为什么领取不用 `@Version`？** 条件更新表达的正是「领走没人领的、没结的那张」，而 `@Version` 把「谁先改谁赢」泛化到所有字段——那是多余的约束，还会把并发控制的失败面放大。
3. **为什么工单出口要做成端口？** 因为本轮起不了工单服务，而这条行为必须继续被测；端口让生产走 HTTP、测试走内存，而**替身只替代传输，不替代语义**——回指、单号、payload 全部照常产生，所以断言仍然是真的。
