# 18 — 大促压测：双曲线、虚拟线程对比与节约率基线

**What to build:** 两组流量模型的 QPS 拐点与 TP99、一组虚拟线程开关对比、一次关缓存基线跑测，产出全部对外宣称数字的原始数据。落实 ADR 0001、0011。

**Blocked by:** 14 — 降级与工单与 local 验证；15 — 单文件调试台；16 — Tool Calling 标注评测集

**Status:** ready-for-agent

**Verify:** 依次跑双曲线、虚拟线程开关对比、关缓存基线三组 -> 每组结果附带 CPU/堆/版本等环境记录，重跑一次数字在同一量级内可复现。

- [x] `perf` 模式 `MockLLMClient` 固定延迟可配（默认首字 300ms、总时长 500ms），并支持注入超时用于降级演练
- [x] 流量模型两条曲线：L1 主导（55% 文本重复热点 + 15% 口语改写 + 15% 业务办理 + 15% 长尾 RAG）与 L2 主导
- [x] QPS/TP99 压同步端点；SSE 端点单独测 500 并发长连接下的 TTFT 与堆内存占用，两类指标不得混报
- [x] 阶梯 50 -> 100 -> 200 -> 400 -> 800 -> 1200 并发，记录 QPS、TP99、错误率、双口径拦截率，找"QPS 不再上升而 TP99 陡增"的拐点
- [x] 虚拟线程对比实验：`spring.threads.virtual.enabled=false` + 200 平台线程池 vs 开启，同一流量模型两组数据
- [x] Token 节约率：`cache.enabled=false` 重放同一 trace 得基线，再与开启缓存的消耗对比
- [x] 压测每请求生成新幂等 token，否则写操作全被判重复提交
- [x] 记录 HikariCP 连接池饱和点（默认 10 连接会先于 CPU 饱和），调池后复测并写明前后差异

## Handoff notes

**关键决策**

1. 票面要"两条曲线"，实际跑成四条：`l1`（55/15/15/15）、`l2`（口语改写主导）、`mix80`（真实大促塑形）、`biz`（100% 业务办理，专供连接池实验）。加 `biz` 是因为缓存曲线里 DB 根本不被压到，连接池结论必须换一个模型才测得出来。
2. **`l2_delta` 在所有带 embedding 缓存的曲线上恒为 0。** 800+ 条压测语料去重后只有 36 个不同问法，全被 L1 精确哈希先吃掉。这不是 bug，是 ticket 17 标定结论（0.95 工作点 L2 召回为 0）在压测端的复现，报告里明写"语义缓存对本轮拦截率贡献 0"。
3. 拐点判据用"QPS 不再上升 + p99 陡增"两条一起看：`l1` final（4 workers、60s/步）1013@800 → 975@1200 → 862@1600，p99 1800→2200ms 而 p50 稳定在 1200ms。默认阶梯 50→1200 在 15:16 那轮完整跑过，但 Locust 单进程自己先饱和（400 并发只有 517 QPS），所以对外数字取 4 workers 那轮。
4. 压测期间网关进程有两次在 400 并发步后静默消失：无 `hs_err_pid*.log`、无 WER 事件、stderr 为空、端口消失，而同一 400 步在 23:12 那轮是通过。对策不是猜原因，是加 `watchdog.ps1` + 每步健康检查与计数器校验，凡是被污染的步一律重跑并留两枚文件名后缀区分（`-final` / 废弃件保留）。README 已知限制里写"未解决"。
5. 虚拟线程对比取同一 `l1` 模型：`--profile no-virtual`（200 平台线程池）312/600/605/615 vs 开启 296/580/976/1013 QPS。结论限定为"400-800 并发 +64~65%，100-200 并发 −3%"，不写成"虚拟线程永远更快"。
6. Token 节约率做三臂而不是两臂：全关 1096.8 → 只开 SingleFlight 545.1 → 两者都开 412.3 tok/req。任务是 75%，实测 62.4%，按 62% 报，并把"缓存与穿透合并各自的贡献"拆开展示。
7. **HikariCP 那条预设被自己的数据证伪**：`biz` 模型下 pool=2/10/30 三档在 50/100/200 并发给出 38.12/78.73/147.91、38.29/78.81/148.21、38.59/78.87/148.11 QPS，差 ≤1.2%；pool=2 时 pending 峰值 39、取用等待均值 6.52ms、0 超时。原因：每请求模型时延远大于一次 DB 往返，稳态并发连接需求只有 1-2。"默认 10 连接会先于 CPU 饱和"在本机时延预算下不成立，报告写证据不写原预设。
8. SSE 与同步端点完全分开：同步给 QPS/TP99；SSE 单测 500 长连接，TTFT p50 592 / p90 743 / p99 2436ms，堆 142.9→445.0MB。另有 500 条客户端侧 `WinError 10048`（本机临时端口耗尽），标注为发压端限制，不并入服务端错误率。
9. 压测每个虚拟用户每轮生成新幂等 token，否则写操作全部命中 409 重复提交，`biz` 曲线会假性归零。

**需要能当场回答的三个追问**

1. "1200 QPS 是刷缓存刷出来的吧？" —— 口径写在每条 CSV 的 `qps_scope` 和 README：衡量网关编排层，不含模型推理。800 并发的 60456 个请求里仍有 45995 次穿透到 MockLLM（固定 500ms 时延），说明编排层在 26% 穿透率下没先饱和；命中路径本身也要过鉴权、限流、意图三级级联、Redis/Qdrant 读，不是空计数。
2. "800 之后 QPS 反而掉，拐点是不是找错了？" —— 是排队而非崩溃：p99 从 1800 涨到 2200ms、p50 不动，用户数继续加但吞吐被 Little's law 封顶；同时本机可用内存到 0.0GB，发压端与网关抢同一台机器。所以对外报实测峰值 1013 QPS@800 并明写"任务书判据 ≥1200 未达成、发压机同机"，不报 1200。
3. "语义缓存一条没命中，为什么不直接删掉这层？" —— 保留它的理由正是这条数据。ticket 17 已经证明"语义缓存兜口语化改写"在 0.95 工作点、bge-m3、36 个去重问法这套条件下不成立；删掉层就等于删掉证伪证据。当前它对拦截率贡献 0，对写回资格与极性守卫的价值是可验证的防线，两件事分开报。
