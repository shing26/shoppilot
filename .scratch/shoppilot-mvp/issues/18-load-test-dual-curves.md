## Handoff notes

**关键决策**

1. 票面要"两条曲线"，实际跑成四条：`l1`（55/15/15/15）、`l2`（口语改写主导）、`mix80`（真实大促塑形）、`biz`（100% 业务办理，专供连接池实验）。加 `biz` 是因为缓存曲线里 DB 根本不被压到，连接池结论必须换一个模型才测得出来。
2. **`l2_delta` 在所有带 embedding 缓存的曲线上恒为 0。** 800+ 条压测语料去重后只有 36 个不同问法，全被 L1 精确哈希先吃掉。这不是 bug，是 ticket 17 标定结论（0.95 工作点 L2 召回为 0）在压测端的复现，报告里明写"语义缓存对本轮拦截率贡献 0"。
3. 拐点判据用"QPS 不再上升 + p99 陡增"两条一起看：`l1` final（4 workers、60s/步）1013@800 → 975@1200 → 862@1600，p99 1800→2200ms 而 p50 稳定在 1200ms。默认阶梯 50→1200 在 15:16 那轮完整跑过，但 Locust 单进程自己先饱和（400 并发只有 517 QPS），所以对外数字取 4 workers 那轮。
4. 压测期间网关进程有两次在 400 并发步后静默消失：无 `hs_err_pid*.log`、无 WER 事件、stderr 为空、端口消失，而同一 400 步在 23:12 那轮是通过。对策不是猜原因，是加 `watchdog.ps1` + 每步健康检查与计数器校验，凡是被污染的步一律重跑并留两枚文件名后缀区分（`-final` / 废弃件保留）。README 已知限制里写"未解决"。
5. 虚拟线程对比取同一 `l1` 模型：`--profile no-virtual`（200 平台线程池）312/600/605/615 vs 开启 296/580/976/1013 QPS。结论限定为"400-800 并发 +64~65%，100-200 并发 −3%"，不写成"虚拟线程永远更快"。
6. Token 节约率做三臂而不是两臂：全关 1096.8 → 只开 SingleFlight 545.1 → 两者都开 412.3 tok/req。任务是 75%，实测 62.4%，按 62% 报，并把"缓存与穿透合并各自的贡献"拆开展示。
7. **HikariCP 那条预设被自己的数据证伪**：`biz` 模型下 pool=2/10/30 三档在 50/100/200 并发给出 38.12/78.73/147.91、38.29/78.81/148.21、38.59/78.87/148.11 QPS，差 ≤1.2%；pool=2 时 pending 峰值 39、取用等待均值 6.52ms、0 超时。原因：每请求模型时延远大于一次 DB 往返，稳态并发连接需求只有 1-2。"默认 10 连接会先于 CPU 饱和"在本机时延预算下不成立，报告写证据不写原预设。
8. SSE 与同步端点完全分开：同步给 QPS/TP99；SSE 单测 500 长连接，TTFT p50 592 / p90 743 / p99 2436ms，堆 142.9→445.0MB。另有 500 条客户端侧 `WinError 10048`（本机临时端口耗尽），标注为发压端限制，不并入服务端错误率。
9. 压测每个虚拟用户每轮生成新幂等 token，否则写操作全部命中 409 重复提交，`biz` 曲线会假性归零。

**需要能当场回答的追问**

1. "1200 QPS 是刷缓存刷出来的吧？" —— 口径写在每条 CSV 的 `qps_scope` 和 README：衡量网关编排层，不含模型推理。800 并发的 60456 个请求里仍有 45995 次穿透到 MockLLM（固定 500ms 时延），说明编排层在 26% 穿透率下没先饱和；命中路径本身也要过鉴权、限流、意图三级级联、Redis/Qdrant 读，不是空计数。
2. "800 之后 QPS 反而掉，拐点是不是找错了？" —— 是排队而非崩溃：p99 从 1800 涨到 2200ms、p50 不动，用户数继续加但吞吐被 Little's law 封顶；同时本机可用内存到 0.0GB，发压端与网关抢同一台机器。所以对外报实测峰值 1013 QPS@800 并明写"任务书判据 ≥1200 未达成、发压机同机"，不报 1200。
3. "语义缓存一条没命中，为什么不直接删掉这层？" —— 保留它的理由正是这条数据。ticket 17 已经证明"语义缓存兜口语化改写"在 0.95 工作点、bge-m3、36 个去重问法这套条件下不成立；删掉层就等于删掉证伪证据。当前它对拦截率贡献 0，对写回资格与极性守卫的价值是可验证的防线，两件事分开报。

4. "向量服务一挂，你这两级缓存不就白做了？" —— 这正是要量出来的东西，不是要藏起来的东西。`perf,no-ollama` 那组冷缓存实测 136 / 265 / 482 QPS（对照组同条件 296 / 580 / 976），纯缓存拦截率归 0，总拦截靠穿透合并撑在 21.8%-37.4%，错误率全程 0。L1 写回对向量的依赖我们已经拆掉（ADR 0018），但端到端仍然停止积累，因为挡在前面的是 ADR 0006 的"检索未降级"资格：稠密召回 0 命中时新答案一律不入库。这道门是有意保留的——把只有一路召回支撑的答案固化 6 小时、服务恢复后继续复用，比缓存冷掉更糟。生产侧对策是给 embedding 做副本与熔断，运维盯 `shoppilot_cache_embed_unavailable_total` 的增速，而不是等拦截率跌下来才发现故障已经持续了一阵。已有存量不受影响：另一轮 `l1_delta` 608 / 1123 / 2035、命中 p50 8ms，停用的是"积累"不是"复用"。

**"压测期间模型服务停用"这一格怎么做到（2026-09-09 补）**

按字面去停 Ollama 做不到，也不该做：`:11434` 是这台机器上共用的服务，别的进程在用；就算停了，故障还波及发压机自己，对照组与实验组之间会混进"两边抢同一台机器"的噪声。真正要量的东西是"向量服务不可用时网关怎样"，那就把它做成一个 profile：`no-ollama` 只把 `shoppilot.embedding.base-url` 指到 `127.0.0.1:59999`，连接立刻被拒，对网关而言与 Ollama 进程消失完全等价，而故障不外溢。

起进程之后不看日志算数：`run_experiment_suite.ps1` 每组都要从 `/api/v1/support/ops/switches` 回读**实际生效**的开关（`embeddingBaseUrl / cacheEnabled / singleflightEnabled / embeddingInProcessCache / virtualThreadRequest`），对不上就地中止。加这道守卫是因为备料本格时踩到一个真实缺陷——`application.yml` 里一次缩进手误把 `no-embedding-cache` 的属性挂到了 `spring:` 下面，profile 生效、健康检查 UP、日志里 profile 断言也通过，但开关原封不动，整组数据会静默作废。这种失败在日志里看不见，只会在数据里烂掉，所以断言必须在属性这一侧。

**"未命中 TTFT <500ms"这一格：先修量具，再谈达没达成（2026-09-09 补）**

原来挂在 README 上的那条 592ms 是这一格里最经不起问的数字。回去读产出它的脚本，两处测量缺陷：

1. `run_sse_ttft.py` 把"收到第一个 SSE 分片"记成首字，而服务端在检索与模型之前就推 `status`/`meta` 帧——量的是首帧，不是首字。
2. 命中与未命中混在同一个分位数里。500 条长连接跑 60 秒，八成以上是 L1 命中（只有 24 个 (租户, 问句) 组合被反复问），
   所以 592ms 实际是"命中路径在 500 并发下的首帧"，跟它要证明的判据压根不是一件事。

修法：首字只认第一个 `event: token` 帧，`first_frame_ms` 另记一列；按服务端自己在 `meta` 里给的 `cacheLayer` 与 `intent`
分成 `hit` / `knowledge` / `action` 三桶，判据只在 `knowledge` 桶上算；`action` 单列不并入——动作意图按 ADR 0008
最多两轮工具调用，perf 下每轮 Mock 各 300ms，拿它去对 500ms 是要素不对。扫描脚本
`run_ttft_sweep.ps1` 每档先清 L1（mix 臂再串行预热 24 条），两臂各 60s，档位 50→500，
起进程后仍从 `/ops/switches` 回读 `llmMode=perf` 才开跑（沿用 noollama 那格的教训）。

实测（客户端口径，含环回与客户端线程调度）：

| 并发 | 命中 P50/P99 | 未命中·知识 P50/P90/P99 | 未命中·动作 P50 |
| --- | --- | --- | --- |
| 50 | 11 / 45 ms | 1031 / 1328 / 1374 ms | 1146 ms |
| 100 | 11 / 48 ms | 1036 / 1347 / 1657 ms | 1148 ms |
| 200 | 21 / 123 ms | 1049 / 1614 / 1997 ms | 1160 ms |
| 500 | 492 / 603 ms | 1499 / 2089 / 2892 ms | 1634 ms |
| 1（归因跑） | — | 690 / 1331 / 1476 ms | — |

未命中那条在 50-200 并发之间几乎是水平线（1031→1049），所以它慢不是因为排队；命中那条到 500 并发才从 21ms 抬到 492ms，
同机争抢只解释最后那一点。旧 592ms 于是有了准确身份：**500 并发下命中路径的首帧**。

归因（`ttft_attribution.py`，服务端计时器口径，网关刚重启所以计数干净）：单连接串行打强制未命中的知识问句，
服务端 TTFT 均值 725ms = Mock 首字固定下限 300 + 本机 bge-m3 单条新问句向量化 311 + 稠密检索 4.8 + 词法检索 5.8
+ **网关编排余量 104ms**。向量化那一步服务端没有计时器包住（新问句的向量在 `CacheService:124` 的 L2 查表里才现算，
T0 关键词层定案的问句不带向量），所以由 `probe_embedding_latency.py` 从外部实测补上：同句重复 p50 315ms、
新问法 p50 327ms——**这条问句是不是新的根本不重要，本机 CPU 跑一次 bge-m3 就是三分之一秒**。
结论写死在 ADR 0019：500ms 在"perf 的 Mock + 单机 CPU 跑 embedding"这个形态下光靠固定项就过不去（300+311=611ms），
要达成得把向量化挪出关键路径（ADR 0011），或在 dev 口径下用云端模型与云端向量重测（PLAN 写明 dev 只报实测不承诺）。
把 `perf-first-token-latency` 调小能让表变绿，那不改系统，不做。

顺带两条副产品：
- 全新问法在高并发下会被向量服务串行化——100 并发时未命中首字 P50 到 10358ms（50 并发 2779ms）。
  这是 ADR 0011"embedding 是第一瓶颈"的图像版，也说明 `--force-miss` 是合法的压力档、不是最真实的一档：
  真实大促里同一政策问题被问一万次，向量化只发生一次。两臂都跑，只跑一臂会得出相反结论。
- L2 语义缓存在真实噪声下并非零召回：同一政策问句加 8 个随机字母仍以 ≥0.95 命中 L2（扫描里 234 条、归因跑 9 条）。
  与 ticket 17 的"人工改写对在 0.95 召回为 0"不矛盾（那测的是改写，这是同一句加噪声），两句都写进文档，
  免得后来人把"召回 0"读成"L2 永不命中"。

5. "判据没达成，你怎么知道不是网关自己慢？" —— 把首字拆开量：单连接串行时服务端 TTFT 均值 725ms，其中 300ms 是 perf Mock 的固定首字下限、311ms 是这台笔记本跑一条 bge-m3 向量化的实价（外部探针测的，服务端那一步没埋点），检索合计 10ms，剩下 104ms 才是编排。而且未命中那条曲线在 50-200 并发间是水平的（1031→1049ms），排队假设直接被自己的数据否掉。判据仍是未达成，但差距有归属：要么把向量化挪出请求关键路径，要么换云端口径复测，而不是把 Mock 调快。
6. "592ms 那个数当初为什么不能信？" —— 因为它量的不是首字而是第一个 SSE 分片（服务端在检索与模型之前就推 status/meta 帧），而且样本八成是缓存命中，等于拿"500 并发下命中路径的首帧"去对"未命中端到端首字"的判据。修法是首字只认 `event: token`、并按服务端自己报的 `cacheLayer`+`intent` 分桶，旧产物保留但降级标注为"首帧口径"。
