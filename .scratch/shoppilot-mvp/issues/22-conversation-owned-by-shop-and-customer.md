## Handoff notes

**关键决策**

1. **会话归属是“店铺 + 买家”两者，键里保留 token 原始 `customerId`，不做 trim。** 订单行守卫也拿原始 claim 比人；如果会话侧归一化，两道防线会对“谁是同一个人”给出不同答案，尾随空格就可能跨买家合会话。
2. **拿别人的会话 id 不是 403，而是得到同 id 的空会话。** 会话 id 不是授权凭证；修的是上下文可见性，不是把 id 本身变成秘密。这个行为也让现有接入契约保持不变。
3. **待办动作随会话归属，跨买家不能续办。** B 既不能让 A 的参数进入 prompt，也不能触发 A 留下的工具动作；正对照证明 A 自己仍能正常续办。
4. **旧键不迁移。** 旧三段落键缺少可信买家来源，迁移必然需要 `conversation -> customer` 映射，而 ADR 0025 已否决这条额外状态；旧键按 TTL 自然过期，读到时降级为空会话。
5. **缺少买家 claim 时读静默降级、写打 WARN。** 读路径沿用 Redis 不可用时“无上下文单轮”的既有语义；写入没有可靠 owner 时才明确告警，避免把新防线藏进错误分支。

**你需要能当场回答的三个追问**

- *Q：订单查询本来就按店铺 + 买家拦，为什么会话还要再加买家段？* A：订单守卫只保护订单行；会话里还会带历史 turns 和待办工具。没有买家段时，同店不同买家只要拿到会话 id，就能载入别人的上下文，甚至续办别人的动作。两处守的是不同资源。
- *Q：`customerId.trim()` 看起来更稳，为什么反而删掉？* A：系统必须对“同一个人”只有一种判断。订单和幂等键用原始 claim；会话侧 trim 后，`C001` 与 `C001 ` 在一边是两个人、另一边是一个人，等于新开一条合号路径。现在由 `whitespaceInBuyerClaimDoesNotMergeSessions` 钉住原样入键。
- *Q：为什么不把旧会话搬到新键形状？* A：旧键没有可靠的买家归属，要迁移只能维护一张 conv 到 customer 的映射和失效路径，正好违反 ADR 0025 的否决结论。旧键按 TTL 走，期间读到旧形状就当作无上下文，不报错也不污染新键。
