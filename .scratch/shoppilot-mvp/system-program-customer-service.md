## 2. 领域模型要补的东西（domain-modeling 记在这里，实施时落 CONTEXT.md）

- **工单统一实体**：现在仓里"需要人工介入"是三个混血体——① 降级工单（`FallbackReason`→ticket）② 满意度复核队列（feedback）③ 退款审批队列（`Refund.PENDING_REVIEW`）。三套机制三张表。分流要成立，必须先统一为**一个工单实体 + 三种来源**，否则规则表没有分母。
- 新术语候选：工单来源 / 队列（技能组）/ 优先级 / 坐席 / 领取 / SLA 计时与升级。

## 3. 主线（tracer bullet）

**买家在渠道问 → 网关处理咨询 → 办不了/该转人工的自动分流成工单 → 坐席在工作台领取处理 → 结果回流给买家**。
一条竖切打到底，其余域（知识多租户、工具注册制、渠道出站全量）按竖切需要逐步带出，不齐头并进。

## 4. 验证分档（由决策 2 直接派生，必须先落）

| 档 | 内容 | 何时可跑 |
|---|---|---|
| 日常档 | 单服务（网关）或子集 + 中间件，够跑 JVM 门禁与定向验收 | 随时 |
| 全栈档 | 四服务 + 中间件 + local 模型 | **仅清场日**（停掉其他项目容器） |

矩阵与收口审计要按档改；全栈档的红不得冒充日常档信号（同 round17 起的既有纪律）。

## 5. 非目标与登记项（触发条件另立）

- 真 IdP / MFA / refresh token；真支付通道；真实商家数据；公网可达部署。
- LLM 辅助分流、自动派单 push、跨会话记忆、知识反向沉淀（沿用 round19 登记触发线）。
- 微服务治理面（服务发现、配置中心、链路追踪）——四条固定服务名 + compose/脚本编排，够用。

## 7. 风险登记

- **返工**：agent 升级若先于拆分做，编排层会被改两遍——已用"系统竖切先行"规避。
- **本机内存**：全栈 7 GB 与另外四套项目冲突；验证分档是唯一出路，不得为跑全栈去停别人的容器。
- **口径滑坡**：一旦开始写"可上线"式表述，ADR 0024 的红线就破了——新 ADR 必须写死"自用/演示，不宣称上线"。
- **工单统一实体的迁移**：三套机制合并会动历史读数口径（"降级工单"在 README 的枚举 10 口径里），迁移方案必须显式登记，不得静默改分母。
