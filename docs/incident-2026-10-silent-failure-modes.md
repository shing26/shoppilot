# 故障复盘：静默失败的三种形状

> 2026-10-04 / 10-05 两天清场日实测。**本文的可读对象是仓库之外的人**——
> 它不讲这个项目怎么做，只讲「一件事怎么坏掉、怎么被发现的、怎么保证不再发生」。
>
> 涉及的产品缺陷已全部修复并有判据钉住；本文末尾列出仍然开着的部分。

## TL;DR（可对外引用的一段）

一次计划外的实跑发现：**事件骨干从未在真实 Redis 上跑通，而守它的门禁是绿的**。
门禁跑在内存替身上，而「至少一次投递、消费组、ACK、幂等去重」这些语义**只在替身上存在**。
用 Redis `MONITOR` 抓下客户端真正发出的命令后，定位到三个缺陷——一个是**我自己在前一轮引入的**
（把流名当消费组名），一个是**配置整段缺失**导致服务静默退化成单机模式，
一个是**配置写死**导致另一个服务在容器档下一直连错地方。
三者有一个共同点：**全部不报错，且全部发生在被精心设计成「软依赖」的地方**。
事后新增了一条 0 token 的机器判据（比对三个服务的 Redis 配置），它**第一次运行就抓到了第三个缺陷**。

---

## 1. 影响面

- **发现时间**：项目建成约两周后，第一次执行「定期实跑验证」时。架构本身无恙，**是验证从未发生过**。
- **持续时长**：从引入到被发现，跨 3 轮迭代。
- **实际后果**：
  - 审计事件写进 Redis 流但**永远不被消费**——`/api/audit` 恒返回 `[]`；
  - 「人工处理完 → 结论送回买家渠道」这条链**从未真的送出去过一次**；
  - 而**两条门禁都是绿的**：一条跑在内存替身上，一条跑在 HTTP mock 上。
- **谁会受害**：任何相信「审计里有记录」来做对账的人，任何等待「处理结论会通知我」的买家。

## 2. 时间线

| 阶段 | 事件 |
|---|---|
| 事件骨干建成 | 三个服务接入 Redis Streams；门禁用**内存通道**（生产包不放替身，这条纪律是对的） |
| 门禁通过 | 事件对账门禁全绿——但它验证的是「替身 ↔ 消费者」的契约 |
| 登记欠账 | 「真实 Redis 行为零验证」被明确写进欠账清单，触发条件是「有人要求干净克隆可复现」 |
| 两次自测门禁 | 两个浏览器门禁写好、只过语法检查，**按未达成登记**，没有实跑 |
| **清场日** | 第一次真的把栈起全 → **投递门禁 4/7**，投递端一条没送出去 |
| 缩小范围 | 手工 `XREADGROUP` 用**完全相同**的组名/消费者名/流 key **成功取到事件**；配置、db 索引、Redis 实例全部核对无误 |
| 一击定案 | Redis `MONITOR`：客户端真正发出去的命令与手工命令**只差一个参数位置** |
| 修复 | 三个缺陷全修；新增机器判据；两个浏览器门禁补跑（buyer 9/9、outbound 10/10） |

## 3. 三个缺陷

### 缺陷一：把流名当消费组名（我自己，前一轮引入）

`XREADGROUP GROUP <组名> <消费者名> STREAMS <流名> >`。

消费代码写的是 `Consumer.from(流名, 消费者名)`——**而第一个参数是组名**。
于是建组建的是 `gateway-outbound`，读取时却在找一个叫 `shoppilot:channel-outbound` 的组。
后果：每 5 秒一次 `NOGROUP`，事件静静堆在流里，日志刷满 18 条/90 秒的警告。

**为什么没被抓到**：JVM 门禁把整条通道换成了内存实现。**参数顺序错误在那一层根本不存在**——
替身没有组名，也没有命令。

### 缺陷二：配置整段缺失，服务静默退化成单机模式

业务服务的配置文件里**没有 Redis 那一段**，于是框架用了默认值 `localhost:6379`——
而本机的 Redis 刻意偏移在 16379（避开被别的进程占用的标准端口）。

**为什么没被抓到**：Redis 在这个服务里是**软依赖**（设计如此：退款放行不能因为审计发不出去而失败）。
于是「连错端口」的代价不是起不来，而是**安静地变成单机模式**：`/api/audit` 恒返回 `[]`，
没有任何异常、没有任何启动失败、健康检查全绿。
一条 2026-09 就写下的「**软依赖**」决策，在这里第一次露出了它的另一面。

### 缺陷三：配置写死，容器档下一直连错地方

工单服务把 Redis 写死成 `127.0.0.1:16379`，不认环境变量占位符。
而编排系统给所有服务注入的是容器网络里的地址。**它一直在连自己进程的本地端口。**

**为什么没被抓到**：本机档（不走容器）下这个配置**是对的**；只有容器档才暴露。
而容器档是「可选档」，平时很少跑。

## 4. 取证方法：为什么最后是 MONITOR，而不是继续推理

在定位缺陷一时，我做的全是**排除性证据**：

| 试过什么 | 结果 |
|---|---|
| 读类签名（javap） | 看到方法有两个字符串参数——**但签名不告诉你参数的位置含义** |
| 比对服务端身份（INFO server） | 同一台 Redis，排除了「客户端连错实例」 |
| 逐个数据库索引查 | 排除了 db 索引不一致 |
| 手工执行完全相同的命令 | **成功**——与客户端行为直接冲突 |
| 检查配置文件 | 配置正确 |

五步排除把范围缩到一个点：**同一台 Redis、同一条命令、redis-cli 成功而客户端失败**，
差异只能在客户端发出的字节里。
`MONITOR` 会把客户端真正发出的命令**原样打出来**——一步就看见了那个错位的参数。

**教训**：签名告诉你有几个参数，不告诉你参数的含义，也不告诉你实现里加了什么。
**推断出来的东西必须去实测**（同一个教训还纠正了我另一个判断：我在代码注释里写下
「建消费组没有 MKSTREAM 选项」，MONITOR 显示它发出去的就是带 MKSTREAM 的命令——
**javap 只列签名，没列默认实现里加的那个参数**）。

## 5. 我自己的三个错误判断（这一节最值得看）

| 我当时的结论 | 实际情况 |
|---|---|
| 「建消费组没有 MKSTREAM 重载，所以这条路走不通」 | 错。三参默认实现**自带** MKSTREAM |
| 「事件骨干（审计侧）在真 Redis 上没跑通」 | **半对**。审计侧代码本来就是对的，是我把「没触发 drain」和「跑不通」混为一谈；而真正坏掉的是我前一轮新写的出站侧 |
| 把四模块用例数写成五个数（凭空多一个开头的 5） | 笔误，横跨 13 个文件。收口时全部更正 |

第三条最轻微但最值得记：**一个被复制了很多遍的错误数字，比一个错误判断更难发现**，
因为它看起来像「已核对过的记录」。

## 6. 复发防护：加机器判据，不是加纪律

新缺陷不会被「以后更小心」挡住。落地的是一条 **0 token**（不依赖任何外部服务）的判据：

> **比对三个服务的 Redis 配置**：必须都显式声明、必须用同一组环境变量占位符、
> 且**端口默认值必须是偏移后的那个**——只比「有没有」不够，
> 「配了却指向一个被别的项目占着的端口」是同一种病。

**它第一次运行就抓到了缺陷三**（写死配置）。变异对照实测：把配置删回事故形态 → 两条判据都红。

另外补了一条**取证路径**的固化：把「客户端与工具行为不一致时，用 MONITOR 抓真实命令」
写进了欠账清单与代码注释，因为它不属于任何测试能覆盖的形状。

## 7. 这类失败的通用形状

| 形状 | 特征 | 对策 |
|---|---|---|
| **静默降级** | 软依赖 + 兜底路径 → 失败表现为「功能变弱」而非「报错」 | 关键链路要有**可观测的计数**，让「降级了」这件事本身可查 |
| **替身掩盖** | 测试替身没有真实系统的约束（组名、命令、配置注入） | 关键集成点要有**至少一条不替身的判据**；0 token 也能做的（配置一致性）优先做 |
| **可选路径腐化** | 「平时不跑」的档位（容器档、本机档）没人维护 | 可选路径要么定期实跑（本文的 live 档），要么判据明确写「未验证」 |
| **复制放大的错误** | 同一个错误读数被抄进多份文档 | 数字**只更新生成物**，其余引用指向它 |

## 8. 仍然开着的部分（如实列，不挑好看的说）

1. **一条同形状的缺陷未定位**：本机档的启动链路下，业务服务拿不到演示口令，
   于是不播种演示账号 → 登录 401，而栈的 readiness 全绿。手工直接跑另一个脚本则正常。
   ——**它和缺陷二几乎是同一族**，这说明「环境变量传递」这条链还需要一次同样的取证。
2. **最完整的一档跑不成**：需要真实模型的档位要约 6.6 GB，而该机器常驻空闲常在 0.3–0.8 GB。
   所以「真实模型下的端到端」至今**只有 JVM 层与静态证据**。
3. **两个浏览器门禁长期积压**：架构从 1 个服务长到 3 个服务，验证仍按「攒到清场日再跑」的节奏，
   于是每轮都在「JVM 层绿、活体未验」的状态下交付。今天把它固化成了一条能定期跑的档位，
   但**它是否真的会被定期执行，取决于有没有人跑**——这也是一条机器判据管不了的事。
