# ShopPilot：3 分钟读懂

## 一句话

面向电商大促的智能客服与业务网关：把买家问题经**有界 Agent 状态机**送到政策答复、业务工具办理或降级工单，并用实测数据证明缓存、隔离、幂等和降级边界。

## 它解决什么

四个工程问题：

1. 重复热点怎么不进模型？
2. 对话怎么真的改成订单，而不是停在“我帮您提交”？
3. 语义缓存怎么不把“怎么退款”和“为什么不给退款”串到一起？
4. 模型、检索、业务依赖挂掉时，怎么给可解释的降级路径？

## 主链路

```text
Browser/App
    |
    v
Gateway :8082
  Auth -> RateLimit -> Triage
  -> L1/L2 Cache -> Hybrid Retrieval
  -> Agent State Machine -> Function Calling
       |                    |
       |                    +--> biz-mock :8091
       |                         orders/logistics/refunds/tickets
       +--> SSE events / fallback ticket
```

10 个显式状态从 `INTAKE` 走到 `REPLY` 或 `FALLBACK`；工具循环硬上限 2 轮。SSE 事件由状态转移直接产生，客户端只以是否收到 `done` 判断失败。

## 三个最关键取舍

| 取舍 | 结论 |
| --- | --- |
| 缓存放在意图之后 | 放弃一部分拦截率，避免跨意图语义串号；反义对实测余弦 0.9682 |
| 工具循环最多 2 轮 | 自由 Agent 循环无法守住大促时延预算 |
| 阈值 0.95 + 极性守卫 | 0.85 处 precision 只有 0.231；召回不能拿误命中换 |

## 三个数字与一个踩坑

- 命中路径 P99 **22 ms**：200 并发、perf 模式、未饱和队列读数。
- Token 节约率 **62.4%**：关缓存基线与开启缓存同一流量模型对比。
- 虚拟线程收益：400-800 并发 **+64%**；100-200 并发没有收益。
- 踩坑：冷缓存雪崩 8 分钟触发 **35264** 次远程 embedding 且全部失败；加进程内向量缓存、穿透合并和检索失败语义后降到 **18** 次。

最好讲的不是全绿，而是三条未达成仍然保留：拦截率 74-78%（判据 80%）、吞吐 1013 QPS（判据 1200）、未命中 TTFT 690-1499 ms（判据 500 ms），每条都有归因和限制。

## 最值得问我的三处

1. 为什么缓存要放在意图判定之后，而不是链路最前面？
2. 为什么小模型场景仍然自己派生工具、抽槽位并限制 2 轮？
3. 为什么 93.3% 与 95.6% 两套工具准确率读数要并列保留？
