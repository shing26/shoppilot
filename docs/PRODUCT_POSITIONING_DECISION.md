# ShopPilot 产品定位决策（2026-10-26）

> 状态：**已决策 · 选择路线 A（2026-10-26 所有者确认）**。本文只做定位判断，不新增功能。
> 触发：所有者反馈“像重复造轮子，没有突出 Agent 的智能性，应用场景定位开始模糊”。
> 执行包：[ROUTE_A_TRUSTED_RUNTIME.md](ROUTE_A_TRUSTED_RUNTIME.md)。

## 一、结论先行

**ShopPilot 现在不是“Agent 智能产品”，而是“一个可验证、可审计的受控 LLM 客服运行时”。**

继续按“通用智能客服 + Agent”讲，会同时输给两类对手：

- 大厂客服平台：功能更全、开箱即用、渠道与生态更强；
- 通用 Agent 框架：自主性更强、扩展更快、社区更大。

当前真正稀缺的不是“能聊天、能调工具、能转人工”，而是：

- 每次回答可回放到 trace / 工具 / 证据；
- 工具有风险分级，资金动作有 HITL；
- 租户与买家隔离有真实 HTTP 反证；
- 评测有 golden、离线 rescore、任务级判据、覆盖率棘轮；
- 质量旁路与告警有 promtool 双侧测试。

所以下一步不是继续加 Agent 功能，而是**选一个能把这些资产变成价值的定位**。

## 二、项目事实盘点

### 已经成立的（不是 demo）

| 资产 | 现状 | 价值 |
| --- | --- | --- |
| 四模块运行时 | gateway / biz-mock / ticket / tool-api | 真实跨进程链路，不是单体演示 |
| 测试与门禁 | **708 tests / 118 suites**，CI 全绿 | 可回归、可交接 |
| 编排 | 确定性 triage、角色、Handoff、工具轮次 | 可控、可审计 |
| 安全 | 租户隔离、买家归属、HITL、幂等、审计 | 能碰真实售后场景 |
| 评测 | 180 gold、UX 30、Handoff 23、promtool | 结果可比较、可复跑 |
| 产品面 | 买家双栏、坐席三视图、订单入口 | 已经能演示完整闭环 |
| 观测 | Agent Run、质量报表、风险指标 | 行为可解释 |

### 仍然是商品化能力的（不构成差异化）

- 聊天窗口
- 快捷问题
- 订单/物流查询
- 工单队列与人工接管
- 退款审批
- 基础看板

这些主流平台都有，而且更成熟。**不能拿它们当卖点。**

### 当前“Agent 智能性”的真实水平

- 有工具调用、有反思重试、有多步计划展示；
- 但计划由代码生成，模型不能自主改计划；
- 复合任务只覆盖一个窄场景；
- 没有长期记忆、没有跨会话目标、没有自主任务队列；
- 没有“根据观察改变后续策略”的通用能力。

**结论：当前是“可解释的自动化”，不是“自主智能”。**

## 三、三条可选路线

### A. 可信 Agent 运行时（参考架构 / 技术资产）

**一句话：** 不卖客服，卖“怎么让 LLM 在真实业务里可验证地工作”。

**目标用户：**
- 招 AI / 后端岗位的评审者；
- 需要参考架构的工程团队；
- 对“可审计 Agent”感兴趣的内部技术决策者。

**为什么是我们：**
- 现有资产几乎全部匹配：trace、HITL、隔离、评测、门禁；
- 不需要新用户、不需要商业化验证；
- 可以把现有 README / EVIDENCE 直接升级成可信度材料。

**还需要补：**
- 一页纸定位与 3 分钟演示路径；
- 与主流方案的对比矩阵（不是功能清单）；
- 一篇“为什么可验证比更智能更重要”的技术文章；
- 把质量报表/Agent Run 作为证据，而不是产品功能继续扩。

**验证方式：**
- 5 位目标读者能否在 10 分钟内说清“这项目解决了什么别人没解决的问题”；
- 3 位工程评审者能否复跑证据链。

**风险：**
- 没有商业价值，只有技术/职业价值；
- 容易被看成“又一个客服 demo”。

**停止条件：**
- 如果目标是创业或收入，这条路不应继续投入功能开发。

---

### B. 垂直售后异常处理 Agent（产品）

**一句话：** 不做通用客服，只做“售后异常处理”这一条深水区。

**目标用户：**
- 有售后团队、但异常单仍靠人肉跟进的电商/零售企业；
- 典型痛点：查物流、判责任、算赔付、改地址、补发、退款审批跨多个系统。

**为什么可能成立：**
- 主流客服平台擅长标准工单，不擅长跨系统异常决策；
- 现有工具、HITL、审计、Handoff 正好是异常处理的底座；
- Agent 的智能性只有在“信息不全、需要多步判断”时才有价值。

**还需要补：**
- 一个真实客户的 3 个异常流程；
- 领域数据与规则（赔偿标准、责任判定）；
- 与现有工单/订单系统的接入；
- 任务级成功率、人工介入率、处理时长对比。

**验证方式：**
- 找到 3 个设计伙伴，愿意给真实流程与数据；
- 用 2 周做人工模拟，证明比现有流程少 30% 人工步骤；
- 没有设计伙伴就不写代码。

**风险：**
- 强依赖行业资源与客户；
- 现有代码要重做产品面与领域模型；
- 销售周期长。

**停止条件：**
- 2 周内拿不到 3 个愿意共创的客户，立即停止。

---

### C. Agent 可靠性 / 评测基础设施（基础设施产品）

**一句话：** 不替企业做客服，替企业证明它的 Agent 可靠。

**目标用户：**
- 正在落地 Agent 的平台团队；
- 需要审计、回归、评测、HITL 证据的工程组织；
- 受监管行业的 AI 落地团队。

**为什么可能成立：**
- 现有 golden / 任务级评测 / trace / 审计 / promtool 是最接近差异化的资产；
- 大厂有内部工具，但外部团队缺少可复用的“Agent 证据链”；
- 与具体客服场景解耦，市场更大。

**还需要补：**
- 把评测与 trace 抽象成独立工具，而不是绑在 ShopPilot 上；
- 定义输入格式、任务级指标、失败分类；
- 找到 5 个正在做 Agent 的团队做访谈。

**验证方式：**
- 5 个团队中至少 3 个能说出“我们现在怎么做评测、为什么不够”；
- 至少 1 个愿意试用/付费试点。

**风险：**
- 市场教育成本高；
- 需要从应用项目中抽离，工作量不小；
- 商业路径比 A 长。

**停止条件：**
- 访谈里没人把评测/审计当独立预算项，就回到 A。

## 四、决策矩阵

评分 1-5，5 最好。

| 维度 | A 参考架构 | B 垂直产品 | C 评测基础设施 |
| --- | --- | --- | --- |
| 与现有资产匹配 | 5 | 3 | 4 |
| 2 周内能出证据 | 5 | 2 | 3 |
| 差异化潜力 | 2 | 4 | 5 |
| 商业潜力 | 1 | 4 | 3 |
| 所需外部资源 | 1（不需要） | 5（客户/行业） | 3（访谈） |
| 失败成本 | 低 | 高 | 中 |

## 五、决策（2026-10-26 已确认）

**已选择路线 A：暂停功能开发，按“可信 Agent 运行时”包装与验证。**
B 只在拿到 3 个设计伙伴后启动；C 保留为后续可验证方向，不并行开工。

理由：

1. 当前没有真实客户证据，直接转 B 是把工程资产押在假设上；
2. C 与现有评测/审计资产最匹配，且可以先用访谈验证，不需要重写系统；
3. A 是保底：即使 B/C 都不成立，现有项目仍然是一个完整、可验证的技术作品；
4. 继续做通用客服功能，是三条路里期望收益最低的。

## 六、接下来 14 天（不写功能代码）

1. **第 1-2 天**：把本文压缩成一页纸，明确“我们不是什么”。
2. **第 3-7 天**：访谈 5 位目标用户（售后负责人 / Agent 平台工程师 / 技术评审），只问现状与预算，不推销方案。
3. **第 8-10 天**：做一张与 3 个主流方案的对比矩阵，按“可验证性 / 异常处理深度 / 接入成本”而不是功能数量比较。
4. **第 11-14 天**：做决策评审：
   - 有 3 个设计伙伴 → 转 B；
   - 有 3 个评测痛点 + 1 个试点 → 转 C；
   - 都没有 → 保持 A，停止功能扩张，只做文档与演示。

## 七、明确停止清单

在定位决策前，停止：

- 继续加客服功能（聊天、工单、看板、订单入口）；
- 继续扩展 Agent Run / 复合任务；
- 启动路线 B 的自主循环；
- 启动 H5 MCP 适配；
- 为“看起来像 Agent”而加视觉或话术。

只保留：

- 事实性 bug 修复；
- 安全/隔离/回归修复；
- 证据链维护。

## 八、一句话判断

**继续做“更聪明的客服”，会输给平台；把“可验证的受控 Agent 运行时”做深，才可能是这个项目真正的差异点。**
