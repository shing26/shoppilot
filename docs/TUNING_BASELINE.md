## 一、结论先行

当前红点不是“模型能力不够”一个原因，而是四类不同问题：

1. **意图/工具边界**：物流口语说法被当成订单查询，越界请求被当成订单查询；
2. **升级动作缺失**：用户明确要求真人，系统有时只在话术里说“转人工”，但没有真正升级；
3. **多意图优先级**：改地址 + 查状态同时出现时，模型退化成只查详情；
4. **小模型答案保真**：意图、引用都对，但答案没带出已检索到的关键事实。

因此阶段 1 不能只“扩词表 + 改 prompt”，必须先修**升级动作**和**动作工具准入**。

## 五、根因分类

### A. 意图 / 工具边界（可确定性修复）

**证据：** ACT-LOG-06 / 09 / 13 / 14 / 18 中，多处把“订单号 + 口语动作”判成 ACTION_ORDER，随后调用 queryOrderDetail。

**判断：**

- “有没有人代收”“这单发了没”是物流语义，但 T0 词表没有覆盖；
- 一旦落到 ACTION_ORDER，模型就会选 queryOrderDetail；
- 这不是模型不会，是上游意图入口把路带偏。

**修复归属：** Triage T0 词表 / 动作证据；工具派生；不改 prompt 主策略。

### B. 升级动作缺失（最高优先级）

**证据：** ESC-03 / 05 / 14 / 18 全部未真正升级。

其中 ESC-14 / 18 更严重：

- 用户已经说“机器人办不了就叫人”“没个活人说不清楚”；
- 但意图被分成 POLICY_PROMO / UNKNOWN，后续没有任何升级动作；
- 模型话术里可能说“帮您转接”，但没有落工单，escalate_ok=false。

**判断：** 当前升级依赖 intent == ESCALATE，而用户表达升级时，意图可能被其他分区抢走。  
**这是 Agent 信任问题：嘴上说转人工，系统没转。**

**修复归属：** 新增独立的显式升级检测（不依赖最终 intent），在工具选择之前裁决；需要 JVM 用例钉住“话术说转”和“实际升级”一致。

### C. 多意图优先级

**证据：** ACT-ORD-13 同时有“改地址”和“查状态”，系统退化为只查详情。  
**判断：** 动作优先规则没有覆盖多意图；缺槽位时没有强制走结构化追问。  
**修复归属：** 动作意图优先 + slotAsk 结构化约束 + 服务端校验。

### D. 小模型答案保真

**证据：** G-006 / G-026 / G-029。  
**判断：**

- 不是检索不到（citations=true），是答案没把关键事实写出来；
- 不是意图错（POLICY_FRESH / POLICY_HOTEL 正确），是回答策略被“要订单号”带偏。

**修复归属：**

- 关键事实注入（48 小时必须出现）；
- 政策回答模板：结论 + 关键数字 + 引用；
- 政策意图禁止无必要地索要订单号。

## 六、阶段 1 调整后的优先级

原计划顺序需要调整：

1. **先修 B（升级动作）**：这是信任问题，且影响所有意图；
2. **再修 A（物流 / 越界工具准入）**：确定性高，直接提升 3 个意图；
3. **再修 C（多意图 + 槽位）**；
4. **最后修 D（小模型答案保真）**，进入阶段 2。

理由：B 不修，即使工具准确率到 95%，用户说“转人工”仍可能没有工单；这比一个工具选错更严重。
