# 面试问答清单（由各 ticket 的 Handoff notes 生成）

生成方式：`python scripts/collect_interview_questions.py`。
每题答案直接取自当时写下的收尾记录，不做事后润色——答不上来的就是当时没想清楚的。

共 93 问，覆盖 20 个 ticket。

用法：每条先只看问题，自己答 30 秒，再对答案。答不出细节的题回去读对应 ticket。


## Ticket 01 — skeleton and compose

**Q：为什么 ES 用 7.17 而不是 8.x？**

A：8.x 强制 HTTPS + 客户端版本协商，本机内存预算下多一层安全握手不值当；7.17 的 `_search` + BM25 就是这个项目要用的全部能力，闭源特性一个没用。

**Q：Redis 设了 `allkeys-lru`，缓存被驱逐了怎么办？**

A：语义缓存的正确性不依赖 Redis 驻留——L1 被驱逐等价于一次 miss，走穿透路径重新生成并写回。真正不能丢的是幂等记录，那部分有 biz-mock 的 DB 唯一约束兜底（ticket 12）。

**Q：`./mvnw` 在你机器上跑得起来吗？**

A：能，但要注意本机 `mvn` 的全局 `conf/settings.xml` 把 `localRepository` 指到了 `E:\maven_repository`，而 wrapper 用的是默认 `~/.m2/repository`。离线复现时加 `-Dmaven.repo.local=E:\maven_repository` 即可对齐；干净机器联网首跑不需要这个。

**Q：两个检出为什么不能并存？容器名不是 compose 自己管的吗？**

A：项目名是 compose 按目录算的，但 `container_name` 一旦写死就是 Docker 全局唯一的容器名，两套检出抢同一个名字，而且"停着"不等于"释放"。我保留钉死的名字（换来的是 README 里那几行命令直接可用），把冲突做成脚本里的显式前提：`down.ps1 -Containers` 现在 stop + rm 腾名字，`clean_clone_check.ps1` 前置检查还会查那三个宿主端口有没有被占用、并把空闲物理内存打出来——克隆起来的第二套全栈在这台 16 G 机器上本身就是失败源。

**Q：你的中间件健康检查真的在检查东西吗？**

A：Qdrant 那条以前没有——它恒红，因为镜像里根本没有 wget/curl，`CMD-SHELL` 每次都 127。2026-09-10 换成 `bash` 的 `/dev/tcp` 手搓 `GET /readyz` 断言 200，才第一次转绿。教训不在 Docker，在"红了一周的东西没人去问为什么红"：现在我对任何健康检查的第一问都是"它失败的时候长什么样"，能稳定失败的检查才有资格说它成功。

**Q：既然 PATH 上有 java，为什么不直接用它？**

A：因为本机 PATH 上是 JDK 18，而项目要 21（虚拟线程）。解析顺序里 PATH 只排第三，而且排在前面的候选也一样要过版本校验——顺序解决"用哪个"，校验解决"能不能用"，两件事不能合并成一条。实测四种组合：给了 21 就用 21；`JAVA_HOME` 指到 18 会被跳过并继续找；全都不是 21 时报错会列出试过的来源与版本号。


## Ticket 02 — mock jwt identity

**Q：伪造一个 claims 正确的 JWT 不行吗？**

A：HS256 验签需要密钥；未签名（`alg=none`）与错签名都在 `JwtService` 解析阶段抛错，filter 直接 401。过期 token 同样 401，`AuthFilterTest` 三条用例分别覆盖无 token、伪造、过期。

**Q：那 `/auth/mock-token` 怎么算？它不要任何凭证就能签出任意身份的 token。**

A：那是**身份领取**，不是**身份伪造**，`CONTEXT.md` 里这两个词分开定义。领取端点只在回环绑定上注册（ADR 0029）：`server.address` 一旦不是回环，这个 bean 根本不装配，三处 dev 默认凭证任一没被环境变量覆盖就拒绝启动，运维端点还要求显式关闭或换成非默认令牌。回环上它照旧是调试台的正门，观测面同时自报「正在吃哪几处默认值」。指标表那一格钉的是验签，不是拿不到身份——这个区分是本轮自己抓出来的，之前那句话说过头了。

**Q：网关重启后 token 会失效吗？**

A：不会，密钥在环境变量里，不在进程内存里。这是有意的——重启打断正在打字的用户已经够糟，再把所有人的会话踢掉是雪上加霜。

**Q：为什么不直接把 tenantId 放进 MDC 或者方法参数往下传？**

A：往下传要改一长串签名，改一处漏一处就是越权；MDC 只用于日志，不作为可信来源。`TenantContext` 是唯一可信入口，且有架构测试兜着。


## Ticket 03 — biz mock data foundation

**Q：A 店查 B 店订单，为什么返回"未在本店找到该订单"而不是 403？**

A：403 会确认"这单存在"，本身就是信息泄露。`@TenantId` 让 B 店订单在 A 店的会话里根本不可见，语义上等价于不存在，这也是 CI 用例的断言内容。

**Q：5 万订单在 H2 上不会慢吗？**

A：会，而且慢是设计的一部分——H2 写入是本项目已知的吞吐瓶颈（README 已知限制里写明）。压测报告里的 TP99 含这段真实成本，不是内存玩具。

**Q：seed 数据是随机的，演示怎么保证可复现？**

A：随机造数之外另钉四张演示固定单 90001-90004（ticket 12），`POST /api/admin/demo/reset` 复位。

**Q：地址四段都可选，会不会把一条空地址写进去？**

A：不会。`receiverName` 与 `receiverPhone` 仍是必填，缺任一项在网关侧就 `SLOT_ASK`；四段留空在 biz-mock 侧是"沿用原值"，写历史与回包用的都是合并后的完整地址。

**Q：`reason` 默认为什么填在 biz-mock 而不是网关？**

A：默认值是业务规则（哪种退款理由算主观），归业务系统所有；网关只负责把"模型没抽到这个字段"如实传下去。放在网关会让 Mock 中台的语义随编排层漂移。


## Ticket 04 — knowledge ingestion

**Q：为什么不用现成的文档解析框架？**

A：语料是自己写的 Markdown，标题层级就是天然结构；引入解析器只增加依赖和不确定性。切分逻辑集中在 `MarkdownChunker` 一个类里，好测也好改。

**Q：90 块是不是太少？**

A：对演示与压测足够，因为要测的是链路而不是召回率上限。真正的信息量在元数据过滤（scope/tenant/intent）上，块数增加不改变结论。

**Q：重跑会不会产生重复向量？**

A：不会，Qdrant 用 `ruleId` 作 point id，重复写是覆盖；验收就是"连跑两次两边条目数相等且不增长"。


## Ticket 05 — thin vertical slice

**Q：为什么用 SSE 不用 WebSocket？**

A：单向服务端推流 + 断线重连是客服场景的全部需求，SSE 走 HTTP/1.1 与现有网关鉴权、限流、`SseEmitter` 天然复用，不需要协议升级与第二套连接管理。

**Q：`done` 事件里的 citations 从哪来？**

A：检索层返回的规则块 `ruleId` 列表，随 `CacheEntry.sourceRuleIds` 一起缓存。命中缓存的回答仍带原引用，所以引用不是"只有实时链路才有"的装饰。

**Q：这条竖切和最终架构差多少？**

A：只差 ES 那一路检索（ticket 08）、L2 语义缓存（ticket 09）、工具闭环（ticket 10/11）。状态机骨架、事件契约、身份注入、三模式模型依赖从第一天起就是最终形态，没有临时脚手架。


## Ticket 06 — l1 cache admission writeback

**Q：怎么证明命中路径没碰模型和向量库？**

A：靠计数器不靠读代码。`shoppilot_llm_calls_total{kind}` 与 `shoppilot_embedding_calls_total{result=remote|in-process-cache}` 是为此专门加的；`scripts/verify-hit-zero-llm.ps1` 冲缓存后同一问题问两次，第二次的模型与远程 embedding 增量必须为 0。

**Q：为什么 L1 TTL 是 6 小时而不是跟着政策走？**

A：跟着政策走的是 `kbEpoch`——纪元一变，key 变了，旧条目自然读不到，TTL 只是兜底回收。政策生效不需要等缓存过期。

**Q：等待者拿完整结果，那第一个请求的流式体验不是被复制了两遍？**

A：不会。穿透者自己流式输出，等待者只在 leader 完成后一次性拿到整段答案并作为单个 `token` 帧推出。代价是等待者没有打字机效果，收益是不用维护 N 路转发；2 秒等待上限保证最坏情况也只是退化成自己穿透。


## Ticket 07 — intent cascade

**Q：为什么不直接让模型分类？**

A：一次模型调用的时延与成本要摊到每个请求上，而 80% 的请求 T0/T1 就能定案。三级级联把分类成本从"每请求一次"降到"少数请求一次"，且 T0 规则可解释、可单测。

**Q：T1 质心会不会一换语料就崩？**

A：质心由 `intent-samples.json` 现算并缓存到 `shoppilot.triage.centroid-cache`，按样本指纹失效；改样例句会重算，不需要重新入库政策语料。

**Q：10 个意图封顶够吗？**

A：对电商客服场景够，且这是刻意的上限——意图数线性影响质心维护成本与误判面。新增意图要走规则表与样例句双份改动，这个摩擦是有意的。


## Ticket 08 — es bm25 rrf fusion

**Q：只有 90 个块，为什么要上 ES？**

A：测的是链路形态而不是召回率上限。真实店铺的规则库是万级，届时稠密向量单独召回会在术语精确匹配上失手，混合检索是标准解；本项目把它在 90 块上先跑通并量化差异。

**Q：RRF 为什么 k=60？**

A：论文给出的经验值，作用是压平头部名次的分数差。语料这么小时 k 在 40-80 之间不改变 top-5，所以不做扫描——扫了也只是给噪声取名字。

**Q：两路都超时怎么办？**

A：任一路失败按空结果处理，另一路仍可出答案；两路都空则走 `INTENT_UNRESOLVED` 降级并落工单，不硬编一段"抱歉"进缓存。


## Ticket 09 — l2 semantic cache epoch

**Q：0.95 这个阈值是拍脑袋的吗？**

A：不是，ticket 17 用 118 组对抗对做了 0.85-0.99 扫描。实测结论是 bge-m3 在短中文问句上同意图改写对的最大余弦只有 0.9435，**0.95 工作点上 L2 召回为 0**——这条已经写进 README 的已知限制，不藏。

**Q：那 L2 还有什么存在价值？**

A：它兜的是"同一政策、写法极近"这一小撮，以及为将来换更强的 embedding 模型预留位置。80% 级拦截实际由 L1 精确哈希与 SingleFlight 承担，这是实测归因，不是设计意图。

**Q：反义问句会不会被 L2 复用？**

A：会，而且实测确实会——有 4 组同桶反义对越过 0.95（0.9645-0.9802），两侧还都在同一个 `POLICY_*` 意图里，阈值和意图分区都拦不住。所以补了 ADR 0016 的 `PolarityGuard`：条目携带原始 `query`，判定肯定/否定极性不一致就拒绝复用并计数 `shoppilot_cache_l2_polarity_blocked_total`；条目缺 `query` 时 fail-closed。

**Q：你的清缓存按钮把自己服务打挂过？**

A：不是打挂，是**报错了但语义没错**。删表重建中间有几十到几百毫秒表真的不在，

**Q：为什么不给 flush 加锁，让检索等表建好？**

A：为一个"清空"动作把在线读路径阻塞几十毫秒不值——缓存空的时候


## Ticket 10 — tool contract http boundary

**Q：为什么不直接用 Spring 的 `@HttpExchange` 声明式客户端？**

A：可以用，但那样 schema 生成与调用签名仍是两份东西。真正的约束是"同一份 DTO 派生两侧"，用哪种 HTTP 客户端是次要的；选 JDK `HttpClient` 还省掉一层依赖并让超时与熔断的接线看得见。

**Q：内部 token 泄漏到浏览器怎么办？**

A：泄漏不到。浏览器只与同源网关通信，`X-Internal-Token` 由网关在服务端补上；调试台的运维动作经网关代理端点转发，代理额外要求 `X-Ops-Token`（ticket 15 的 Playwright 验收里有一条专门断言页面拿不到内部 token）。

**Q：biz-mock 挂了用户看到什么？**

A：熔断打开后请求不再打过去，直接 `TOOL_UNAVAILABLE` 降级并落工单，`GET /ops/circuit` 能看到 `CLOSED/OPEN/HALF_OPEN` 与模型名、当日 token 用量。实测停进程后返回降级语义而非 500。


## Ticket 11 — action loop

**Q：网关直接执行工具，那还要 Function Calling 干什么？**

A：分工不同。网关只在"槽位来自用户原话且可确定性抽取"时接管读操作；意图判定、参数不全时的追问、写操作前的确认、以及把结构化结果组织成人话仍然归模型。写操作不接管是硬边界——自动改址/退款的错误代价不对称。

**Q：2 轮上限会不会把复杂问题判死？**

A：会，而且是故意的。超限走 `FALLBACK` 落工单，比让用户在屏幕前等第 5 轮更负责。`shoppilot_tool_round_exhausted_total` 计数，真流量里这个数就是"该扩到 3 轮"的证据。

**Q：A 店买家问 B 店订单，怎么保证不泄露？**

A：仓储层按 `(tenantId, orderNo)` 查，查不到就是查不到，返回 `NOT_FOUND`，网关文案固定为"未在本店找到该订单，若您在其他店铺购买请联系对应店铺客服"。响应里没有任何 B 店字段，因为根本没读出来。`TenantIsolationAndIdempotencyTest` 有这条越权用例。

**Q：同一家店里两个买家把会话 id 填成同一个值，谁能看见谁？**

A：票 22 之前是同店铺内双向可见：会话状态外置在 Redis，键是 `shoppilot:session:{tenant}:{conv}`，不含买家，而 `X-Conversation-Id` 由客户端自带。B 填成 A 的值，就把 A 的对话轮次载进了自己的 prompt，还能把新轮次写回 A 的会话；A 办到一半的改址会被 B 的输入接着续办。改法是键里加一段买家归属（ADR 0025），旧键不迁移、靠 TTL 自然走。「服务端派生会话 id、拒收客户端自带」是被否决的选项——客户端自带是真实接入方的常态形状，该动的是隔离而不是接入契约。量具九条，其中一条是正对照：同一套夹具下 A 自己的待办动作确实会被续办，否则那几条 `never()` 断言可能只是链路没跑起来的白绿。README 那格「串号防线」只写上下文可见性，没写成跨买家隔离已达成——订单行与含买家的幂等键那道守卫本来就按「店铺 + 买家」拦，这次修的是另一扇门。

**Q：为什么不直接 `tool_choice=required` 逼模型必调工具？**

A：那会打死合法的槽位追问。`我要退款` 没给订单号，正确行为是问，而不是拿一个编造的订单号去撞库——`required` 会把"绝不猜订单号"这条硬线换成"必须发一个调用"。现在仍然 `tool_choice=auto`，纠偏消息里也明说"必填参数确实缺失就照实向用户追问"。

**Q：纠偏轮会不会被模型用来再查一次别的工具、绕回老路？**

A：轮次预算仍然封顶，第二次规划如果又发查询，`rounds` 到 2 就出循环，答案照常落地，只是没救回来；`shoppilot_write_nudge_total` 与评测明细里的 `corrective_round` 列让这种绕行为看得见。

**Q：为什么只对两个写操作做，读意图不查？**

A：读意图答错的后果是信息不全，写意图答错的后果是顾客以为钱已经退了。这条防线守的是"承诺与事实不能分家"。


## Ticket 12 — write idempotency state guard

**Q：Redis 挂了会不会重复退款？**

A：不会。`IdempotencyService.begin()` 捕获 Redis 异常后放行，但 biz-mock 的 `uk_refund_idempotency` 会在插入时抛 23505，`applyRefund` 捕获后回查首次记录并返回 `IDEMPOTENT_REPLAY`。`TenantIsolationAndIdempotencyTest` 里有一条用例直接绕过网关、用同一个 token 往仓储层插两次，断言唯一约束拒绝。

**Q：50 个并发同 token 请求，为什么不是 1 成功 49 个都插库撞约束？**

A：两层。Redis `SETNX` 先让 1 个请求拿到占位，其余 49 个看到 `__PENDING__` 后 `waitForResult` 最多等 300 ms；等不到结果的再抢 `lock:{tenant}:{order}` 业务锁。实测 50 并发 = 1 个 `OK` + 49 个 `IDEMPOTENT_REPLAY`，库里恰好 1 行。

**Q：幂等和分布式锁不是重复了吗？**

A：职责不同。幂等键解决"同一请求别执行两次"，业务锁解决"同一订单的两个**不同**请求别并发改写"（比如同时改地址和申请退款）。锁带 10 秒租约，释放失败最坏是提前占用一个租约窗口，不会死锁。

**Q：参数进哈希之后，用户把同一句话再说一遍还算幂等吗？**

A：算。同一句话 -> 同一组参数 -> 同一个派生 token，回放首次结果；这条由 `identicalPayloadReplaysTheFirstResult` 钉住。变的只是“参数不同”不再被误判成重试。

**Q：那用户连改三次地址，会不会留三条地址历史？**

A：会，而且应该留——`address_history` 每次带 version 递增，这是审计链不是脏数据；防刷由 ticket 13 的令牌桶与同一订单的写锁承担，不该拿幂等键当限流用。

**Q：为什么门禁冒烟之前没发现？**

A：因为幂等验收（`verify-idempotency.ps1`）用的是显式同 token 重放，走的正是客户端带 token 那条分支，派生分支从来没有 JVM 用例覆盖。这次是评测链路把“真实对话里客户端不带 token”的形态跑出来了。


## Ticket 13 — rate limiting

**Q：为什么不用 Sentinel 或网关自带的 RequestRateLimiter？**

A：要的是"按店铺配额 + 按买家/IP 双维度、且配额能从业务系统读"。Spring Cloud Gateway 的限流挂在路由层，读不到业务配额；Redisson `RRateLimiter` 是现成的分布式令牌桶，几十行代码就够，不用为此引入一个组件。

**Q：Redisson 的速率改了为什么不生效？**

A：这是实测踩到的坑——`trySetRate` 只在"没设置过"时生效，是幂等首写；配额变更后必须显式 `setRate`。现在按 `appliedRates` 记录本进程已对齐过的速率，只在配额变化时写一次 Redis，顺带把每请求 3 次 Redis 配置写降掉了。

**Q：限流和幂等锁不重复吗？**

A：不重复。限流管"这个买家每秒能问几次"，幂等管"同一个动作别执行两遍"，业务锁管"同一订单的两个不同动作别并发写"。三者键空间不同、失败语义不同。


## Ticket 14 — fallback tickets local mode

**Q：七种降级你怎么证明不是写在纸上的？**

A：`scripts/verify-fallback.ps1` 一条命令跑完七种，每种打印 `reason` 与 `ticketId`，末尾再经网关代理拉一次工单队列做交叉核对。LLM 三种靠 `LlmFaultInjector`，工具一种靠 biz-mock `failRate=1.0`，限流一种靠连打超配额，槽位一种靠两轮对话拒答，转人工一种靠用户直接说。另有 `FallbackReasonTest` 6 项守住"枚举齐全 + 每种都落单 + 每种都有话术"。

**Q：为什么 `LLM_CIRCUIT_OPEN` 和 `TOOL_UNAVAILABLE` 是两个原因而不是一个？**

A：熔断器分别套在模型调用链和业务调用链上，恢复时间差一个数量级——模型超时可以先降级到本地小模型，业务系统超时只能转人工。合并成一个，值班的人就分不出该找算法还是该找交易。

**Q：限流合并工单，会不会漏掉真实的大面积限流事故？**

A：不会漏，只是不重复开单。工单里带 `(tenant, customer)`，另有 `shoppilot_rate_limited_total` 计数器按维度打点，Grafana 看的是计数而不是工单条数。工单是"有人需要被跟进"的凭证，不是监控指标。

**Q：用户喊转人工，依赖的 embedding 服务挂了怎么办？**

A：字面显式表达在 T0 定案，不碰 embedding 也不碰模型，这是事故后补的最低可用线（ADR 0017）；换说法的求助（"叫你们经理过来"）仍走 T1/T2，embedding 超时就 fail-closed 进模型定案，模型也没了才落到 LLM_* 那几种 reason。三层各自兜一段，不承诺任何说法都不依赖服务，这句话写进 README 已知限制。


## Ticket 15 — debug console

**Q：为什么不直接上 React + Vite？**

A：这个页面的定位是"克隆仓库的人不起 npm 也能看到系统怎么跑"。多一条构建链就多一类起不来的理由，而它不承担任何产品职责。零构建不等于零结构——SSE 解析、事件渲染、代理调用各自一个函数。

**Q：`X-Ops-Token` 放在页面输入框里，跟内部凭证有什么区别？**

A：作用域不同。它只授权"演示环境的故障注入与复位"，默认值 `dev-ops-token` 是公开的开发凭证；`X-Internal-Token` 授权"以任意租户身份读写业务库"，永远只在网关进程里。生产把 `shoppilot.ops.enabled=false`，运维端点整条 503，页面只剩对话与时间线。

**Q：页面怎么保证时间线和后端状态机一致？**

A：它不保证——它只转发。每一帧都是 `SseEventSink` 写出来的原样内容，页面不做二次推断，所以后端加一个事件（比如 `duplicate_submit`）前端不改一行也能显示。这是刻意的：调试台一旦开始自己"编"状态，就失去作为证据的资格。


## Ticket 16 — tool calling eval

**Q：任务书说工具调用准确率 ≥95%，你这里最高 88.9%？**

A：95% 是 dev 模式（qwen-plus）的验收线，本轮 local 用 3B 小模型跑，作用是自证链路与评分口径。分意图报就是为了让差距可见：POLICY_* 四个意图 100%，失败集中在 ACTION_* 的多参数抽取，指向模型能力而非编排契约。

**Q：ACTION_ADDRESS 66.7%，还有 2 条凭空编订单号，怎么兜？**

A：改地址是唯一"写操作 + 两个必填槽"的意图，小模型缺槽时倾向填空而不是问。防线是三层叠加：`ToolDispatcher` 订单号格式校验当场拦（这 2 条正是被拦下才计 fabricated 而不是蒙混过关）、缺槽走 `SLOT_ASK` 追问、真正落库前还有 ticket 12 的订单状态前置校验 + 幂等 token。

**Q：180 条能说明什么？**

A：每意图 18 条，分辨率 1/18 ≈ 5.6 个百分点，够看出 POLICY(100%) 与 ACTION(66-89%) 的结构性差距，不够区分 95% 与 97%。所以报告按区间读，并把逐条明细留在 CSV 里可复查，不拿点值当结论。

**Q：93.3% 离 95% 只差两个点，为什么不再调一调？**

A：剩下的 miss 有明确归因：ACTION_ORDER 那 4 条是"到哪了"该查订单还是查物流的标注边界，收掉它要合并工具或改判据，两者都是在动口径；ESCALATE/UNKNOWN 那 5 条是转人工字面词表太窄加模型不肯听"别调工具"，扩词表要连着否定词窗口一起改。能靠 Prompt 收的（可选参数、已给信息不重复索要、不虚报已提交）已经收完，实测 ADDRESS 与 REFUND 都到了 94.4%。

**Q：18 条一批，94.4% 和 95% 有区别吗？**

A：没有统计上的区别（1/18 = 5.6 个百分点，94.4% 就是 17/18 对 18/18 的差别）。所以这格数字要按区间读，判据写 ≥95% 是分意图红线，真正过不了线的是 72.2% 那一行——它才是需要解释的。

**Q：为什么不干脆用 `--force` 越过预算，省得补跑？**

A：熔断是 ADR 0012 花血泪教训换来的防线，`--force` 是给人看错预算时的手动出口，不该是流程。缺额度的正确解法是补跑受影响的意图，同时把这一轮的真实消耗与不完整性一起写进报告。

**Q：24 条的冒烟凭什么抓得到 180 条全量抓不到的东西？**

A：靠形态不靠样本量。冒烟跑的是不带幂等 token 的对话式入口 + 本地 3B + 用例间状态传递，全量那轮三样都被换掉了（显式 token、qwen-plus、按意图分组）。同一套判据在两种形态下看的是不同的失效面。

**Q：既然 REPLAY 会让答案看起来"成功"，评分为什么没把它判成错？**

A：因为 `tool_ok`/`args_ok` 量的是模型发出的调用与参数，那部分确实是对的；错的是执行语义。这一格后来由 `tool_status` 列暴露出来——也是这次把 `answer_excerpt` 加进明细的价值：不看模型原话，根本发现不了它在复述上一单的地址。

**Q：花四万六千 token 去复核"本来就说模型无关"的四条防线，值吗？**

A：值，因为判据写的是 dev，而读者不会替你区分"有理由不测"和"找借口没测"。花掉的一轮换来的是 README 那格不再需要读者相信一段解释。

**Q：怎么保证下次没人再印出一条切不了模式的"dev 复核"提示？**

A：脚本自己回读 `/ops/circuit` 的 `llmMode`，不是 dev 就直接拒绝开跑（`拒绝在假 dev 下复核`），并且跑完无条件放回 local——把"模式对不对"从人读提示语变成机器查活体。

**Q：README 里现在同时留着 93.3% 和 95.6%，是不是留了两套真值？**

A：是，而且是有意的。旧那套是当时口径下的真值、也是已经公开引用过的那个数，抹掉它读者就没法核对这轮改动到底动了哪几条；新那套是判据修订后对同一批明细的重算。8 个 id 钉在正文里，改动范围是可审计的，这比"只留一个好看的数"更难被追问倒。

**Q：放开的资格为什么必须是「对偶矛盾」，而不是"这条看起来也该算对"？**

A：后者是品味，一旦允许就没有边界（`ACT-ORD-13` 那条双诉求看起来也有几分道理，而三条真错就没有对偶可指）。前者可机器化：同租户、同买家、同场景、两侧都是进度问法（`到哪`/`发了没`/`签收` 这类在订单详情与物流轨迹之间本就等价的说法），而订单桶认 `queryOrderDetail`、物流桶只认 `queryLogistics`。全表含进度问法的 ACTION_ORDER 样本恰 5 条，指得出对偶的正是放开的 4 条，第 5 条 `ACT-ORD-14` 的 gold 本来就是 `queryLogistics`、指不出对偶所以不放开；注意订单号相同不是判据（4 组里只有 1 组两侧同单号）。差异集合再由 `--rescore-expected-diff` 锁死，多放开一条重算命令就非零退出。

**Q：填对参数那一格为什么改报条数、不给一个比率了？**

A：因为一个诚实的比率给不出来，就不硬凑。三分法是 57 条比对过且全对、3 条放开后合格工具已打出但明细当年没存它的实发参数（要重跑才判得了）、3 条工具仍未命中天然不可比对。把它们折算成 `57/60 = 95.0%` 是编一个不存在的读数，而本项目全部信用都在"数字怎么量的"这一句上。


## Ticket 17 — threshold calibration

**Q：那你这语义缓存不是白做的？80% 拦截率是虚的？**

A：拦截率是真的，归因不是。标定实验的价值就在这：它把"语义缓存兜口语化改写"这句任务书原文证伪了，并给出替代结论（L1 + 穿透合并兜热点，L2 只兜写得极近的同意图重复）。

**Q：为什么不换个 embedding 模型或者加 rerank 把召回救回来？**

A：换模型改变的是余弦分布，不改变"同意图桶内存在反义"这个结构问题；0.9645-0.9802 这四对换成任何通用中文模型都可能还在。要提召回就得同时提误命中，0.85 处 precision 0.231 那一行就是证据。

**Q：词法守卫会不会把正常改写也拦掉？**

A：会，NEGATED 与 AFFIRMING 永不互用是有意的保守。A-not-A 判 NEUTRAL 不拦、句末语气词不拦，剩下的误杀在当前工作点不可测量（召回本来就是 0），且每次拒绝都打点，不是静默失效。


## Ticket 18 — load test dual curves

**Q：1200 QPS 是刷缓存刷出来的吧？**

A：口径写在每条 CSV 的 `qps_scope` 和 README：衡量网关编排层，不含模型推理。800 并发的 60456 个请求里仍有 45995 次穿透到 MockLLM（固定 500ms 时延），说明编排层在 26% 穿透率下没先饱和；命中路径本身也要过鉴权、限流、意图三级级联、Redis/Qdrant 读，不是空计数。

**Q：800 之后 QPS 反而掉，拐点是不是找错了？**

A：是排队而非崩溃：p99 从 1800 涨到 2200ms、p50 不动，用户数继续加但吞吐被 Little's law 封顶；同时本机可用内存到 0.0GB，发压端与网关抢同一台机器。所以对外报实测峰值 1013 QPS@800 并明写"任务书判据 ≥1200 未达成、发压机同机"，不报 1200。

**Q：语义缓存一条没命中，为什么不直接删掉这层？**

A：保留它的理由正是这条数据。ticket 17 已经证明"语义缓存兜口语化改写"在 0.95 工作点、bge-m3、36 个去重问法这套条件下不成立；删掉层就等于删掉证伪证据。当前它对拦截率贡献 0，对写回资格与极性守卫的价值是可验证的防线，两件事分开报。

**Q：向量服务一挂，你这两级缓存不就白做了？**

A：这正是要量出来的东西，不是要藏起来的东西。`perf,no-ollama` 那组冷缓存实测 136 / 265 / 482 QPS（对照组同条件 296 / 580 / 976），纯缓存拦截率归 0，总拦截靠穿透合并撑在 21.8%-37.4%，错误率全程 0。L1 写回对向量的依赖我们已经拆掉（ADR 0018），但端到端仍然停止积累，因为挡在前面的是 ADR 0006 的"检索未降级"资格：稠密召回 0 命中时新答案一律不入库。这道门是有意保留的——把只有一路召回支撑的答案固化 6 小时、服务恢复后继续复用，比缓存冷掉更糟。生产侧对策是给 embedding 做副本与熔断，运维盯 `shoppilot_cache_embed_unavailable_total` 的增速，而不是等拦截率跌下来才发现故障已经持续了一阵。已有存量不受影响：另一轮 `l1_delta` 608 / 1123 / 2035、命中 p50 8ms，停用的是"积累"不是"复用"。

**Q：判据没达成，你怎么知道不是网关自己慢？**

A：把首字拆开量：单连接串行时服务端 TTFT 均值 725ms，其中 300ms 是 perf Mock 的固定首字下限、311ms 是这台笔记本跑一条 bge-m3 向量化的实价（外部探针测的，服务端那一步没埋点），检索合计 10ms，剩下 104ms 才是编排。而且未命中那条曲线在 50-200 并发间是水平的（1031→1049ms），排队假设直接被自己的数据否掉。判据仍是未达成，但差距有归属：要么把向量化挪出请求关键路径，要么换云端口径复测，而不是把 Mock 调快。

**Q：592ms 那个数当初为什么不能信？**

A：因为它量的不是首字而是第一个 SSE 分片（服务端在检索与模型之前就推 status/meta 帧），而且样本八成是缓存命中，等于拿"500 并发下命中路径的首帧"去对"未命中端到端首字"的判据。修法是首字只认 `event: token`、并按服务端自己报的 `cacheLayer`+`intent` 分桶，旧产物保留但降级标注为"首帧口径"。


## Ticket 19 — materials star

**Q：README 上的数字你自己当场能复现吗？**

A：每个数字旁边就是文件名，抽查任意一行能落到 `loadtest/results/` 或 `eval/results/` 的具体 CSV/JSON，同批 `-meta.json` 记了 git commit、容器内存、空闲内存。复现不到同一量级我会先说不达标，而不是先解释。

**Q：任务书写 80% 拦截率，你为什么写 74%？**

A：口径冲突不是没做完。74% 是 L1 主导曲线的总拦截率，78% 是 80% 热点塑形口径，两者分母都是准入数；要写 80% 就得把拦截率记到语义缓存头上，而 ticket 17 实测那一层在 0.95 工作点召回为 0。

**Q：已知限制里那条进程静默消失，下一步怎么查？**

A：先分诊"是 OS 杀的还是 JVM 自己崩的"：没有 `hs_err_pid*.log`、没有 WER 事件、stderr 为空，这三条同时指向外部终止。下一步是 `-XX:+HeapDumpOnOutOfMemoryError` + WER 本地 dump + `jcmd` 定时采样，并把发压端挪到另一台机器排除同机争抢（本机 16GB、阶梯谷底 free 0.0GB）。在换机复现之前不动业务代码。

**Q：十分钟那条是你自己跑的，凭什么算过？**

A：判据的对象是"提交物自不自足"，不是"某个人的手感"：HEAD 克隆出来的目录没有 `target/`、没有 `.env`、数据卷是空的，构建、seed、入库全部重跑，241 s 就是这么量出来的。它确实不覆盖"另一台机器"和"另一个人"，这两条缺口连同落点日志一起写在 README 与 ADR 0020 的 Consequences 里；对外说法是"同机干净检出达成、异机未验"，不是"任何人都能在十分钟内跑起来"。

**Q：为什么不等一个真人跑一次？**

A：交付窗口（9/13，无余量）内不会有这个真人，而这条判据真正要防的东西此前每一项都是机器先撞出来的：容器名全局唯一挡住第二个检出、fat jar 文件锁、`.env` 在仓库外、入库依赖、内存挤死构建 JVM。人来了也只是重复机器已经能判的那一半，剩下那一半（换机）换个人也证不了。


## Ticket 20 — action order attribution

**Q：改标注是不是为了让数字过线？**

A：八个 id、四条问句原话都钉在 README 指标表那一格里，读者可以自己对照 `eval/cases-part2-action.jsonl` 复核；判据原文是分意图各 >= 95%，新判据下仍有 5 行未达线，承诺项结论没变。另外差异集合由 `--rescore-expected-diff` 锁死成恰好那 4 条，多放开一条重算命令就非零退出。

**Q：95.6% 越过了 95%，为什么还写未达成？**

A：因为承诺项的量纲是分意图，不是聚合；聚合那格并列两套读数（93.3% 与 95.6%）正是为了防止它被单独引用成"过了"。

**Q：重标为什么不重跑？**

A：重标只改判据、不改样本采集，`选对工具` 依赖的实际调用链当年已落进明细，重算与实测共用同一个 `judge()`，同源只差采样；参数与 `NOT_FOUND` 离线补不出，前者记成不可比对、后者下沉成 JVM 断言，都不靠嘴说。花钱那条约一键预检命令留在本票「备用的花钱路线」。

**Q：这套改动怎么保证不是又一次"把测试改成能过"？**

A：三类反证都在机器上：把四处量具修复分别改回旧语义，`--selfcheck` 必须红；把坏标注（空合格集、非法工具名、重复元素、越权样本缺标记、标记用跨租户共享词、标记用店名子串/整串/加长串、标记用裸街道名）注入仓库外临时副本，`build_eval_set.py` 必须 `FAIL`；阈值常量与 `EVAL DONE` 由断言盯住未在 diff 中出现。跑一遍 `python scripts/verify_eval_judge.py` 就是这 40 条，一条命令全复现。

**Q：门禁跑不完的时候，你怎么确定那不是防线失效？**

A：看现场而不是看等待时长——第三轮那次 `stack` 步 20 分钟不动，被冻住的 pwsh 是活的、19 线程、CPU 停在 5.546875 不再增长、**没有任何子进程**、`8082`/`8091` 始终不通，而它的日志最后四行是被拉起的第三方进程自己打的 `INFO`；这五条合起来指向"继承句柄的探活挂死"，不指向任何一条业务防线，因为业务防线连开口的机会都没有。同一套区分用在 `polarity` 的 `exit 3` 上：前置不成立时脚本自己拒绝下结论，栈不动单跑一次就绿，那种红也不记成防线失效，见 README「假红」一节。
