# 渠道出站的第一生产者是坐席结单，投递失败落回执工单

Context: ADR 0054 定的三个 topic 族里，`channel.outbound` 至今**没有生产端也没有消费端**——全仓只有契约（`ChannelOutboundEvent` + topic 常量）。round23 的裁定 C 是「为没有消费者的 topic 造代码是本仓明禁的」，所以它被正确地留着。但「为什么一直没有消费者」此前没人回答。

把现状读一遍就清楚了：`web`/`app`/`miniapp` 三个渠道的答案是**同步 HTTP 返回**的（`ChannelController` 把 `answer` 放进响应体），`email` 按 ADR 0035 本来就没有实时回包通道、交付物是回执工单（`EmailReceiptWriter` → `reason=EMAIL_REPLY`）。**今天每个渠道都已经有交付路径**，所以出站没有生产者不是缺陷，是**还没有一个真的异步答复**。

而 program 主线第 3 节写的最后一格正是它：买家问 → 转人工落单 → 坐席处理若干分钟到若干小时 → **结果回流给买家**。这条链在今天是断的：`resolve` 之后除了工单表多一行 `RESOLVED`，买家侧什么都收不到。

Decision:

1. **第一生产者是工单结单**。`shoppilot-ticket` 在 `resolve` 时发 `channel.outbound`，事件带 `ticketId` / `channel` / `target` / `body`（处理结论）。
2. **工单要有渠道与目标两格**：`tickets` 加 `channel` 与 `contact` 列（Flyway `V2`）。今天它们只以 `transcript` 里一句 `【回执渠道】{contact}` 的字符串存在——拿字符串做投递目标，等于让一次文本改动决定邮件发不发。
3. **消费端在网关进程内**（ADR 0053 已经把「渠道出站适配」划给网关，这里只是把它落实）：读 `channel.outbound`，按 channel 投递。**不为它起第五个 JVM**——理由同 ADR 0058（本机全栈已约 6.6 GB，而一个只做 HTTP 的消费者不值 500 MB）。
4. **webhook 入站新增可选 `callbackUrl`**：没有它就不发事件，**照登不假装**。渠道适配器的入站契约今天没有「回我哪儿」这一格。
5. **投递语义**：至少一次（0054）。消费端按 `eventId` 去重，重投不产生第二次投递。
6. **投递失败：重试 3 次后落一张 `CHANNEL_RECEIPT` 工单**。理由：退款结论这种内容丢了就再也回不去，而落单是本仓已有的、买家与坐席都看得到的地方。**「丢一条出站」与「一张没人看的死信」之间，我们选后者。**
7. **email 出站本轮只落投递口，不真发 SMTP**：本仓没有 SMTP 依赖，收件地址是 seed 出来的假数据。email 的交付仍然是回执工单（ADR 0035 不动）。**照登，不假装发过。**

Considered Options:

- **第五个 `channel-outbound` 服务**：否决。理由与 ADR 0058 相同（每多一个 JVM 约 500 MB，本机全栈已约 6.6 GB、可用约 1.9 GB），且这个消费者干的事几乎全是发 HTTP，拆分换不到任何独立性。
- **让网关轮询工单服务的已结单列表**：否决。那是第二套投递机制；事件骨干已经在了，再加一套轮询等于给自己造两个真相。
- **投递失败进死信 topic**：否决。三条 topic 族是 ADR 0054 的明账，而「死信」要一个新 topic + 一个消费者 + 一个重投入口。落回执工单用现成的表、现成的队列、买家看得见。
- **不做出站，登记「暂无异步答复」**：否决。这条断链正是 program 主线写下的最后一格，登记它的代价是主线永远停在倒数第二步。

Consequences:

- **工单多两列，`TicketView` 多两个字段**（追加在尾部，不改动既有反序列化契约，与 ADR 0055 当初的加法同手法）。
- **回流的可见性是「买家侧可查」，不是「买家一定收到」**：web 渠道靠买家端页面自读（本 program 下一块），webhook 靠一次真实 POST，email 靠回执工单。三者都验得了，但它们不是同一个保证。
- **投递口径可对账**：发出去几条、消费几条、失败几条，都要有计数（G9 那类门禁），否则「回流了没有」只能靠人点。
- 本 ADR 只定「谁生产、投到哪、失败怎么办」；**具体每一步的实现与验收**在 `round26-spec-result-delivery.md`。
