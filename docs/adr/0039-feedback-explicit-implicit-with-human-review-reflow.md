# 满意度反馈走"显式点踩 + 隐式行为信号"，回流只到人工复核队列，不自动再训练

Context: 对标架构含满意度检测与反馈闭环（bad case 回流改进）。ShopPilot 无任何满意度采集。闭环有两个必须诚实面对的边界：一是"自动回流再训练"在本项目形态下不可达（无训练管线、无数据规模），二是隐式信号的每个定义都必须可机器判定，否则闭环叙事在面试里一追问就散。

Decision: 新增 `feedback` 包，双信号采集，落 biz-mock `feedback` 表：

- **显式信号**：SSE 新增 `feedback` 事件（赞/踩 + 可选原因），回复完成后前端可发；REST 同步端点同形。会话结束未评 = 无信号，不猜测。
- **隐式信号**（全部取自状态机已有的可观测转移，零新增判定逻辑）：
  1. 同会话内重问同意图（T0/T1 判定结果一致且间隔 < 会话窗口）→ `implied_dissatisfied`；
  2. 走到 FALLBACK → `negative`（降级即不满，与用户是否再点踩无关，口径分开记）；
  3. `duplicate_submit` 幂等重放 → `implied_retry`。
- **闭环最小形态**：踩 + 负信号自动关联当次会话的工单（若有）与检索引用块（ruleId），进入 ingest 待复核队列；**人工复核后才进知识库修订，不做自动改写**。自动回流再训练列为外部前置（无训练管线），与"真实投产"同列非目标。
- 指标：`shoppilot_feedback_explicit_total{verdict}`、`shoppilot_feedback_implied_total{kind}`、周聚合负率进 README 口径表（标注单机演示口径，不外推生产）。

Considered Options:

- 用 LLM 给每条回答自评质量（模型当裁判在线打分）：否决。在线自评每次回答多一次调用，且"裁判与选手同源"的分数没有证据价值；离线评测已有 357 条用例的 judge()，那才是量具。
- 踩评自动触发知识库改写（LLM 起草新条款）：否决。合成语料的修订必须过人工复核，自动改写等于让上次犯错的链路自己修自己。
- 满意度进缓存写回资格（踩过的答案作废缓存）：登记不做。语义正确但会让写回资格从 7 道变 8 道，且显式评分覆盖率在演示口径下太低，资格判定实际不触发；触发条件=显式评分覆盖率达到可观测水平。
- 隐式信号单独存 Redis：否决。反馈是审计资产不是热数据，与工单同库同生命周期。

Consequences:

- 状态机零改动：三个隐式信号全是既有转移上的计数埋点；`ChatController` 加一个回传端点。
- 验收脚本一条三断言：点踩 → feedback 表落行 → 关联工单与 ruleId 可查 → 待复核队列可见。
- 评测集 `cases-part7-style-feedback.jsonl` 中 6 条反馈用例：显式赞/踩落库、重问判 implied、降级判 negative、幂等重放不重复计数。
- 面试叙事对应关系直接成立："bad case 去哪了"→ 踩评关联工单与检索块 → 人工复核队列 →（触发条件下）知识库修订 → kb_epoch 递增使旧缓存全部失效（ADR 0003 既有机制，闭环在这里自然咬合）。
