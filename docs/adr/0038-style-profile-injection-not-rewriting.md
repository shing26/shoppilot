# 风格引擎是 REPLY 后置的"基座+注入段"提示词拼装，不做独立生成模型

Context: 对标架构含风格引擎（按渠道/情绪切回答风格）。ShopPilot 的回答风格目前只有降级话术一层（`FallbackReason.userMessage()`），正常回答风格完全由基座提示词决定。风格若做重（独立改写模型、模板全文生成）会把"回答内容正确性"与"回答形态"耦进两套系统，评测判据也被迫双轨。

Decision: 新增 `style` 包，`StyleService` 在 REPLY 阶段做提示词拼装，不做回答后处理改写：

- 输入三元组 `channel × emotion × intent` → 风格档位（`FORMAL / FRIENDLY / CONCISE`），映射关系为静态配置表（`style/profiles.yml`）；
- 档位映射为一段**注入提示词**（语气约束、称呼习惯、长度倾向），拼在 0037 的版本化基座之后；回答正文仍由同一次 LLM 调用产出，不二次调用；
- 约束上限：注入段 ≤ 200 token，超出即配置错误（启动校验拒绝，风格不该贵过回答）；
- 降级话术随档位联动：`FallbackReason.userMessage()` 增加档位参数，FRIENDLY 档在话术前加安抚短句——改的是话术选择，不是话术生成；
- SSE `meta` 事件携带 `style` 档位，与 `promptVersion` 共同构成提示词形态归因。

不改变正确性语义：风格注入只允许约束形态，不允许携带业务事实（"改地址免费"这类内容只能来自检索或工具结果）；注入段进评测断言——出现业务事实型语句即判红。

Considered Options:

- 回答后处理改写（生成后再润色一遍）：否决。每次回答翻倍的模型调用直接击穿 TTFT 预算，且二次改写是幻觉新增点。
- 独立小模型做风格分类替代静态映射表：否决。三元组到档位的映射是产品决策不是推理问题，静态表可审计、0 token、可机器复跑，过筛。
- 风格只做渠道维度（App 简洁/邮件正式）：否决。情绪维度才是风格的本职（ANGRY 用户收到活泼语气是事故）；映射表天然支持三元组，砍维度不省任何东西。
- 置信度不足时随机档位：否决。UNCERTAIN 情绪一律回落 `FORMAL`——风格宁可不讨好，不可不确定。

Consequences:

- 评测集新增 `cases-part7-style-feedback.jsonl` 中 6 条风格用例：3 渠道 × 2 情绪矩阵断言档位正确、注入段无业务事实。
- profiles.yml 为配置资产，改档位映射不改代码；映射表进 README 附表，面试可直接指着讲"风格是决策不是生成"。
- 指标新增 `shoppilot_style_applied_total{style}`；风格与 TTFT 的联合曲线照登（注入段加大提示词，TTFT 理论上有微小上浮，实测数字说话）。
