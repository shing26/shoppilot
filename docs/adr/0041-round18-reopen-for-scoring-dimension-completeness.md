# round18 重开：补齐评分维度完备性（B8 数据层 + B9 测试体系），B5 挂触发条件

Context: 独立评估按《项目开发判断标准-三维度评分体系》（`D:\WorkBuddyData\项目开发判断标准-三维度评分体系-20260920.md`，sha256[:8] = `431790b9`）对 ShopPilot 判后端子表 12 维，得分率 97.53%、判定合格，但 **11 维已是 3 分，唯一非 3 分是 B8 数据层设计（2 分）**——全仓零 `.sql` 文件、零迁移工具，schema 的唯一来源是 `shoppilot-biz-mock/src/main/resources/application.yml` 的 `ddl-auto: create` 打在 H2 内存库上，于是「迁移可回滚」一项结构性不适用；B9 测试体系已是 3 分（42 文件 / 216 个 `@Test` 声明 / **267 条实际执行**，CI `verify` + 三步 0 token 门禁齐备），但没有覆盖率数字，防退化靠用例数量而非覆盖率棘轮。这两条都不是事实性错误、不是崩溃或回归，因此 **ADR 0031 的「面试同一缺口被问两次」触发条件未命中，`PROJECT_PLAN.md:19` 的 v1.0.0 冻结线也放不过**。本轮重开不是该条件的触发，而是项目所有者在知情该政策的前提下做出的显式覆盖决策：以评分体系为对标补齐维度完备性。**重开必须诚实记录为政策覆盖，而不是伪装成面试反馈触发**——与 ADR 0033 同形。

Decision: round18 范围锁定 **B8 全两半 + B9**，B5 可观测性不执行、只挂触发条件。

| 票 | 模块 | 要点 | 依赖 |
|---|---|---|---|
| 42 | B8-① 版本化迁移体系 | 引入 Flyway，V1 基线由 Hibernate 导出后人工固化；`ddl-auto` 全档切 `validate` | 无 |
| 43 | B8-② 慢查询优化前后对比 | 索引落成 V2 迁移；证据以 EXPLAIN 前后对照为主、放大种子量后的耗时为辅 | 42 |
| 44 | B9 覆盖率棘轮 | JaCoCo 报告绑 `verify`，0 token 脚本按模块分别设闸 | 无 |

具体口径：

- **迁移形态**：`V1__baseline.sql` 是 9 张表的完整 DDL，由 `jakarta.persistence.schema-generation.scripts.*` 从 Hibernate 导出一次、人工审阅后固化，**不手猜方言**；`V2` 是票 43 新增的两个索引。V2 的存在让「版本化迁移体系」从一次性基线变成真的增量演进，而不是摆设。
- **`ddl-auto: validate` 全档统一**（含测试路径）：3 条 `@SpringBootTest` 继承主 `application.yml`，因此实体与 DDL 一旦漂移会在 267 条用例里当场报错。**这是迁移体系自己的防退化守卫**，也是拒绝「validate 只在主档开」的理由——只开主档等于让一致性在 CI 里无人看管。
- **回滚口径按社区版实况写**：Flyway 社区版没有 `undo`（Teams 才有）。回滚 = `flyway clean` 重放（需 `clean-disabled=false`）+ `db/rollback/` 下的手工 down 脚本（约定载体，不被自动执行）。**不假装社区版有 undo。**
- **索引的真相源是迁移文件**：`validate` 不校验索引与唯一约束，实体上的 `@Index` 注解在换代后已降级为文档。既有 3 处注解保留不动（它们同时是评分报告 B8「索引有依据 3 处」的证据）；票 43 新增的 2 处两处都写，但防退化不靠注解一致，靠一条断言**真实数据库里存在这 2 个索引且查询计划用上它们**的 JVM 用例。
- **覆盖率棘轮数值先测后定**：按模块分别设闸（gateway 249 条与 biz-mock 15 条的量级差太大，聚合门槛会让量小的那个模块的回归被掩盖，而本轮改的正是 biz-mock），LINE 设闸、BRANCH 只报不设闸，门槛取首次实测值向下取整留余量，**不设高门槛、不猜数字**。

非目标（本轮不执行）：B5 可观测性（清单列为「可选补」——已 3 分、不构成风险，但要推翻 ADR 0013/0015/0024 三个已锁定结论才成立；触发条件沿用 ADR 0030 第 5 条：本仓出现可机器寻址的 Prometheus/Alertmanager 形态时该否决自动失效）；清单第④项「Agent 雏形能力是否单独出 A 表」——它是定位决策不是技术短板，登记不执行。

Considered Options:

- **不重开，只按 ADR 0030 写触发式挂账**：否决。B8 的 `ddl-auto: create` 是生成姿态上的硬伤，与评分无关也该改；只登记等于把一个已知的生产缺陷留在代码里。
- **只修 `ddl-auto` 硬伤、不做迁移体系**：否决。只把 `create` 换成 `validate` 而不引入迁移，schema 就没有任何产生源，起栈必失败；而若换回 `create`，硬伤照旧。二者是一件事。
- **三项全做（含 B5 看板）**：否决。为一条「可选补」推翻三个 ADR，治理资本花得不成比例；且 ADR 0030 已经给过 B5 一条明确的触发条件，尊重它比提前兑现它更省。
- **只补 V1 基线、不做 V2**：否决。那样迁移体系从未跑过一次真实增量，「可回滚」无法被验证；而票 43 本来就要加索引，落成 V2 是零额外成本。
- **手写 V1 的 DDL 而不从 Hibernate 导出**：否决。9 张表全是显式 `@Column(name=...)`，导出结果确定，人工固化的风险远低于凭记忆手写方言。
- **用 `jacoco:check` 直接绑 `verify`**：否决。失败信息可读性差、不产出可引用的数字摘要；本仓已有的形状是「报告进构建 + 0 token 脚本读产物判定」，沿用同形。
- **覆盖率棘轮设一个像样的目标值（如 70%）**：否决。设成当前值就已经拿到「防退化守卫」要件，高门槛只会制造与功能无关的补测压力，且会诱导未来为过闸而写无断言用例。

Consequences:

- 冻结线对 round18 之后的轮次继续有效；本轮结束后回到 ADR 0031 机制，**不自动续期**。每张票独立可交付，中途冻结任意时刻项目仍自洽。
- `ddl-auto` 换代改变起栈行为：所有依赖「schema 由 Hibernate 自动生成」的路径（含 3 条 `@SpringBootTest`、`SeedRunner` 的 `JdbcTemplate` 计数与删除）必须重验，这是本轮的主要回归风险面。
- 票 44 把「覆盖率」从 round15 spec 的 Out of Scope 里移出，是**范围边界的更正而不是判据改动**：round15 排除覆盖率的原始理由是子集门禁不依赖外部服务，而 JaCoCo 在进程内运行，那条理由对覆盖率本来就不成立。同步要在 round18 spec 里记录这次覆盖及理由。
- `CONTEXT.md` 新增「模式迁移」术语：本仓现在有两套互不相干的版本轴——管政策知识的「知识库纪元」与管表结构的「模式迁移」，必须消歧，否则下一个读者会把二者混为一谈。同时明写**迁移不改变数据的持久性作用域**：库仍是内存库、每次起栈 reseed，「可查工单」的作用域不变。
- 评分报告（`D:\WorkBuddyData\项目评估结果\`）与跨项目台账（`项目提升计划-20260921.md` 第 3 步 B-4/B-3 行）在本轮执行后会变陈，需要回写；那两份产物不在本仓纪律约束范围内，本 ADR 只登记这个欠账。
