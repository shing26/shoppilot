# 事件骨干用 Redis Streams，不引 Kafka/RabbitMQ

Context: 0053 拆出的四个服务之间有三类天然的事件流：待分流工单（对话侧产生"该转人工"）、渠道出站（回复要送回 webhook/email）、审计（谁审了退款、谁领了工单）。这三类都不是"调用方等结果"的同步语义，而是"发生即记录、有人消费"。本机 16 GB 内存已被另外四套项目压到只剩约 0.5 GB 可用，全栈四服务已占约 4 GB——再引入一个消息中间件就是与验证能力直接冲突。

Decision: **同步查询与命令走 REST（跨域只走 API），事件走 Redis Streams**。三个 topic 族：`ticket.routing`（待分流）、`channel.outbound`（渠道出站）、`audit`（审计）。消费组 ACK + pending 列表作为对账面。事件 schema 属契约，放 `shoppilot-tool-api`（0053 定义的契约库）。投递语义是**至少一次**，消费端必须幂等。

Considered Options:

- 全同步 REST（分流与出站靠调用或轮询）：否决。坐席工作台要轮询刷，渠道出站要调用方重试；同步链把四个服务耦成串行，一个慢全链慢。
- Kafka：否决。内存 + 运维面 + 主题治理，收益（真正的高吞吐削峰、消息重放生态）在演示流量下吃不到。
- RabbitMQ：否决。比 Kafka 轻，但仍要新增容器与账号体系；且 Streams 的 pending 列表恰好给本仓提供了现成的"可对账"面——这是选它的实际理由，不是因为它功能更强。

Consequences:

- 事件成为**可对账的第三类证据**（既有：指标、离线产物）。收口审计可新增一类门禁：事件发布数 / 消费数 / pending 是否归零。
- 至少一次投递 → 每个消费端都要幂等（工单服务与渠道出站消费器各有一份幂等键）。
- Redis 是既有依赖，零新增中间件；代价是事件与缓存共实例，Streams 积压会影响缓存延迟——需要给 `ticket.routing` 定容量上限与丢弃告警。
