# round36 开轮依据：产品面履约（两个产品入口从「验收夹具」到可用界面）

Date: 2026-10-20　Status: **Accepted**（2026-10-20 所有者指令「A+B+C 一起走」）
Owner basis: 2026-10-20 所有者观察「前端太极客化」→ 要求盘点三个前端 → 裁定把 A（坐席端信息完整性）、
B（买家端产品化）、C（视觉与工程收口）**三段一起开轮**。
Tickets: 实现票 [151](../../.scratch/shoppilot-mvp/issues/151-product-surface-ux-gaps.md)（单票三段；票面即本轮 spec）。

Context:

`ADR 0057` 把前端定成两个产品入口加一个运维页：`/buyer/`（买家中心）与 `/workspace/`（坐席工作台）是产品面，
`/`（调试台）保留为运维页且明确是过渡态。此后三张票（73 / 93 / 110）都按**行为门禁**收口：
买家端量跨买家隔离，工作台量领取/结单确认，调试台量静态放行与内部令牌不泄漏。**没有任何一条判据量过
「这一页是否让人能完成工作」**，于是产品面停在了「通过断言」的形态：

- **买家端**：`answer` 是单值 ref，每次提问先清空（`frontend-buyer/src/App.vue:29-30`、`:90-93`）——
  页面永远只有最后一轮，没有对话流；登录第一格要求买家输入内部租户号（`:155`）。
- **坐席端**：状态/来源/队列三个内部枚举裸印（`frontend-workspace/src/App.vue:274`、`:278`、`:255`）；
  页头副标题直接写「round23 票 72 / 票 83 / ADR 0056」（`:235`）。
- **三个入口之间零导航**：调试台全文没有一个 `href`。

盘点时核实出三条比观感更硬的事实（建票取证，逐条可查）：

1. **`TicketView` 没有 `transcript` 字段**（`shoppilot-tool-api/.../view/TicketView.java`，44 行，尾部是
   `channel`/`contact`），而 `frontend-workspace/src/types.ts:11` 声明了它——前端读的是一个永远 `undefined`
   的字段。`WorkItemService.java:171` 的注释也声称买家视角「少 transcript 一格」，与代码不符。
2. **那条隔离测试是真空断言**：`BuyerOwnTicketsTest.java:71-78` 断言买家响应 `!has("transcript")`，
   而 `toView` 与 `toBuyerView` 都不带该字段，所以它永远绿；两边真正的差异是 `contact`。
3. **结单意见永远是空串**：工作台 `resolveTicket(id, session, '')`（`App.vue:144`），而
   `WorkItemService.resolve` 把 `note` 同时写进审计说明与出站正文（`:254`、`:259`）。`ADR 0059` 承诺
   「结单结论送回原渠道」，实际送到买家手里的是「已处理完成」——**这是对既有承诺的偏离，按缺陷处理**。

冻结线：`v1.0.0` 已冻结，新功能须命中 `ADR 0030` 五条或 `ADR 0031` 面试反馈触发。本轮 B/C 段（对话流、
店铺入口、视觉系统）**未命中任何一条**；A1（空结单意见）属缺陷，A2-A4 属契约与可读性修正。
因此本轮归类为**所有者政策覆盖**（与 0066 / 0067 / 0069 同一机制），一条条写明依据，不伪装成事实性修正。

Decision:

**一、开轮：round36 = 产品面履约**，单票 **151**，三段按 A → B → C 顺序执行，**每段单独提交、单独验证**。
A 段可独立合并；C 段可与 A/B 分开合并。票面「范围与验收」即本轮最小 spec，不另立 spec 文件。

**二、A 段（坐席端信息完整性）：**

- **A1 结单意见**：确认框内加文本框（去空白后 ≥1 字），提交进 `note`；前端拦空，后端维持宽容口径
  （不新增 400 分支——结单的其他前置条件已由状态机与领取人校验承担）。依据 = ADR 0059 的「结论」语义。
- **A2 转人工上下文**：`TicketView` **尾部追加** `transcript`（沿用「追加在尾部 + 保留旧构造器」家法）；
  实跑确认该字段的内容是降级出口的 `detail`（失败/升级说明），不是完整对话记录——页面按
  「转人工上下文」展示，契约注释同步改准；
  `toView` 传入、`toBuyerView` 传 `null`；把真空断言改成真断言并做**变异对照**（让 `toBuyerView` 带上
  transcript → 该用例必须红）。工作台渲染，买家端不渲染。
- **A3 枚举可读化**：工作台补 `STATUS_LABEL` / `SOURCE_LABEL` / `QUEUE_LABEL`，未知值原样透出。
- **A4 去内部编号**：页头副标题换成产品话术；`round\d+` / `票 \d+` / `ADR \d+` 不出现在页面文本里。

**三、B 段（买家端产品化）：**

- **B1 对话流**：消息数组（user/assistant）+ SSE 增量写入最后一条；保留进行态、失败时保留已生成部分
  与工单号。会话 id 仍只在内存（刷新即新会话，照登，不引入持久化）。
- **B2 店铺入口**：**取 (a) 店铺码走 URL**（`/buyer/?store=T001`），登录后从
  `GET /api/v1/support/ops/tenants`（`{tenantId, name, rateLimitQps}`）取店名显示；UI 不再要求买家理解
  内部 id。**否决 (b) 新增公开只读店铺端点**：那会多一个未鉴权面，为一次产品化改动引入安全复核，收益不抵。
- **B3 加载态**：`loading` / `empty` / `error` 三态分开；读取中不得显示「你还没有需要人工处理的工单」。

**四、C 段（视觉与工程收口）：**

- **C1 共享层**：新建 `frontend-shared/`，以 `file:` 依赖接入两个工程（**否决根 npm workspaces**：
  后者要改两个 `npm ci` 的位置与 lockfile 结构，而本票的收益只是去重）。导出设计令牌、基础样式、
  `ApiResult` / `request` 与契约类型；base 路径由各工程注入。
- **C2 导航**：只在调试台加「买家端 / 坐席工作台」两个入口；**产品页不回链运维台**。入口放页脚 `.ctl` 组，
  **不塞 header**（49px 高度被抽屉 `inset` 钉死，且 `verify-console.mjs` 有 390px 页脚不溢出断言）。
- **C3 窄屏**：两个产品页在 390px 下不横向溢出；宽表格转卡片或表内横向滚动。

**五、红线：**

- 判据面零触碰：gold 180 / 阈值 / 分母 / `judge()` / 既有验收判据一字不动。
- 既有 ADR 原文一字不改；本轮结论只写在本 ADR 与票 151。
- 不引组件库（`ADR 0057` 已否决全套组件库）；不新增运行时 UI 依赖。
- 前端产物入库：`static/buyer/`、`static/workspace/` 改动后必须重建并提交；CI 第九步逐字节校验；
  `verify-console.mjs` 会重写 `docs/console.png`，视觉变化连同截图一起提交。
- 门禁语义不降：三个 Playwright 门禁可以改引导方式（例如自定义确认框替代 `window.confirm`、URL 带店铺码），
  但所量的东西（静态放行、内部令牌不泄漏、跨买家隔离、领取/结单确认）一条不少。

**六、不并入本轮**（登记，不在票面夹带）：

- 买家侧订单/商品上下文：仓里没有买家读端点，要做得先加 biz-mock 读面与隔离判据，属于新功能。
- 买家端会话持久化、多店铺切换、图片/富文本。
- 调试台重做或并入产品导航（它是运维页，极客化是职责；`ADR 0057` 已明确不要求两套能力对齐）。
- 概览/看板类页面（与 R5 长期指标存储同一触发线）。

Considered Options:

- **只做 A（坐席端缺陷）**：否决本轮采用。A 能让坐席把活干完，但买家端仍是「单轮表单」，产品面只修了一半；
  所有者已明确 A+B+C 一起走。
- **一次大提交做完三段**：否决。三段的风险面不同（后端契约 / 前端交互 / 构建结构），混在一起后
  一旦某个浏览器门禁红，定位不到是哪一段；分段提交也让 A 段可以先合入。
- **新增公开店铺端点**：否决（见 B2）。
- **根 npm workspaces**：否决（见 C1）。
- **给产品页塞一个「返回运维台」链接**：否决。买家不该看到运维面；导航是单向的。
- **把调试台改成产品首页**：否决。它与 35 条以上断言、故障注入、运维令牌绑定，改成产品页等于拆掉验证面。
- **用 `window.prompt` 收集结单意见**：否决。原生 prompt 不可样式化、不可测试非阻塞交互，且与 C 段的视觉
  目标相反；用轻量自建对话框，门禁改量「对话框出现 + 空意见被拦 + 填写后提交」。

Consequences:

- 票 151 转 `ready-for-agent` 并在同一 session 认领（`Claimed by`），frontier = {151}。
- **判据与夹具变动面**：
  - `TicketView` 增字段 → 契约库、`WorkItemService` 两个映射、`BuyerOwnTicketsTest`；
    `BuyerOwnTicketsTest` 的变异对照必须实测为真。
  - `verify-workspace.mjs`：确认框从 `window.confirm` 改为自建对话框，断言改为「对话框出现 / 空意见被拦 /
    填写后提交并落审计」；领取、释放、无页面异常三条原样。
  - `verify-buyer.mjs`：入口 URL 带 `?store=T001`；新增「加载态不冒充空态」与「窄屏不横向溢出」两格。
  - `verify-console.mjs`：新增「两个产品入口存在且 href 正确」一格；390px 页脚断言原样。
- **产物与证据**：两个 `static/` 目录重建入库；`docs/console.png` 随调试台改动重拍（若 C2 改了页脚）。
- **读数**：JVM 条数随 A2 的契约测试增长，收口时按实测换代（G6 常数与矩阵日志照旧只在重跑矩阵时换代）。
- **未达成照登**：三个浏览器门禁需要活体栈（本机按清场日裁定）；若本轮未实跑，必须逐条登记，
  不许把「typecheck + build 绿」写成「页面真的能用」。
