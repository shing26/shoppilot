# ADR 0091：内部试用就绪——以退款全链路为验收脊柱，分波硬化而不是一次清债

Status: Accepted（2026-11-28 所有者授权「剩下问题按推荐执行」）
Date: 2026-11-28
Deciders: 所有者
Round: 63（spec：`.scratch/shoppilot-mvp/round63-spec-trial-hardening.md`）

## Context

ShopPilot 已经具备可运行的买家端、坐席工作台、退款受理与人工审核、工单回流、
持久化档和 29 步活体验收。继续往下走时，仓库里仍有一批登记债：模型与验收稳定性、
数据一致性、架构服务化、长期指标和输入侧防护。把它们全部清完再交付，会得到一个
没有真实使用反馈的「大而全但未试用」系统；只挑最容易的做，又会继续堆演示面。

所有者 2026-11-28 的目标已经明确：**先把开放项做起来，完善项目各部分，再通过测试
体验持续迭代**。因此本轮需要先回答「什么算完成」，再排执行顺序，而不是继续用
「还能做什么」驱动开票。

约束：

- `v1.0.0` 冻结线仍然有效；本轮以所有者政策覆盖 ADR 0030 / 0031，但只覆盖本 ADR
  写明的范围，不自动续期；
- 一次只做一张票，每张票仍有独立契约、独立 Verifier 与所有者书面签收；
- 不改 gold、阈值、分母、`judge()` 或既有验收断言来换绿；
- R1（知识服务化）、R3（跨平台身份统一）、R8（输入侧提示注入）维持登记，
  触发条件不变。

## Decision

### 1. 完成线是「内部试用就绪」，不是「13 项全清」或「生产上线」

内部试用就绪的判据：

1. 真实买家与坐席能连续走完主流程：登录 → 提问 → 业务办理 → 转人工/退款受理 →
   坐席处理 → 买家读回；
2. 失败可解释、可查询、可降级；涉资动作始终停在 `PENDING_APPROVAL` 或
   `DEGRADED + 可查工单`，不允许正文冒充已办理；
3. 退款链路连续 10 次端到端通过，覆盖放行、驳回、超时/降级三条分支；
4. 10 次运行中：0 次谎报已办理、0 次跨买家串号、0 次重复退款；
5. 所有未达成项保留实测值、归因和触发条件，不摘红、不改判据。

这条线**不代表生产就绪**：多实例、真实支付、真实 SMTP、跨平台身份、知识服务化
和输入侧防注入仍不在承诺范围内。

### 2. 第一验收脊柱是退款全链路

退款同时穿过身份、会话、工具派发、业务状态机、跨进程工单、人工审核、审计和买家
读回，是当前仓库里最能暴露一致性问题的路径。第一波只做三张票：

1. **U3 / 票 234：退款审批跨进程原子性**——受理事务内落待开单意图（outbox），
   事务外幂等补偿开单、重试/退避、可回填 `ticket_id`；开单失败不得回滚受理。
2. **U12 收窄 / 票 235：退款回读结构化**——保留自由文本断言，新增机器可读的
   `refundReview` + 到账边界字段；local 3B 的工具派发率接受为「可降级 + 工单」，
   不追 local 27/2。
3. **R10 / 票 236：测试审计事件隔离**——审计流名可配置，JVM 测试写独立流，
   不污染活体 `audit_event`；活体默认流名不变。

三张票按 234 → 235 → 236 顺序执行；235/236 在前一张签收前保持 blocked。

### 3. 后续分波只做能形成产品闭环的项

- **第二波（票 237–241）**：U8（检索降级可见性 + 旧 L1 `sourceDocs`）、
  U11（极性守卫前置稳定性）、U10（压测工装可比性）、R21（dev 矩阵判据）、
  R15（gold 红点裁决）。这组先解决「测量是否可信」，再决定是否改产品。
- **第三波（票 242–243）**：R5（长期指标/看板）、R6（政策词表扩充）。
  两项都以真实试用反馈为触发，不以「看起来更完整」为理由提前做。
- **维持冻结**：R1、R3、R8 按各自既有触发条件登记，不在本程序内开票。

### 4. 程序边界与终止

- 本 ADR 只授权 Round63 的第一波；第二、三波在上一波收口后重新由所有者确认，
  **不自动续期**。
- 每张票的完成仍以契约冻结、独立 Verifier 亲跑、P0/P1 清零、所有者书面签收为准。
- 任何一项若要改判据、阈值、gold、分母或降级枚举，必须另立 ADR，不得借本程序
  顺带放行。

## Considered Options

- **把 13 项登记债一次清完再交付**：否决。范围跨越知识服务化、跨平台身份、
  长期存储与模型稳定性，任何一项都不是单轮可验证的；同时做会让「哪一项真的
  改善试用」无法归因。
- **直接按生产就绪标准做**：否决。真实支付、SMTP、多实例、跨平台身份和知识
  服务化都缺少真实依赖；在本机合成数据上宣称生产就绪是不诚实的。
- **先追 local 3B 的 27/2**：否决。local 模型能力边界不是本轮产品缺口；
  已用「未派发写工具不得声称已办理」把风险收口到可降级 + 工单。
- **只做 UI/演示面**：否决。退款受理与开单之间的跨进程缺口、审计流污染都会
  在真实试用时直接损坏证据。

## Consequences

- 第一波会让退款受理多一张 outbox 表与一个补偿器；受理事务只写本地事实，
  跨进程开单失败不再丢意图，但工单创建仍是至少一次语义，极端崩溃窗口可能重复
  开单，需在票面登记。
- 买家回读增加结构化到账边界字段，旧 `message` 文案与自由文本断言保留；
  前端与脚本可以逐步从措辞匹配迁到字段断言。
- JVM 测试默认写独立审计流，活体查询面不再混入 `agent-001` / `alice` 之类的
  测试行；生产流名与已有数据不变。
- 第二、三波在此之前保持登记；R1/R3/R8 仍不执行。
- README、tracker、`docs/PROJECT_PLAN.md` 与 `registered-debt.md` 需要同步
  本程序的状态，但不得把「已开票」写成「已完成」。
