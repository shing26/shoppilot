# 自建轻量身份域，审计走事件流

Context: 身份注入目前是 mock JWT（ADR 0014）：网关发签、身份直接进上下文，没有真实账号体系。定位改为可运行系统后有两处立刻暴露——买家端需要一个真登录（否则"我的订单"是假的），坐席工作台需要一个真账号（否则"谁审了这笔退款、谁领了这张工单"无法回答，而退款审批是不可逆的资金动作）。同时 PII 已有脱敏标记体系（跨租户 gold 的 `mustNotLeak` 三条标记就是这个），需要延续而不是另起一套。

Decision: 自建轻量身份域——用户表（买家 / 坐席 / 管理员三角色）+ bcrypt 密码哈希 + 自签 JWT（沿用 ADR 0029 的密钥与 bind-address 门控设施）+ 登录/注册端点 + 角色守卫。审计事件（谁审批退款、谁领取工单、谁改了规则表）发布到 `audit` topic（0054），**可查询、可对账**。PII 沿用现有脱敏标记体系，不新增第二套。

非目标（本轮明确不做）：refresh token、多因子、密码重置与找回、联邦登录、账号生命周期管理。

Considered Options:

- 引入 Keycloak：否决。本机内存已紧（见 0053 的资源账），再吃 0.5-1 GB；身份协议的调试工夫对本仓的核心叙事（客服系统的咨询与售后闭环）贡献低。
- 维持 mock JWT：否决。买家端与坐席端都建在假身份上，"安全与合规"这一域等于交白卷，退款审批这类不可逆动作也失去责任归属。
- 自建但引入现成用户表框架：否决。JPA 已在本仓（Flyway + Hibernate validate），再加一个用户表框架是重复投资。

Consequences:

- 买家端、坐席端从此有真账号；工单与审批动作有责任人。
- 审计从"日志里翻"变成"可查询的事件流"——收口审计可新增一条门禁：关键动作是否都有对应 audit 事件。
- 密码与令牌策略不做到量产级（BCrypt cost、锁定策略、密钥轮换都只做到演示口径），这一点必须写进交付材料而不是省略。
