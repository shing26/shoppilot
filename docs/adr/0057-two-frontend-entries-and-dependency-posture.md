# 前端双入口（Vite+Vue3），依赖口径在 program 期间放开

Context: 前端现状是单文件原生 JS 的调试台（`gateway/src/main/resources/static/index.html`），零 node 依赖、零构建、CI 无前端步。黑盒 QA 已经证明过这份省法的代价：单文件里塞满读数格、抽屉、审核面板、确认框，交互缺陷成批出现（ticket 61/61 的收尾修复七处里有一半在前端）。定位改为可运行系统后，还要做坐席工作台——队列列表、领取、处理、SLA 倒计时——这是交互最密集的一页，继续手写全局状态会是下一个 QA 事故源。

Decision: 引入 **Vite + Vue 3**，两个入口：

1. **买家会话页**：SSE 对话、售后进度、工单状态；
2. **坐席工作台**：队列可见、领取、处理、SLA 倒计时。

旧调试台**保留为运维页**（不删：它承载读数与验收脚本的入口）。CI 增加一步前端构建门禁。依赖口径：v1.0 冻结期「发布阶段不新增依赖」是那张时期的约束（见 `docs/PROJECT_PLAN.md`），program 期间**允许前端 node 依赖**入仓（`package.json` + lockfile 一并入库，构建产物不入库，由网关或静态目录加载）。

Considered Options:

- 继续零构建、多文件原生 JS：否决。零新依赖很诱人，但交互密集页的状态管理靠手写会持续产出缺陷，且"系统"在前端这一层明显薄。
- 只做坐席工作台、买家端继续用调试台的会话 tab：否决为"以后再说"，接受为"下一轮"。但用户端是本 program 点名的域，推后会让"系统"的完整叙事缺一角；本 ADR 取两者都做。
- React + 全套组件库：否决。Vue 3 在本仓场景足够，引入更大的组件树只增加构建与审计面。

Consequences:

- 仓内首次有 node 依赖 → 干净克隆的验证需要 node 环境，`clean_clone_check` 与 CI 都要加一步。
- CI 从八步 → **九步**（加前端构建），门禁读数与 EVIDENCE 同步更新。
- 前端断言仍走既有 `verify-console.mjs` 那套 Playwright 路线扩展，不另立判据体系。
- 调试台保留意味着前端有两套（运维页 + 两个新入口）——**明确它是过渡态**，不要求两套能力对齐。
