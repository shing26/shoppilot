# 缓存准入拆掉向量这道门，但保留检索降级这道门

Context: 备料 ticket 18 的"压测期间模型服务停用"那一格时，先发现 `CacheService.prepareWrite` 把"有没有查询向量"当成整次写回的门槛，而 L1 的 key 是 `MD5(租户 + 意图 + 知识库纪元 + 归一化问法)`，从头到尾不需要向量。这不是设计，是把 L2 的前置条件顺手写在了两层共用的入口上：向量服务一挂，连不依赖向量的那一层也停止积累。拆掉之后用 `perf,no-ollama` 实测，才看见第二道门——而且那道门是对的：向量服务停用使稠密召回 0 命中，混合检索据此标记 `degraded=true`，ADR 0006 的资格判定拒绝为降级检索出来的答案建缓存。于是缓存照样停止积累，但原因换成了一个有意保留的质量门。决定：只拆第一道门，保留第二道门，并把第二道门的代价实测出来写在这里。

Considered Options（已否决）：给 L2 塞零向量或随机向量占位——零向量的余弦无定义，随机向量会在语义空间里造出不存在的近邻，等于用缓存污染换一个好看的可用性数字；写回时同步重试 embedding——写回发生在 SSE 收尾之后的虚拟线程上，重试既拖慢异步路径，又把缓存层重新耦合回向量服务，正是这次要拆掉的东西；为降级检索的答案单开一个短 TTL 写回桶——这条真能把故障期间的纯缓存拦截率从 7.3% 拉回七成，代价是把只有一路召回支撑的答案固化进缓存、并在服务恢复后继续复用，与 ADR 0006 立这条门的初衷正面冲突。收益不过"故障那几分钟少打一些模型"，和污染风险不对称，本冲刺不做，列为后续实验。

Consequences:
- ADR 0006 的写回资格清单由本 ADR 收窄一项：`能拿到查询向量` 不再是资格，`检索未降级` 仍然是。前者是缓存层的实现细节，后者是答案质量。
- 向量服务停用时的两条信号要分开读，别再混成一条。`shoppilot_cache_embed_unavailable_total` 增长，说明 L2 检索与向量定位落空；`shoppilot_cache_writeback_l1_only_total` 在整场停用里为 0——这不是缺陷，而是它前面还有一道门：向量拿不到时稠密召回同时失败，写回在资格判定处就被 `degraded` 拒掉了。但后一个计数器不是摆设，D 组（`perf,no-embedding-cache`，每请求真打 bge-m3）把它跑出来了：100 并发那档 `embed_unavailable_delta` 22、`writeback_l1_only_delta` 13——向量服务没死、只是被压到超时时，缓存那一次 embed 超时了，而稍后稠密召回那一次成功，于是答案非降级、向量却不存在。这 13 条正是拆门的意义所在：不拆的话它们连 L1 正文都进不去。
- 代价量化成两组曲线（`perf,no-ollama`、`l1` 流量模型、4 workers、60s/步，与同机 `perf` 的 A 组对比），分开报是因为“缓存里有没有存量”是这一层唯一还在服务的东西。
  - 冷缓存（先 flush 再压）：136.20 / 265.05 / 481.73 QPS @ 100 / 200 / 400 并发，纯缓存拦截率 0，拦截总量 21.8% / 29.6% / 37.4% 全靠穿透合并独扛（`ladder-l1-perf,no-ollama-20260909-123509-noollama.csv`）。
  - 有存量：Redis 里已有的 L1 条目照常命中（`l1_delta` 608 / 1123 / 2035、命中 p50 8ms），纯缓存拦截率 7.34% / 6.84% / 6.91%（`ladder-l1-perf,no-ollama-20260909-114341-noollama.csv`）。停用的是“积累新答案”，不是“复用已有答案”。
  - 对照组 A 组同条件是 296 / 580 / 976 QPS、纯缓存拦截约七成。四组数字错误率都是 0，p99 稳定在 1200-1300ms：系统降级而不停摆。
- 运维真正要盯的是 `shoppilot_cache_embed_unavailable_total` 的增速，不是拦截率：拦截率跌下来时，故障已经持续了一阵子。意图 T1 质心、L2 缓存、稠密召回共用同一个向量服务，所以这一个信号同时预告三件事失效。
- 性质由 `CacheServiceTest` 钉住四条：向量不可用时 `lookup` 不抛异常而是返回未命中；无向量的写回只触达 L1 且 L2 零调用；有向量时两层都写；L1 命中路径零 embedding 调用。
