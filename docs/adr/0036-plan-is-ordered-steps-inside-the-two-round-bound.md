# PLAN 升级为有序步骤序列（≤2 步），仍在上限 2 轮的工具边界内

Context: 对标架构中 LLM 规划产出 PlanStep 列表再调度执行。ShopPilot 的 PLAN 阶段目前是"单次 tool_call + 循环重入"，硬上限 2 轮（ADR 0008）。单步循环已覆盖"查完再答"，但覆盖不了"先查订单状态、再对该订单发起退款"这类**后步参数依赖前步结果**的两步链——现状只能靠用户分两句说，或模型一次把参数全猜对。

Decision: PLAN 阶段的产出物从单次 tool_call 升级为 `Plan`：有序步骤列表，长度 ≤ 2，每步 = 工具名 + 参数表达式（参数可引用前步结果字段，形如 `{steps[0].result.orderId}`）。执行语义：

- `TOOL_EXEC` 按序执行；前步失败即中止整条 Plan，不执行后步（后步的前提已不成立）；
- 每步结果仍走既有视图校验与归属双条件校验，校验语义不变；
- Plan 之外的一切不变：不并行、不分叉、不重排；`plan.length ≤ 2` 与 ADR 0008 的 2 轮硬上限是**同一条边界的两种表述**，不放宽；
- MockLLM（perf 口径）返回固定 Plan 模板，JVM 层 0 token 可测执行语义（依赖注入、失败中止、归属校验）。

意图层不感知 Plan：T0/T1/T2 的判定与缓存准入语义完全不变；Plan 只发生在已进入 action 链路之后。

Considered Options:

- 放宽到 3 步以上以覆盖"查订单→查物流→改地址"长链：否决。长链的本质是用户诉求不聚焦，正确做法是槽位追问或转人工，不是延长机器自主性；ADR 0008 的时延预算论证今天仍然成立。
- 步骤并行/DAG：否决，见 ADR 0040。两个工具 20ms P99 的世界里，并行的收益不存在的风险是归属校验与幂等语义复杂化。
- 用通用规划框架（LangGraph 类）替换手写编排：否决，与 ADR 0032（手写编排 + provider seam）直接冲突；Plan 只是把 PLAN 阶段的返回类型从"一个调用"变成"一个列表"，60 行内的改动。
- 依赖表达式让模型自由生成 JSON path：否决。表达式只支持 `steps[i].result.<field>` 单一形态，正则可校验，防注入面收敛——模型自由生成取值路径等于把归属校验的输入交给模型。

Consequences:

- `AgentStateMachine` 是本轮唯一触碰的核心文件，改动收敛在 PLAN/TOOL_EXEC 两段；工单/幂等/降级代码不动。
- 评测集新增 `cases-part6-plan.jsonl` 14 条：两步链 8 条（含前步失败中止 2 条）、单步应退化为单步 4 条、表达式越界注入 2 条。
- 硬性闸门（ADR 0033）：全量 357 条评测回归不得低于基线；不达标则 round17 收缩、本票挂账。
- 指标新增 `shoppilot_plan_steps_total{steps=1|2|aborted}`，两步链的时延分布单独一条曲线，防止两步链混入单步口径拉高 P99。
