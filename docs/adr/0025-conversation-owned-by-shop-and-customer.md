# 会话归属是「店铺 + 买家」两者，键形状随之改变

Context: 会话状态外置在 Redis，键形状是 `shoppilot:session:{tenant}:{conv}`，不含买家；而 `conversationId` 由客户端经 `X-Conversation-Id` 自带（缺失时网关给一个随机 UUID，前端用 `crypto.randomUUID()`）。于是同店铺内任何买家把该头填成别人的值，就能载出对方的对话轮次喂进 prompt，并把新轮次写回对方会话，双向污染。词汇表把**串号**定义成「一个买家的答案被发送给另一个买家」，不限跨租户；ADR 0005 的三道防线里，防线一只拦客户端传来的 `tenantId`，防线三的用例只钉跨租户。定义要求拦的事，防线没覆盖。

决定：会话归属取「店铺 + 买家」两者，键形状加一个 `customerId` 段。不迁移旧键，靠 TTL 自然走。

## Considered Options

- 首写绑定 owner、后来者不匹配即拒：否决。多存一份 conv 到 customer 的归属映射与一条失效路径，只换来「能报警说有人试过别人的会话 id」，而本仓没有告警面可收这个警。
- 服务端派生 `conversationId`、拒收客户端自带：否决。客户端自带会话 id 是真实接入方的常态形状，这一刀改的是接入契约而不是隔离。

## Consequences

- 订单行侧不受影响：`findByIdAndCustomerId` 与含买家的幂等键照旧拦得住跨买家的写操作。本 ADR 修的是上下文可见性，不是资金安全，README 隔离矩阵那行不许顺手升格成「跨买家隔离已达成」。
- 最要紧的一条用例是跨买家不得续办别人的待办动作：现在的形状是 B 带 A 的会话进 resume 分支、拿 A 的参数去发动作，行级守卫会在最后一步挡下，但参数已经进了 prompt。
- ADR 0005 的覆盖边界由本 ADR 收窄而非改写：三道防线管租户与订单行，会话上下文归本 ADR。既有 ADR 不改，按 ADR 0023 那条例子走新 ADR 声明。
