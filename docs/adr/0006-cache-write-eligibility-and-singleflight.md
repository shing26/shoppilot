# 缓存写回资格判定与 singleflight

Context: 任务书只定义了命中返回，未定义写回与击穿防护。无条件写回会把"系统繁忙已转人工"、LLM 拒答、检索无结果的兜底话术固化进缓存，监控上呈现拦截率 85%、TP99 22ms 的虚假繁荣，实际在批量复读道歉语；同时大促爆款问题在写回前的数百毫秒窗口内会被并发全量打穿到模型。决定：引入写回资格判定 + singleflight 合并穿透。

写回资格（全部满足才写）：意图为政策咨询、检索有命中、答案非空且长度达标、未触发降级或转人工、未触发工具调用、无错误标记。写回内容含 `intent / tenantId / scope / kbEpoch / sourceRuleIds / modelId / 生成时间`，读取时校验 intent 与 tenant 一致。TTL 政策类 6 小时，叠加知识库纪元强制失效。写回在 SSE 收尾后由虚拟线程异步执行，失败不影响用户响应。**2026-09-09 修订**：这份清单不要求"能拿到查询向量"——L1 的 key 不需要向量，向量缺失时只写 L1 正文、不写 L2 定位，见 ADR 0018。

Considered Options（已否决）：把 token 流 tee 给 singleflight 等待者——需要引入多路流转发状态机，收益只有约 800ms 等待，冲刺周期不值得；等待者改为**收完整答案后一次性推送**，等待上限 2s，超时则自行穿透。

Consequences:
- 负缓存：检索无结果的冷门 query 写 60s 空标记，但仅对已准入缓存的意图生效，不污染业务办理链路。
- singleflight 进程内用 `ConcurrentHashMap<String, CompletableFuture>` 合并，跨实例用 Redis `SETNX`；单实例演示时进程内层即够，但两层都写出来才讲得出分布式合并。
- 命中路径与未命中路径的推送形态不同（一次性 vs 打字机），前端调试台需能区分展示。
