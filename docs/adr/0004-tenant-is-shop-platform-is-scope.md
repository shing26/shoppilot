# 租户 = 店铺，平台以政策范围表达，跨店不聚合

Context: 任务书在缓存 key 与限流维度上使用了 `TenantId` 却未定义租户，而知识库内容同时含平台规则（7 天无理由、跨店满减）与店铺规则（生鲜保鲜理赔、退换细则），"跨店"一词已预设多店铺加一个平台。决定：租户 = 店铺（Shop），是数据隔离、缓存分区、限流配额与政策归属的唯一单位；平台不作为租户，而是以政策条目上的 `scope = PLATFORM | SHOP` 表达，平台级政策全租户共享同一份；买家（Customer）身份平台级唯一，会话上下文携带 `(tenantId, customerId)` 二元组。

Considered Options: 租户 = 平台（店铺级政策无处安放）；跨店聚合查询（需要引入买家对平台的跨店授权同意，数据模型复杂度翻倍，冲刺周期内做不完）。

Consequences:
- 跨店咨询一律不聚合：买家在 A 店问 B 店的订单，网关只查本店，查不到即回答"未在本店找到该订单，若您在其他店铺购买请联系对应店铺客服"，不把 B 店任何数据带进 A 店会话。
- 订单归属校验必须是 `order.tenantId == session.tenantId && order.customerId == session.customerId` 双条件，这是任务书未提及的 IDOR 防线。
- 限流分两层：租户级配额（店铺大促包量）+ 买家/IP 级防刷。
- 缓存 key 与向量检索 filter 必须含 scope，否则平台级政策会按店铺复制 N 份且答案漂移。
- 平台级政策共享意味着一个租户不能污染平台条目，入库脚本需区分来源。
