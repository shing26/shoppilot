# 系统提示词外置为版本文件，meta 记当前版本，SSE 与评测报告携带版本号

Context: `SYSTEM_PROMPT` 目前是 `AgentStateMachine` 内的 `private static final String`，全仓无 prompt 版本痕迹。round17 的风格引擎（0038）要按渠道×情绪×意图改写提示词片段，若无版本化，任何一次风格改动都无法归因、无法单独回滚、评测报告无法标注对应的提示词形态。此票是 0038 的硬前置。

Decision: 最小版本化，不引框架：

1. 提示词正文抽到 `shoppilot-gateway/src/main/resources/prompts/agent-system/v1.0.0.md`（正文与现行 11 条规则逐字一致，迁移即不改语义）；
2. 同目录 `meta.json` 记 `{"current": "v1.0.0"}`，启动时读入并打印版本号；
3. 历史版本文件只增不删；`meta.json` 指向不存在的版本 → 启动失败（fail-fast，与 ADR 0029 同取向）；
4. SSE `meta` 事件新增 `promptVersion` 字段（事件已存在，加字段成本为零，旧客户端不读不受影响）；
5. 评测报告头写入 prompt 版本；EVIDENCE 纪律下，任何评测数字必须能归因到提示词版本。

风格引擎的动态片段（0038）不写死进版本文件：版本文件是基座，风格段以运行时拼接注入，基座版本 + 风格档位共同构成"提示词形态"的完整归因。

Considered Options:

- 每渠道/每情绪独立提示词文件：否决。文件数爆炸且组合语义漂移无人守得住；基座 + 注入段两层才能让"改一个词影响哪条链路"可回答。
- 引入 prompt 管理框架（Langfuse 等远端管理）：否决。新增外部依赖与网络依赖，违反单机边界；两个文件的版本化解决的是归因问题，不是协作问题。
- 只加版本常量不外置文件：否决。常量在代码里改一行就发版，版本号与人肉 diff 无从对账；外置文件使 git 历史即版本历史。

Consequences:

- 改提示词的 PR 必须同时动 `meta.json` 与评测基线（若走门禁比对），"顺手改一句 prompt"从不可追踪变为必须留痕。
- 评测子集进 CI（ADR 0033 前置票）之后，CI 报告同样携带版本号，基线比对才有归因意义。
- 迁移本身无行为变更，验证判据 = 迁移前后 `mvnw verify` 全绿 + 11 条规则文本逐字 diff 为空。
