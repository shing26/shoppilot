# 缓存查询位于意图路由之后，且 fail-closed

Context: 任务书原顺序是 `query -> L1 精确匹配 -> L2 语义匹配 -> 命中即返回`，即在判定意图之前就把答案发出去。这会造成串号：「我的订单发货了吗」对所有买家文本完全相同，连 L1 精确哈希都拦不住；「怎么退款」与「为什么不给退款」余弦轻松过阈值；通用政策答案对带了特殊服务标的具体买家是错误结论。决定：把缓存降级为意图路由之后的一个分支，只有判定为政策咨询的请求才准入 L1/L2，业务办理与含实体请求直接进 Agent 编排；预判不确定时一律不准入（fail-closed）。

Considered Options: 保留前置缓存但在 key 中加入 userId（堵不住政策类答案的个性化误判，也堵不住意图漂移）；只靠调高语义阈值（降低概率而非消除，且拦截率随之崩塌）。

Consequences:
- 缓存不再是零成本前置，它依赖意图预判规则表的维护质量；预判错分会让本该缓存的请求打穿模型。
- 拦截率 80% 是结果而非目标，实测低于 80% 可接受，串号 0 次不可协商。
- 缓存条目必须携带意图与租户并在读取时校验一致，把语义漂移转化为跨意图隔离问题。
- 政策答案模板禁止断言式个性化结论，涉及「你是否适用」时输出引导语，把个性化判断交回业务办理链路。
