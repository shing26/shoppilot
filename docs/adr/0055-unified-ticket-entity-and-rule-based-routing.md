# 工单统一为一个实体，分流是规则表 + 坐席领取

Context: 「需要人工介入」在本仓现在是三个混血体——① 降级工单（`FallbackReason` → ticket 表，九种降级每种都落这里）② 满意度复核队列（feedback 的显式点踩与隐式信号）③ 退款审批队列（`Refund.PENDING_REVIEW`，round21 建的审批闸门）。三套机制、三张表、三种流转、各自的"处理完"定义。自动分流要成立，第一步不是写规则，是先有**一个统一实体**：否则规则表没有分母，「这张工单该去哪」这个问题对三种表有三种答案。README 的公开口径「降级原因 枚举 10 / 降级 9」挂在第一种上，合并时不得静默改它。

Decision: 统一为**一个工单实体 + 三种来源**（`degrade` / `feedback_review` / `refund_approval`）。分流规则：

- **规则映射**（可配置表）：意图 × 情绪 × 租户 → 队列；表是数据不是代码；
- **优先级枚举**：情绪紧急 > 资金类 > 普通；
- **坐席模型**：pull——工作台队列可见、坐席手动领取，不做自动派单；
- **SLA**：只做计时与超时升级标记，不承诺解决时限。

结算与坐席：工单处理结果回写工单实体并发布事件，买家侧通过对话网关读回。

Considered Options:

- LLM 判断工单归类/优先级/摘要：否决并登记。自主性叙事更强，但模型方差进入分流链路——同一张工单两次分流可能不同，审计与对账都变难，且多一跳模型调用。触发条件 = 出现真实的分流准确率诉求。
- 自动派单 push + least-busy 负载均衡：否决并登记。需要坐席在线状态/心跳/占用管理，而目标场景坐席就一两个人，负载均衡是空转。触发条件 = 坐席数 > 1 且有并发分配诉求。
- 维持三套机制各自流转：否决（这是改动的起点，不是选项）。分流没有统一实体就无法做，而"三套各自可查"正是当前对买家和坐席都不友好的原因。

Consequences:

- **CONTEXT.md 补术语**：工单、工单来源、队列、优先级、坐席、领取、SLA 计时。
- **降级口径的迁移必须显式登记**：枚举 10 / 降级 9 的公开数字不变，三种来源的映射关系写进本 ADR 与 EVIDENCE，不得改分母让数字变绿。
- 规则表是数据 → 需要一张"规则可改且改动被审计"的机制，否则规则漂移无法归因。
- 工单服务（0053 的第四个服务）以本实体为它的核心表。
