# 首字时延按路径分桶重测：未命中那条判据的差距归因到向量化，不归因到编排

Context: 复核 PLAN 承诺项"未命中 TTFT < 500ms"时读了产出那条数字的脚本，发现两处测量缺陷。
第一处：`run_sse_ttft.py` 把"收到第一个 SSE 分片"当成首字，而服务端在检索与模型之前就会推 `status`/`meta` 帧，
所以旧产物 `sse-ttft-20260909-001822-500-perf.csv` 量的是首帧，不是首字。第二处：它把所有样本混进同一个分位数，
而判据的对象只有"未命中"那一部分——500 条长连接跑 60 秒里七成以上是 L1 命中（24 个 (租户, 问句) 组合被反复问），
所谓 592ms 其实是"命中路径在 500 并发下的首帧"，与它要证明的判据不是同一件事。
把两处都修掉之后重测，旧数字的解释力直接没了，但判据本身也第一次变得可谈：未命中慢在哪一段，能量化。

决定：
1. 首字只认第一个 `event: token` 帧；`first_frame_ms` 另记一列，两者都落盘，不再互相冒充。
2. 按服务端自己在 `meta` 帧里给出的 `cacheLayer` 与 `intent` 分三桶：`hit`（L1/L2/FLIGHT）、
   `knowledge`（未命中且非动作意图）、`action`（未命中且 `ACTION_*`）。判据只在 `knowledge` 桶上算。
   `action` 单列不参与 500ms：动作意图按 ADR 0008 最多两轮工具调用，perf 下每轮 Mock 各 300ms，
   拿它去对"未命中端到端首字"是要素不对，不是成绩差。
3. 未命中判据必须配一份分段归因（`scripts/ttft_attribution.py`）：单条长连接串行打强制未命中的知识问句，
   网关先重启到 perf（服务端计时器按进程累计，不重启就分不清是哪一轮），再把服务端四个计时器与
   外部探针（`scripts/probe_embedding_latency.py`）拼成一张分解表。没有这张表，"未达成"三个字没有工程价值。
4. 归因里"新问句向量化"这一步服务端没有计时器包住，用外部探针实测补上，并在文档与表里写明它是补的，不伪装成埋点。

Considered Options（已否决）：
- 把 `perf-first-token-latency` 从 300ms 调到 100ms。数字立刻变绿，改的却是判据的分母而不是系统，
  与 PLAN "未达线必须给出实测值与归因，不得改口径蒙混"正面冲突。
- 只用服务端已有的 `shoppilot_ttft_seconds` 替代客户端测量。它不区分命中与未命中，且只有进程级累计值，
  混合样本照样把它带偏；保留它，但作为归因口径而非判据口径，两者并报。
- 只在 500 并发上测（任务书字面条件）。单点分不出"排队"与"每请求固定开销"，而这次要回答的正是这个问题。
- 关掉 L2 语义缓存来"隔离未命中"。关掉之后稠密召回仍要同一个向量，未命中的开销一点没少，
  只是把缓存层自己的指标搅浑（ADR 0018 已经说明这两道门各自量的是什么）。

Consequences:
- 判据结论是**未达成**，但差距第一次有了归属：未命中知识路径 P50 690 ms（1 并发串行）/
  1031-1049 ms（50-200 并发，几乎不随并发变）/ 1499 ms（500 并发）。
  分解表：服务端 TTFT 均值 725 ms = Mock 首字固定下限 300 + 本机 bge-m3 单条新问句向量化 311
  + 稠密检索 4.8 + 词法检索 5.8 + **网关编排余量 104**。
  也就是说 500 ms 这条线在"perf 的 Mock + 单机 CPU 跑 embedding"这个形态下光靠固定项就过不去（300+311=611 ms）。
  要达成只有两条路：把向量化挪出请求关键路径（ADR 0011 的独立批处理服务），或在 dev 口径下用云端模型与云端向量重测——
  PLAN 本来就写明 dev 模式只报实测不承诺。
- 一个结构性事实被顺带挖出来：**新问句的向量化发生在 `CacheService` 的 L2 查表里**（T0 关键词层定案的问句不带向量进缓存读，
  见 `AgentStateMachine:125` → `CacheService:124`），那一步没有任何 Timer 包住，所以它在服务端指标里是隐形的。
  真要做首字 SLO 告警，第一个该补的就是这里的埋点；列后续，不在本冲刺。
- 全新问法在高并发下会被向量服务串行化：100 并发时未命中首字 P50 到 10358 ms（50 并发 2779 ms）。
  这与 ADR 0011 的"embedding 是第一瓶颈"互相印证，也说明 `--force-miss` 这类流量是压力测试的合法一档，
  不是"最真实的一档"：真实大促里同一政策问题被问一万次，向量化只发生一次。两臂都要跑，只跑一臂会得出相反结论。
- 顺带修正一条会被读歪的实测结论：**L2 语义缓存在真实噪声下并非零召回**。同一政策问句加 8 个随机字母仍能
  以 ≥0.95 命中 L2（扫描里 234 条、归因跑 9 条）。这与 ticket 17 的"同意图人工改写对在 0.95 工作点召回为 0"不矛盾——
  那测的是人工改写，这里是同一句加噪声。两句都写进文档，避免后来人把"召回 0"读成"L2 永不命中"。
- 新增产物：`loadtest/results/sse-ttft-*-sweep{mix,miss}.csv` 8 份、`sse-ttft-*-attrib.csv` 2 份、
  `ttft-attribution-*-1conn.csv` 1 份、`docs/ttft-sweep.png`；`docs/loadtest-report.md` 由
  `build_loadtest_report.py` 自动汇编这三节。旧的首帧产物保留并降级标注，README 与报告都写明它不能作为未命中 TTFT 的证据。
- 命中路径获得一份独立复核：SSE 客户端口径 P50 11 / 11 / 21 / 492 ms、P99 45 / 48 / 123 / 603 ms
  （50 / 100 / 200 / 500 并发）。200 并发内贴着十几毫秒、500 并发整条曲线一起抬，
  这是同机争抢第一次被这样隔离出来，而不是被当成一句归因话术。
