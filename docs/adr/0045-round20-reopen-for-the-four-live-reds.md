# round20 重开：修 22 步矩阵的四条红（三条事实性修正 + 一条需新决策的 orderNo 溯源）

Context: 2026-09-24 全量 22 步活体矩阵复测得 **18 步绿 / 4 步红**（`logs/acceptance-run-20260924-180518.log`，512 s）。四条红是 `action`、`emotion`、`feedback`、`plansteps`。次日（2026-09-25）对四条红逐条做根因取证，结论是**三条红的根因不在被测代码，而在验收脚手架与用例数据自身**：

- `feedback`（4 PASS / 3 FAIL）：三条断言**在结构上不可能通过**。`scripts/verify-feedback.ps1:103/106/116/123` 用管道形式调用自己定义的 `Get-Counter`，而该函数（`:27`）只有位置参数、没有 `ValueFromPipeline` → 参数整体前移（`Metrics` 收到指标名、`Name` 收到标签、`Tags` 为空），`$_ -like "$Name*$Tags*"` 永不命中 → 恒返回 `0.0` → `0 -gt 0` 为假。**已用仓库自己的 pwsh 7.4.20 复现参数位移**。另一条（`negative`，`:36-42`）的刺激与它自己的注释矛盾：注释写「用一个必然走降级的问题」，实际发的是正常政策问句（实测 `intent=POLICY_RETURN cache=NONE degraded=false` → `fallbackReason == null`），按 `FeedbackService.java:107` 本就不该自增。
- `emotion`（7 PASS / 1 FAIL）：唯一失败项 `EMO-ESC-02` 的问句含 T0 升级词表里的「转人工」，而 **ADR 0042 规定显式转人工优先于情绪判定**——所以它现在落 `USER_REQUESTED` 是**正确行为**，是这条用例数据被 ADR 0042 从语义上推翻。机械核对确认：20 条问句里**只有它一条**含升级词。附带发现 `eval/cases-part4-emotion.jsonl:2` 的 `"intent": "ACTION_LOGISTICS"` 同样已失效（活体会被 T0 判成 `ESCALATE`）。
- `plansteps`（0 PASS / 7 FAIL）：机制是 local 档 `qwen2.5:3b` 不产生两步链（`shoppilot_plan_steps_total{steps="2"}` 恒为 0），语义本身已由 `PlanExecutionTest` 5 项确定性地钉住。**但这条红的登记材料本身有两处不实**：round17 spec 的 F3 行（`:106`）把 `PlanExpressionTest` 列为覆盖源，而**该文件在仓内不存在**（只有 `main/.../agent/PlanExpression.java`；全仓只此一处引错——票 39 引的是正确的 `PlanExecutionTest`）；且 `steps=2:0 aborted:7` 的 `aborted:7` 是进程生命周期累计值，被当成"本次读数"读。
- `action`（8 PASS / 3 FAIL）：**这一条是真正的功能缺陷，先前就存在**。本地 3B 把工具 schema 描述里的示例订单号 `10023`（`@ToolParam(description = "平台订单号，例如 10023")`，自 `f58e439` 起在仓）直接填进了 `orderNo`，而 `ToolDispatcher.isFabricatedOrderNo`（`:116-118`）只校验格式（`ORDER_NO = \d{1,12}`），`10023` 格式合法因而拦不住，工具被真的派发出去。回退到 round19 起点 `06331a4` 重建后同一步同样红，故非 round19 引入。

这四条都不是"回归"（`action` 有对照实验排除；其余三条根因在被测代码之外），因此 **ADR 0031 的触发条件未命中**。分两种依据处置：**票 53/54/55 走 ADR 0031 第 10 行的「事实错误、回归、崩溃和现有门禁要求的修复不受上述限制」**（三条都不改被测功能行为，改的是脚手架与用例数据）；**票 56 走项目所有者在知情政策下的显式覆盖**，因为它要动工具调用参数的来源判定（新的功能行为），需要一份新决策。**重开必须诚实记录为政策覆盖，而不是伪装成事实性修正**——与 ADR 0033/0041/0044 同形；反过来，也不许把三条事实性修正说成"必须开轮才能做"。

Decision: round20 范围锁定四条红的修复，票 53-56，一条一票。

| 票 | 内容 | 依据 | 依赖 |
|---|---|---|---|
| 53 | `feedback` 步：修正 `Get-Counter` 调用形式（两处读数恒定失败）与 `negative` 的刺激 | ADR 0031:10（事实性修正，不动被测代码） | 无 |
| 54 | `emotion` 步：把 `EMO-ESC-02` 从「词典层升级样本」重分类为「显式转人工样本」 | ADR 0031:10（用例数据与 ADR 0042 冲突） | 无 |
| 55 | `plansteps`：更正两处不实登记（不存在的 `PlanExpressionTest`、`aborted` 的生命周期语义）并把该步在 local 档登记为**已知不达成** | ADR 0031:10（只改文档，判据一字不动） | 无 |
| 56 | `orderNo` 溯源守卫：模型自报的 `orderNo` 不在本轮对话里出现过就不许拿它撞库 | **所有者政策覆盖**（新功能行为） | 无 |

具体口径：

- **票 53 不许改 `FeedbackService`。** 三条计数在代码侧都按 ADR 0039 正确实现（`negative` 判据 `fallbackReason != null`、`implied_dissatisfied` 判同意图且窗口内、`implied_retry` 判幂等命中）；红的成因全在脚手架。修读数之后若 `implied_retry` 仍不增，**那是模型能力问题**（3B 未必两次都发 `applyRefund`），按票 55 的处置登记，不许回头改被测代码去迎合脚本。
- **票 54 的修法是"重分类"，不是"把期望改成能过"。** 三个候选里：把期望直接改成 `USER_REQUESTED` 会让这条用例**不再测情绪驱动的升级**（且必须改 `eval_suites.py:73`，那里把 `EMOTION_ESCALATION` 硬编码成唯一的升级证据）；改问句去掉「转人工」则要动 `eval/cases-part4-emotion.jsonl` 的 query（该文件属"只增不改"）。**取重分类 + 新增**：把 `EMO-ESC-02` 移到"显式转人工"这一类（期望 `USER_REQUESTED`），并**新增**一条**不含**升级词的强情绪样本补回「词典层升级」的计数（满足 add-only）。随之换代 round17 spec 与 README 里「词典层 8 条」的自述。
- **票 55 一条判据都不改。** ADR 0043 的 Considered Options 明写「把判据改窄去适配实现，本仓明令禁止」，AGENTS.md 也禁「不改验收判据、阈值来让结果变绿」。所以 `plansteps` 的 7 条判据原样保留、该步在 local 档**照红**，只把登记材料改对：删掉不存在的覆盖源、把 `aborted` 的语义写清、并补一句「脚本只筛 `TOOL_EXEC` 行、丢了 `round=` 行，所以归因无法从该脚本自证；要看 `multi_tool_calls` / `write_nudge` 计数器或完整响应 trace」。可选：把 local 模型换 `qwen2.5:7b` 试一次（走 `.env`，零仓内 diff），**但换模型不改变判据，且本机内存/显存已紧（见 EVIDENCE）**。
- **票 56 必须先定"来源判定"的口径再动代码。** 现状是唯一守卫 `isFabricatedOrderNo` 只校验格式；网关在模型已经发出工具调用后不再介入（`deriveActionCall` 的入口条件是 `rounds == 0 && !toolUsed`，模型一发工具就整体跳过），所以**没有第二道**。修法要同时满足三条硬约束：① 不许把合法格式的值一律拒掉（`10023` 是合乎格式的，黑名单写法从语义上就是错的）；② 不许破坏续办路径（`askSlot` 之后买家补充的订单号来自补充轮的 query，`extractSlots` 能取到，必须继续放行）；③ 不许动 gold——`eval/cases-part2-action.jsonl:30` 的 `ACT-LOG-12` 已经逐字要求 `"slotAsk":true` 且 `"mustNotContainArgs":["orderNo"]`，即**这条红同时也是 gold 未达成**，修好它会让 gold 更绿而不是改 gold 去适应代码。
- **四条红的归因必须在收口时能自证。** 票 53/54/55 的修法是"让门禁真的开始测量"，所以收口要求是**修前红、修后绿的活体重跑读数**（`verify-feedback.ps1` / `verify-emotion.ps1` / `verify-plan.ps1` 以及 22 步矩阵的对应步），而不是"改完看起来合理"。票 55 例外：它本来就该继续红。

非目标（本轮不执行）：`feedback` 的三条隐式计数在 3B 下若仍不增，不做代码侧适配（登记为模型能力边界）；`plansteps` 的判据不动、不在 local 档强求转绿；`action` 的 schema 描述对称化（把 `QueryOrderDetailRequest` 那句「用户未提供时必须追问而非猜测」补到另外三个请求上）**只作为票 56 的辅助手段、且不得替代溯源守卫**——prompt 级劝阻对 3B 的有效性未证，而 `ACT-LOG-12` 要的是行为保证不是措辞建议。

Considered Options:

- **四条全走事实性修正豁免、不开 ADR**：否决。票 56 要新增一层行为判定（参数的来源校验），那不是"修既有门禁"而是新功能；把它塞进豁免等于**把政策覆盖伪装成事实性修正**，正是 ADR 0033 起就明令禁止的那件事。
- **四条全走所有者政策覆盖开一个大轮**：否决（形式上）。票 53/54/55 的依据确实是 ADR 0031:10，写成"需要开轮"会把豁免范围说窄，下次遇到同类脚手架缺陷又要重新论证一遍。本 ADR 一条一条写明依据，而不是图省事统一贴一个标签。
- **票 53 改 `FeedbackService` 让三条计数更"容易"增长**：否决。代码按 ADR 0039 实现正确，改它会让实现偏离已锁定的决策，而且掩盖掉"脚手架从未真正测量"这个更值得记住的教训。
- **票 54 直接把 `EMO-ESC-02` 的期望改成 `USER_REQUESTED`**：否决。它会让 8 条 ANGRY 样本降为 7、且这条用例不再测情绪路径；重分类 + 新增一条不含升级词的强情绪样本能同时保住两个判据面。
- **票 55 把两步链判据按 profile 分档（local 只验单步）**：否决。这正是 ADR 0043 明令禁止的"把判据改窄去适配实现"；本地模型弱是事实，掩掉判据不是修法。
- **票 56 在 `isFabricatedOrderNo` 里把 `10023` 加黑名单**：否决。它能立刻让这条红转绿，但语义是错的（`10023` 只是碰巧是示例值，换个示例值即失效），且把"防编造"退化成"防一个已知字符串"。

Consequences:

- 冻结线对 round20 之后的轮次继续有效；本轮结束后回到 ADR 0031 机制，**不自动续期**。四条票独立可交付，中途冻结任意时刻项目仍自洽。
- 票 53/54 会**改变验收脚手架的读数**（从"恒定失败"变成"真的在测"）。这是本 ADR 唯一需要特别声明的风险：门禁变绿不等于系统变好，所以在 spec 的验收判据里强制要求**修前红 / 修后绿**两组活体读数，缺一组不算收口。
- 票 54 要动 `eval/cases-part4-emotion.jsonl`（"只增不改"的用例文件）。取 add-only 形态：**新增**显式转人工 case 与新的强情绪 case，`EMO-ESC-02` 的处置写进该文件时同步更新 `eval_suites.py` 的 emotion 分支与其 24 条夹具。
- 票 56 会改变工具调用的行为面（某些原本被派发的调用会改为 `slot_ask`）。回归风险集中在续办路径与 gold：`ACT-LOG-12` 等缺槽位用例应转绿，而任何"用户确实给了订单号"的路径必须逐条复核不误伤。
- 本机资源已紧（主机内存剩 2.0 GB、TIME_WAIT 占满动态端口 80%、四套项目 17 容器争 4 GB 显存，见 `docs/EVIDENCE.md`），四条票的活体验收都要起栈，建议按票 55 → 53 → 54 → 56 的顺序做，把最省栈的一次放前面。
