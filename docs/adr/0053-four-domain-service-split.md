# 四个域服务：对话网关 / 知识 / 业务与工具 / 工单与坐席

Context: 现状是三模块——`shoppilot-gateway`（对话、编排、两级缓存、渠道入站、检索调用、运维端点、调试台）、`shoppilot-biz-mock`（订单、退款、工单、审批、反馈）、`shoppilot-tool-api`（跨模块工具与视图契约）。单进程里混着四个演化节奏不同的域：对话编排（毫秒级、模型调用）、知识（秒级、索引）、业务与工具（写动作、幂等、资金）、工单与坐席（人工异步、分钟到小时级）。工单域一旦要坐席 pull 领取与 SLA 计时，它就不该和实时对话共用一个进程的心跳与资源池。

Decision: 拆成四个 Spring Boot 服务 + 一个共享契约库：

1. **对话网关**：对话入口、意图/编排、缓存、渠道入站与出站适配；
2. **知识服务**：入库与混合检索（独占 ES/Qdrant）；
3. **业务与工具服务**：`biz-mock` 升格——订单、物流、退款、工具执行、审批闸门；
4. **工单与坐席服务**：工单实体、队列、坐席领取、SLA 计时。

`shoppilot-tool-api` 升为**契约库**：工具入参/出参、事件 schema、错误码，四服务共用。服务名固定（`gateway` / `knowledge` / `business` / `ticket`），不引入服务发现、配置中心、链路追踪——四条固定名字 + 编排脚本够用，引入治理面是本机内存与运维预算都换不来的收益。

Considered Options:

- 模块化单体（对话网关内按包切域）：推荐过，被否决。工单与坐席的 SLA 计时、pull 领取、事件消费需要一个独立生命周期；包边界挡不住"同一进程里实时链路被人工任务拖慢"。
- 五服务以上（渠道网关独立、审计独立）：否决。本机全栈已约 7 GB，每多一个 JVM 约 500 MB；收益（独立扩缩容）在演示流量下吃不到。
- 不拆，只加队列：否决。队列解决的是"人工任务不阻塞实时链路"，但四个域仍会互相直连调用，边界不成立，后续每次改动都要跨域协调。

Consequences:

- **本机资源账**：全栈约 7 GB（4 JVM ≈ 2-2.4 GB + ES/Qdrant/Redis ≈ 1.7 GB + local 模型 ≈ 3 GB），而本机同时跑着另外四套项目。**活体验证必须分档**（日常档子集 / 全栈档仅清场日），矩阵与收口审计按档改，全栈档的红不得冒充日常档信号。
- 跨域只走 API 与事件（见 0054）；禁止服务间直连数据库。
- 迁移是分阶段的：新服务先与旧模块并存、以开关切换，再摘除旧路径。**迁移期间不得静默改任何既有读数的分母**（尤其降级工单口径）。
