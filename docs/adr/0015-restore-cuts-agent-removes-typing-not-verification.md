# 恢复以"写代码耗时"为由砍掉的范围，保留以"无价值"为由砍掉的部分

Context: ADR 0013 的砍单把三类不同性质的削减混在了一起：因打字耗时砍的、因墙钟验证耗时砍的、因在项目里没有价值砍的。本项目由 coding agent 持续实现，打字耗时不再是约束，因此第一类全部恢复：跨实例 singleflight（Redis SETNX）、Prometheus 指标暴露与看板、`local` 模式专项验证、工单接管交互、全链路集成测试、数据规模回到 3 租户 / 200 买家 / 5 万订单、以及 L2 语义缓存阈值标定实验（反义对抗对 + 0.85-0.99 阈值扫描曲线）。

第二类与第三类不恢复，理由不是省时间：不做 rerank 精排（5 条候选加 30 篇语料喂不出精排价值，这是判断不是妥协）；ES 停在够用级（不做自定义分词器调优与同义词词典，同上）；Grafana 只导入现成 JVM 看板加两个自定义 panel，不自制仪表盘。

Supersedes: ADR 0013 的砍单清单。

Consequences:
- 排期不变（5.5 天），但省下的不是工时而是**墙钟**：真实约束变成压测重跑轮次（每轮 20-40 分钟且同机不可并行，否则数据互相污染）与**人对代码的理解预算**。
- 硬规则一：每个 ticket 收尾必须产出"本切片的关键决策 + 你需要能当场回答的三个追问"，否则交付物是一个自己讲不出来的项目。
- 硬规则二：每天预留 1 小时读当日 agent 产出，优先读状态机转移、缓存准入判定、归属校验三处——这三处最容易写出"能跑但理由错"的代码。
- 硬规则三：agent 不得自行修改 `CONTEXT.md` 术语定义与 ADR 结论；发现冲突时停下来问，不得选一个"能跑通"的写法继续。本轮 grilling 抓出的六个设计矛盾（缓存前置串号、QPS 与 embedding 吞吐、同进程无法演示降级、EventSource 不支持 POST、租户未定义、裸 Header 越权）都属于会被固化成数千行错误代码的那类。
