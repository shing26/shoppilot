# ACTION_ORDER 最低行归因：是 gold 边界太窄，重标 4 条；合并两个查询工具否决

Context: 交接文档「还欠着的三件事」第 1 件。README 指标表里最低的一行是 `ACTION_ORDER` 选对工具
72.2%（13/18），比次低的 `UNKNOWN` 还低 11.1 个百分点，答辩时一定会被指着问。悬而未决的是它到底属于哪种病：
(a) gold 标注的边界太窄——`到哪了`、`是不是已经发出去了` 这类问句两个工具都答得上，标注只准答一个；
(b) `queryOrderDetail` 与 `queryLogistics` 本来就该收敛成一个工具，契约错了。两条路的成本差先摆开：
(a) 全程零模型额度，(b) 要动 `ToolName`、`ToolContracts`、`AgentStateMachine` 的工具下发、
`ToolDispatcher`、`MockLlmClient`、biz-mock 六个面，并且必须重跑 180 条 dev（实测约 26.7 万 token，
超过 26 万的日预算）才有资格改 README 那一格。用户定的规矩是：**不许为了让 93.3% 变高而改测试或换口径**。

归因查到一半发现第三件事：评分器本身有四处缺陷（第 4 处是复核第 2 处时顺手查同型代码查出来的），其中一处让"参数填对没"这个子指标实际成了"工具选对没"
的函数，直接违反 ticket 16 票面的"分意图两个子指标分开报"。所以下面**严格分两段记录**——
第一段是业务能力读数（这个系统会不会选错工具），第二段是量具缺陷归因（我们那把尺子准不准）。
两段的证据、结论、修法互不引用对方的数字：重标改的是判据要接受什么，量具修的是判据能不能被信任，
把它们混成一句"修完涨了两个点"会把本轮全部信用赔进去。

## 一、业务能力读数（重标前后并列，不互相覆盖）

同一批明细、同一份模型输出，只换 gold 的合格答案集，离线重算（`--rescore`，零额度）：

| 意图 | n | 选对工具（旧 gold） | 选对工具（新 gold） | 判据变动条数 |
| --- | --- | --- | --- | --- |
| ACTION_ADDRESS | 18 | 94.4% | 94.4% | 0 |
| ACTION_LOGISTICS | 18 | 100.0% | 100.0% | 0 |
| **ACTION_ORDER** | 18 | **72.2%** | **94.4%** | **4** |
| ACTION_REFUND | 18 | 94.4% | 94.4% | 0 |
| ESCALATE | 18 | 88.9% | 88.9% | 0 |
| POLICY_FRESH / PROMO / RETURN / SHIPPING | 18×4 | 100.0% | 100.0% | 0 |
| UNKNOWN | 18 | 83.3% | 83.3% | 0 |
| 聚合 | 180 | **168/180 = 93.3%** | **172/180 = 95.6%** | 4 |

支撑这一段的证据，四条都可离线复查：

1. **放开的唯一资格是「对偶矛盾」**（定义见 `CONTEXT.md`，判据实现是 `verify_eval_judge.py` 的 `dual_partners()`）：
   同租户、同买家、同场景、两侧都是进度问法（`到哪` / `发了没` / `签收` 这类在订单详情与物流轨迹之间本就等价的说法），
   而订单桶认 `queryOrderDetail`、物流桶只认 `queryLogistics`。全表含进度问法的 `ACTION_ORDER` 样本恰 5 条，
   其中 4 条指得出对偶、这 4 条就是放开集，8 个 id 钉在 README 正文里当自缚证据——
   `ACT-ORD-09`「90002 这单是不是已经发出去了」↔ `ACT-LOG-09`「90002 这单发了没」（同单号）；
   `ACT-ORD-11`「帮我看看我的单子到哪一步了」↔ `ACT-LOG-11`「我的包裹现在到哪儿了」（两侧都还没给单号）；
   `ACT-ORD-16`「订单 88888888 现在到哪了」↔ `ACT-LOG-15`「99999999 的物流到哪了」；
   `ACT-ORD-17`「90001 这单到哪了」↔ `ACT-LOG-17`「90002 的快递到哪了」。
   第 5 条 `ACT-ORD-14`「90003 签收了吗？没签的话我要退款」的 gold 本来就是 `queryLogistics`，指不出对偶，所以不放开。
   后两组两侧单号不同，但同属"查不到单"与"跨租户探别人的单"这两个同场景：本轮认的是**问法形态**，不是订单号相同——
   写成"同订单"会把这 2 组排除在自己的结论之外，那是复核时纠正过来的。
2. **仓库自己的代码支持新读法**：`MockLlmClient.pickTool()` 的规则是
   `物流|快递|到哪|签收 → QUERY_LOGISTICS`，即 `到哪` 归物流；旧 gold 却把 `ACT-ORD-16/17` 的"到哪了"
   判给订单详情。模型与代码一致、与 gold 不一致——按"代码是活的、标注是死的"这条，错的是标注。
3. **反方向 0 犹豫**：18 条 `ACTION_LOGISTICS` 全部选 `queryLogistics`，一条不歪。真混淆应当双向，
   单向只说明"订单桶里混进了物流问句"，不说明"两个工具分不开"。
4. **差异集合被机器锁死**：`--rescore-expected-diff ACT-ORD-09,ACT-ORD-11,ACT-ORD-16,ACT-ORD-17`
   断言"新旧判定的**选对工具**差异集合恰好等于这 4 条 id"，其余 176 条的选对工具判定逐格一致——
   限定到这一列是必要的（复核时纠正的措辞）：同一份重算明细里 `args_ok` 列变了 72 条、`status_ok` 列变了 2 条
   （正是 `ACT-ORD-16/17`），说"其余 176 条逐格一致"会把量具那几处修复一起吹掉。
   多出来任何一条工具判定变化，重算命令直接非零退出。
   三条真错（`ACT-ORD-13`、`ACT-ADR-14`、`ACT-RFD-14`）未被放开。

这一段的结论不因为读数越过某条线而改变：承诺项的量纲是**分意图各自 ≥ 95%**，新判据下仍有 5 行未达线
（ACTION_ADDRESS 94.4%、ACTION_ORDER 94.4%、ACTION_REFUND 94.4%、ESCALATE 88.9%、UNKNOWN 83.3%），
所以 README 承诺项那一格仍然是「未达成」，一字未改；聚合那格并列两个读数正是为了防止它被单独引用。
阈值常量 `ACCEPT_TOOL=0.95`、`HARD_FAIL_INTENT=0.80` 与 `EVAL DONE` 标记在本轮 diff 里一行未动。

## 二、量具缺陷归因（与上一段独立，四处）

这四处缺陷在重标之前就一直存在，它们不改"模型选了什么"，只改"我们把什么算成对"。逐条给反证。

1. **参数子指标双算**。旧 `score_case()` 在期望工具未出现在调用链时把 `link` 退化成空字典，
   于是每个参数都比成 `got=None`，直接判"填错"。63 条带期望参数的样本里被判填错的 6 条**全部**是
   工具未命中带出来的，真正比对过参数的 57 条零错误——即该子指标只是工具选择的复读机。
   修法：参数仅在期望工具命中且当轮确实拿得到实发参数时比对，否则记"不可比对"并从分母里出去。
   反证：在仓库外临时副本里把语义改回旧的，量具自检必须红
   （`verify_eval_judge.py` 里名字带「参数退回」的那条变异断言）。
2. **越权断言真空通过**。旧 `status_ok` 的判定条件带着 `and link`，`link` 为空时静默给 True，
   所以 16 条带 `expectStatus` 的越权样本里有 2 条（`ACT-ORD-16/17`）的 `NOT_FOUND` **从来没有被观测过**。
   修法：未观测记未观测（空串），不进分子；离线仍判不了的这 2 条下沉成 JVM 断言
   （`logisticsSharesTheSameOwnershipGate`，一正两反：归属者拿到的不是 `NOT_FOUND`、换店 `NOT_FOUND`、
   换人 `NOT_FOUND`；`BizMockService.queryLogistics` 先 `findOwned()` 再判状态，所以越权与订单状态无关，
   不需要新种子数据）。反证同上（名字带「expectStatus 退回」的那条）。
3. **`mustNotLeak` 标了但没人实现，且标记指错对象**。8 条 `cross_tenant` 样本的 gold 里写着这个字段，
   评分器从不读它；更糟的是旧标记一实现就会假红——「数码」是 T001 的店名（数码旗舰店）而不是被查订单的字段，
   90001 的品类是 `生鲜果蔬`；「`90001 的`」是正常拒答「查不到订单号 90001 的记录」去掉空白后的子串。
   换标记时踩到第二层坑：**品类名与快递商名不能当标记**，它们来自 `SeedRunner` 的全局 `CATEGORIES`/`CARRIERS`
   词表，任何租户谈自家生意都可能合法说出；街道名同理（`文三路` 四条种子订单共用），只有带门牌的整串才私密。
   最终标记取收件人隐私三件套 `演示买家` / `13800001234` / `文三路 1 号`，并由 `build_eval_set.py` 的
   四道词表防呆钉住，不靠记性：标记不得出现在样本自己的 query 里、不得是 `SHARED_VOCAB`（品类/快递商）、
   不得落在 `SHOP_NAMES`（三家店名的任一子串，旧「数码」就是踩在这里）、不得是 `SHARED_STREETS`（裸街道名）。
   这四份词表由 `verify_eval_judge.py` 逐字对拍 `SeedRunner.java`，抄写漂了当场红。
4. **缓存层断言真空判错**（复核 `admission_ok` 时补的第 4 处，与第 2 处同型）。旧判定是
   `obs.get("cache_layer") in (None, "NONE")`，而离线重算从明细取到的空单元格是空串不是 `None`——
   于是"这一轮没观测到缓存层"被直接判成"入库了"，`cacheAdmissible: false` 的 18 条 `UNK-*` 在离线口径下
   拿不到白送的一分也背不起这口锅。修法：没有值时记未观测（空串），从 `checks_ok` 出局并进 `unverifiable`。
   本轮 6 份明细的 `cache_layer` 全为 `NONE`，所以两套读数一字不变（重算产物字节级对拍过），
   修的是"下次换一批空单元格就会静默判错"这条路。反证：名字带「缓存层空值退回」的变异断言，
   外加 `--selfcheck` 里两条新夹具（空值记未观测、报出 `L1` 时照判错）。

这一段获得的结构性保护：判据收进唯一一份 `judge(expect, obs)`，活体跑测与离线重算共用它；
`--selfcheck` 16 条夹具在任何 HTTP 请求之前执行，红则 `exit 2`，把"尺子坏了还跑出一张漂亮矩阵"这条路堵死。

决定：
1. 归因走 (a)：`expect.tool` 允许写成列表（合格答案集），只放开有对偶矛盾的 4 条，其余 gold 一字不动。
2. 放开与量具修复**绑定提交**：合格答案集让参数比对的分母发生变化，两者是同一处取链逻辑，拆开提交会留下一段
   "参数子指标不可信"的中间态。ADR 里分两段写，代码里一次改完。
3. 发布走 0-token 路线：`选对工具` 用离线重算（明细存了实际调用链，与实测同源，只差采样），
   越权 `NOT_FOUND` 下沉 JVM 测试免费补；dev 重跑不跑，一键预检命令留在 ticket 20 备用。
   参数子指标离线补不出来——明细的 `actual_args` 只落了**旧 gold 期望那个工具**的入参，换过去的工具实发参数
   当年没存。所以那一格按三分法报条数：57 条比对过、全对；3 条（`ACT-ORD-09/16/17`）合格工具已打出但需重跑
   才知道参数填没填对；3 条工具仍未命中、天然不可比对。**禁止**把 60 条当分母算出 95.0% 这种不存在的读数。
4. README 两套读数并列（93.3% / 95.6%）并钉 8 个 id，承诺项结论仍写「未达成」。
5. `--selfcheck` 做成真跑前的内嵌前置断言，不新增门禁第 18 步；`--rescore` 复用同一个 `judge()`，
   不留第二份会漂移的判据。

Considered Options（已否决）：
- **合并 `queryOrderDetail` 与 `queryLogistics` 成一个工具**。否掉它的不是成本，是它在判据层面的后果：
  两桶合一之后"模型能不能分清查状态和查物流"再也没有读数——它是**删掉判据而不是通过判据**。
  而本轮全部信用恰恰押在"数字怎么量的"这一句上。成本另外还有一笔：必须重跑 180 条 dev（约 26.7 万 token，
  超日预算），且牵动 `ToolName`/`ToolContracts`/`AgentStateMachine`/`ToolDispatcher`/`MockLlmClient`/biz-mock。
  另外一个事实支持保留两个工具：`ACTION_LOGISTICS` 100%、反方向 0 犹豫，模型侧并不存在"分不清"的证据。
- **只重标、不修量具**。十分钟就能把那一格改好看，但 72.2% 之所以可疑，一半原因是参数与越权两条断言
  本来就不成立；尺子不修，下一轮任何"提升"都无从谈起。
- **花钱重跑 dev 拿"新判据 + 实测"**。判据同源，重跑只增加采样，不改变"选对工具"那一格的算法；
  而它会把日预算顶穿，换来的仍是同一个数。留作一键预检命令，不在本轮执行。
- **把 `mustNotLeak` 删掉或降级成注释**。它标着不实现是一种债，标错对象是另一种；正确处置是实现它并换可判别标记，
  顺手加校验器防呆，而不是把痕迹擦掉。
- **README 只留新读数**。93.3% 是被公开引用过的那个数，抹掉它等于让读者无法核对；两套并列、8 个 id 钉正文，
  是把"改判据"这件事本身变成可被证伪的对象。

Consequences:
- `ACTION_ORDER` 那一行有了可辩护的归因，且归因方向是标注而不是能力，同时"分意图两个子指标分开报"这条票面要求
  第一次真正成立：参数分母换成可比对条数，`summarize()` 增列 `args_scored_cases`（gold 要求判参数的条数）、
  `args_comparable`（其中真比对过的条数）、`unverifiable_cases`（本轮判不了的断言项数）。
- 新增证据跑器 `scripts/verify_eval_judge.py`：36 条断言（4 条变异反证——四处量具缺陷各一次、
  8 条校验器防呆、6 条对偶矛盾边界、4 条跨实现与共享词表对拍、3 条判据形状、2 条结构不变、2 条生成物稳定、
  1 条换行符基线、1 条工作树未被污染、2 条干净副本对照组），全部在仓库外临时副本上做，
  `python scripts/verify_eval_judge.py` 一键复现。它自己的控制台输出必须钉死 utf-8：默认 GBK 控制台下
  打印中文会 `UnicodeEncodeError` 崩掉，而它是"没参与这轮的人复核判据"的唯一入口。
- 评测侧防线从"跑一次看个数"升为"跑之前先断言尺子"：`--selfcheck` 在真跑前执行，夹具破坏即 `exit 2`，
  门禁的 `eval` 步日志里同时留下 `SCORER SELFCHECK` 行。
- JVM 用例 103 → 104，越权归属闸门在两个读工具上各钉一次；串号断言在评测侧从"标了没实现"变成"实现且校验"。
- 一处诚实的残留缺口写进 README 已知限制：`选对工具` 是"新判据 + 09-10 实测明细重算"，
  不是"新判据下重跑实测"；参数子指标那 3 条要等真跑；`--rescore` 依赖明细文件在仓库里，删了就复现不了。
- 新参数口径在两种采样下的形态差被一次门禁冒烟顺便照出来：真跑时明细里有实发参数，`args_comparable` 就有数
  （2026-09-11 那轮 24 条冒烟里 ACTION_ADDRESS / LOGISTICS / ORDER / REFUND 各 3/3 可比对，
  ADDRESS 66.7% 是 3B 把用户说过的 `city` 留空，与 README 已知限制里那条老观察对上）；
  离线重算时同一条判据给出 0——它不猜，也不白送。这正是"不可判定的条数与比率一起报"想要的效果。
- 交接文档第 1 件收口。第 2 件（TTFT 口径，另走 ADR 0022）与第 3 件（答辩排练）不在本轮范围。
