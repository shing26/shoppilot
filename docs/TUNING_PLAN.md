# ShopPilot 调优路线与执行计划（2026-10-26）

> 状态：**待执行**。所有者要求“梳理路线、整理计划”。
> 范围：降低模型依赖、修复当前可测缺口；**不新增产品功能**，不改 gold / 阈值 / 分母。
> 与路线 A 的关系：路线 A 是对外定位；本文是支撑该定位的工程调优计划。

## 一、先定目标

不是“让模型更聪明”，而是：

1. 让更多请求在**不调用模型**的情况下正确完成；
2. 让必须调用模型的请求，在**小模型**上也能达到可接受质量；
3. 让每次优化都能用现有判据证明“变好了且没弄坏别的”。

## 三、调优路线（按 ROI 排序）

### 阶段 0：基线复现与失败分类（1 天）

**目的：** 先确认红点可复现，避免拿环境噪声当模型问题。

任务：

- 复核 180 条 gold（qwen-plus）与 local UX 30 的最新入库产物；有有效 key 后再复跑确认；
- 复跑 local UX 30，确认 3 个失败仍在；
- 把失败分成 5 类：路由 / 工具选择 / 槽位 / 答案保真 / 环境；
- 为每条红点记录：query、期望、实际、模型、promptVersion、是否可确定性修复。

产出：

- docs/TUNING_BASELINE.md（或 EVIDENCE 增补行）
- 失败分类表：每条红点一个 owner 决策

**Gate：** 分类完成前不做任何 prompt / 模型改动。

### 阶段 1：工具选择与意图边界（3–4 天，最高 ROI）

**目标：** 把 4 个红点里“可确定性判断”的部分移出模型。

> **票 162 后的顺序调整：** 先修“假转人工”（ESC-03/05/14/18），再修物流/越界工具准入，
> 再多意图，最后小模型答案保真。
> 依据：[TUNING_BASELINE.md](TUNING_BASELINE.md)。票 163 已收口。

#### 1.0 ESCALATE：显式升级独立裁决（先做）

- 问题：用户明确要求真人，系统有时只在话术里说“转人工”，没有实际升级；
- 其中 ESC-14/18 被分成 POLICY_PROMO/UNKNOWN，升级依赖 intent 的写法漏掉；
- 修复：新增不依赖最终 intent 的显式升级检测，在工具选择前裁决；
- 验收：ESC-03/05/14/18 全部实际升级且工单可查。

#### 1.1 ACTION_LOGISTICS：物流词优先

- 问题：2 条 query 被模型选成 queryOrderDetail 而不是 queryLogistics
- 修复：query 同时含订单号 + “物流/快递/到哪了/轨迹”时，由确定性派生直接选 queryLogistics
- 保留：模型只在没有明确物流词时参与选择
- 验收：LOGISTICS 88.9% → ≥95%

#### 1.2 ACTION_ORDER：散文追问新地址

- 问题：1 条模型用散文追问，没有发结构化工具
- 修复：订单动作意图下，缺槽位必须走 slotAsk，禁止散文追问；服务端校验兜底
- 验收：ORDER 94.4% → ≥95%

#### 1.3 ESCALATE：升级措辞漏判

- 问题：4 条升级措辞未被 T0/模型实际转人
- 修复：扩充 T0 显式转人工词表（投诉、监管、曝光、起诉、找负责人等），并加“升级意图”回归用例
- 验收：ESCALATE 88.9% → ≥95%

#### 1.4 UNKNOWN：越界请求不要查单

- 问题：3 条越界请求被调 queryOrderDetail 追问单号
- 修复：无订单上下文时禁止动作工具；政策形状 / 越界形状先做确定性拦截
- 验收：UNKNOWN 83.3% → ≥95%

**Gate：** 180 gold 重新跑，总分不下降；四个意图达到 95%；gold / 阈值零改动。

### 阶段 2：小模型答案保真（3–4 天）

**目标：** 把 local 3B 从 27/30 提到 ≥29/30，且 dev 30/30 不回落。

三个失败都不是“推理能力不足”：

- G-006 / G-026：生鲜赔付答案缺“48 小时”
- G-029：酒店早餐问题答成“请提供订单号”

修复顺序：

1. **上下文注入**：把命中条款的关键数字做成“必须包含的事实”，而不是整段塞给模型；
2. **检索排序**：确认生鲜赔付条款排在前 2，而不是靠模型从第 5 条里找；
3. **回答约束**：政策答案要求“先给结论 + 引用关键数字”，缺数字视为失败；
4. **未知问题边界**：酒店早餐属于政策/店铺信息，不应触发订单槽位追问。

**Gate：** local ≥29/30；dev 保持 30/30；180 gold 政策分区不下降。

### 阶段 3：模型分级与成本（2–3 天，可与阶段 2 并行）

**目标：** 不要求一个模型全包。

- 低风险 / 高确定性：T0/T1、模板、确定性派生，不调模型；
- 中等：本地 3B / 7B；
- 低置信 / 复杂政策：云端 qwen-plus；
- 任何模式都必须保留既有 fallback 与 HITL。

先做“离线路由表”评估，不直接改线上：

- 用现有 180 + UX 30 结果，按意图 / 置信度 / 是否命中规则分组；
- 估算每组用哪个模型的质量与 token；
- 选一个“质量不降、token 明显降”的组合。

**Gate：** 质量不降；token / 延迟有实测收益；不引入新的失败模式。

### 阶段 4：是否微调（可选，最后做）

只有满足以下条件才进入：

- 阶段 1–3 完成后，残余失败仍以“格式 / 话术 / 工具调用语法”为主；
- 知识类失败已通过检索/上下文解决；
- 有 ≥300 条高质量领域样本与固定 holdout；
- 有明确回滚与评测门禁。

微调只做：

- LoRA / SFT 小模型
- 工具调用格式
- 领域话术
- 固定输出结构

**不微调解决：**

- 政策数字缺失
- 检索没召回
- 开放式推理不足

**Gate：** local 提升且 dev 不降；否则回滚，不上线。

### 阶段 5：回归与证据（2 天，贯穿）

- 每阶段跑：JVM verify、UX 30、180 gold（或受影响子集）、CI；
- 所有变化写 EVIDENCE：命令、模型、promptVersion、结果、未达成项；
- 不把“阈值调低”当优化；
- 不把“demo 30/30”当模型能力证据。

## 六、明确不做

- 不改 gold、阈值、分母、FallbackReason；
- 不为了变绿改 Mock 参数或缩短答案；
- 不在阶段 0 之前改 prompt；
- 不在知识/检索问题没解决前微调；
- 不新增客服功能、不扩 Agent Run；
- 不把“模型升级”当第一选择。
