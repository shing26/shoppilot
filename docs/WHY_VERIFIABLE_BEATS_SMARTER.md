# 为什么在真实业务里，“可验证”比“更智能”更重要

> 这是一篇技术文章草稿，不是产品宣传。它只回答一个问题：
> 当 LLM 进入真实售后业务，什么能力才是稀缺的？
> 证据与数字均来自本仓可复跑的测试、CI 与 EVIDENCE，未达成的部分照登。

## 一、Agent demo 的三个陷阱

过去一年，Agent demo 很容易做得“看起来很聪明”：

- 用户说一句话，模型自己选工具、填参数、连续调用；
- 界面上展示一段“思考过程”，看起来像在规划；
- 成功案例剪成 30 秒视频，失败案例不录。

但真实业务不是这样验收的。真实业务会问四个问题：

1. 工具选错时，系统会不会拿错误结果继续编答案？
2. 模型想越权时，有没有硬边界？
3. 出了问题，能不能回放到“哪一步、用了什么参数、为什么”？
4. 改了 prompt / 模型 / 工具后，怎么知道没有把旧场景弄坏？

大多数 demo 答不上来。它们优化的是“首次演示成功率”，不是“长期可验证性”。

## 二、三个具体的失败模式

### 1. 静默错误：答案很好听，工具结果不对

模型可以在没有订单号时编一个订单号，也可以在工具返回 `STATE_NOT_ALLOWED` 时
用一段“已为您处理”的话术盖过去。用户看到的是一段流畅回答，业务侧看到的是一条错误事实。

### 2. 无界自主：模型自己决定能做什么

自由多 Agent 很吸引人，但一旦模型能自己扩权、自己改路由、自己跳过人工审批，
安全边界就从“系统约束”退化成了“prompt 约束”。prompt 不是授权。

### 3. 不可回归：只验证过一次

一次成功的 demo 不能证明系统稳定。没有固定判据、没有离线重算、没有任务级指标，
每一次 prompt 调整都可能悄悄破坏旧场景，而团队只能靠人记得再点一遍。

## 三、ShopPilot 的选择：把“智能”关进可验证的笼子

这个项目没有追求“更自主”，而是做了五个反向选择。

### 1. 路由是确定性纯函数，不是模型

`AgentRole.routeFor()` 把意图映射到角色，`HandoffGraph` 只允许
`PRE_SALES -> AFTER_SALES` 一条边，且最大深度为 1。

这不是因为模型做不到更复杂，而是因为：

- 路由错误会直接改变工具面与责任边界；
- 一条固定边比一张自由图更容易测试、解释和审计；
- 被拒绝的 Handoff 可以落成可查工单，而不是静默失败。

### 2. 工具风险是静态元数据，不是模型判断

`ToolRiskTier` 把工具分成 `READ_ONLY` / `LOW_RISK_WRITE` / `MONEY_WRITE` /
`IRREVERSIBLE_WRITE`。退款是 `MONEY_WRITE`，必须走 HITL；模型只有提案权，没有放行权。

模型可以决定“调用哪个工具”，但不能决定“这个工具危不危险”。

### 3. 被拒绝的 Handoff 不是错误页，而是工单

当同诉求升级被图拒绝时，系统停止推理，落一张 `INTENT_UNRESOLVED` 工单，
payload 带 `handoffTrail`、`blockedReason`、`confirmedSlots`、`promptVersion`、`policyVersion`。

这解决的是“Agent 踢皮球”问题：用户不会看到一句含糊的“已为您转接”，
坐席能看到为什么被拒绝、之前已经确认了什么。

### 4. Agent 行为要可见，但推理文本不必公开

买家端能看到 Agent Run：计划、工具调用、观察结果、兜底。
看不到的是模型的内部推理文本——那既不可验证，也容易泄露。

可解释不等于把思维链贴给用户。可解释是：**每一步外部行为都有可核验的事实**。

### 5. 评测是门禁，不是报告

仓库里有：

- 180 条 gold
- UX 30
- Handoff golden 23
- promtool 告警双侧测试
- 离线 rescore
- 任务级判据
- 覆盖率棘轮
- 689 条 JVM 测试 / 117 suites

它们不是“有空再跑”的脚本，而是 CI 每次 push 必须通过的闸门。
关键失败在 `EVIDENCE.md` 里照登，不藏。

## 四、代价是什么

这条路不免费：

- **自主性更低**：很多任务需要人确认，体验不如自由 Agent 顺滑；
- **工程成本更高**：路由、图、风险分级、审计、评测都要自己写；
- **功能迭代更慢**：每加一个能力都要补判据，不能只改 prompt；
- **演示不够炫**：没有“模型自主规划 20 步”的视频。

如果目标是做一个研究性 Agent，这些约束是负担；  
如果目标是让 Agent 进入真实业务，这些约束就是产品本身。

## 五、什么时候不该走这条路

- 低风险、容错高的消费级场景：用户能接受试错，速度比审计重要；
- 探索性研究：需要最大化自主性，不该先加边界；
- 任务边界每天变化：固定判据会变成负担；
- 没有真实用户与真实失败样本：容易把“自认为重要”的约束做成过度设计。

## 六、结论

“更智能”会持续被平台和模型能力追上。  
“可验证、可审计、可回归”不会自动出现，它需要工程选择。

ShopPilot 的价值不在于它比大厂客服更聪明，而在于它回答了一个不同的问题：

> 当 LLM 不被完全信任时，业务系统应该如何组织它？

这个问题比“再做一个客服 Agent”更难，也更少人认真做。
