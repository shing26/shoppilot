# 路线 A 执行包：可信 Agent 运行时

> 状态：**Active**（2026-10-26 所有者选择路线 A）。
> 本文是路线 A 的对外叙事、对比矩阵、演示脚本与 14 天收口清单。
> 它不新增功能；所有产品功能开发在此暂停。

## 0. 一句话定位

**ShopPilot 是一个可验证、可审计、可回归的受控 Agent 运行时。**

不是“通用智能客服平台”，不是“自主 Agent 框架”，也不是“比大厂更聪明”。

## 0.1 对外 300 字版本

ShopPilot 是一个可验证、可审计、可回归的受控 Agent 运行时。它不追求“比大厂客服更智能”，
而是解决另一个问题：当 LLM 进入真实售后业务，如何保证它不越权、不静默失败、每一步都能解释、
每次改动都能回归。

它用确定性路由与有界状态机约束自主性，用工具风险分级与 HITL 约束资金动作，用 trace、Agent Run
与工单 payload 让行为可解释，用租户/买家隔离、幂等、审计守住边界，用 180 条 gold、Handoff golden、
任务级判据、promtool 与 701 条 JVM 测试让结果可复跑。

它不是通用客服 SaaS，也不是自主 Agent 框架；它是一套“LLM 在受监管业务里如何可靠工作”的工程答案。

## 1. 我们到底卖什么

不是功能，而是三个可被验证的工程承诺：

### 承诺 1：有界自主，不是黑盒自治

- 确定性 Router；Handoff 只有一个方向、最大深度 1
- 工具轮次有硬上限
- 工具有 `ToolRiskTier`；资金动作必须 HITL
- 模型不能自己扩权、不能自己改路由

**证据：**
- [ADR 0072](adr/0072-agent-handoff-graph-and-role-kernel.md)
- `ToolDispatcher` / `HandoffGraph` / `ToolSurfacePolicy`
- 701 JVM tests

### 承诺 2：每一步可解释，不是只看最终答案

- 买家能看到 Agent Run：计划 → 工具 → 观察 → 回复
- 每个 blocked handoff 落可查工单，payload 带 trail / reason / confirmed slots
- 坐席台可看编排质量、工具风险、上下文丢失

**证据：**
- [Agent Run 截图](buyer-agent-run-compound.png)
- [坐席质量视图](workspace-console-quality.png)
- [ADR 0076](adr/0076-round41-agent-run-visible-trace.md) / [ADR 0077](adr/0077-round42-plan-first-compound-task.md)

### 承诺 3：结果可回归，不是一次性 demo

- 180 条 gold、UX 30、Handoff 23、promtool 告警测试
- 离线 rescore、任务级判据、覆盖率棘轮
- 701 tests / 117 suites，CI 每次 push 强制跑
- 关键失败在 EVIDENCE 里照登，不藏

**证据：**
- [docs/STATUS.md](STATUS.md)
- [docs/EVIDENCE.md](EVIDENCE.md)
- [CI 工作流](../.github/workflows/ci-subset.yml)

## 2. 我们不卖什么

不要对外说：

- “比 Zendesk / Intercom / 大厂客服更智能”
- “自主完成任何售后任务”
- “生产级 SaaS，开箱即用”
- “多 Agent 协作平台”

这些要么没有证据，要么不是当前实现。

| 维度 | 大厂客服平台 | 通用 Agent 框架 | ShopPilot |

| 自主规划 | 中 | 强 | 弱（刻意有界） |

## 4. 三分钟演示脚本

### 0:00–0:20 开场

打开 `/`：

> “这不是一个通用客服产品，而是一个可验证的 Agent 运行时。今天只看三件事：有界自主、可解释、可回归。”

### 0:20–1:10 买家端：计划先行的复合任务

打开 `/buyer/?store=T001`，登录演示买家，输入：

> 帮我查一下订单 90004 的物流和详情

展示：

- 计划：查询订单详情 → 查询实时物流 → 汇总
- 两次真实工具调用
- 汇总答案：待付款、家居日用、¥199、未发货无物流

一句话：

> “计划不是模型编的，是运行时生成的；工具调用与结果都能看到。”

### 1:10–1:50 blocked handoff 与工单

用已有四轮序列或打开工单页，展示：

- 允许 Handoff
- 回到售前
- 再次升级 → blocked
- 工单 payload 含 trail / reason / confirmed slots

一句话：

> “被拒绝的 Handoff 不是静默失败，而是一张可查工单。”

### 1:50–2:30 坐席控制台：编排质量

打开 `/workspace/`，进入“编排质量”：

- Handoff allowed / blocked
- 决策耗时
- blocked reason
- 工具风险
- 上下文丢失

一句话：

> “运行时不仅能回答，还能解释自己哪里不健康。”

### 2:30–3:00 证据收口

展示：

- 701 tests / 117 suites
- CI 全绿
- gold / handoff golden / promtool
- EVIDENCE 里未达成项也照登

一句话：

> “这不是一个 demo，是一套可以被复跑、被质疑、被回归的工程资产。”

## 5. 十分钟深讲结构

1. 问题：不可靠模型 + 真实业务，缺的不是更聪明的 prompt，而是运行时约束
2. 架构：triage → 有界状态机 → 工具治理 → HITL → 工单
3. 安全：租户/买家隔离、幂等、审计、风险分级
4. 可解释：trace、Agent Run、工单 payload、质量旁路
5. 可回归：gold、任务级判据、promtool、覆盖率
6. 取舍：为什么不做自由多 Agent、为什么不做通用 MCP
7. 局限：只验证了一个复合读场景；没有商业客户；不是 SaaS

## 6. 14 天收口清单（不写功能代码）

### 第 1–2 天：对外一页纸

- [ ] 从本文抽出 300 字版本
- [ ] 明确“我们不是什么”
- [ ] 把 3 条承诺各配 1 个证据链接

### 第 3–5 天：3 分钟演示录制

- [ ] 确认没有“内部枚举 / 报错 / 空看板”入镜
- [ ] 视频 3 分钟内，不超过 4 分钟

### 第 6–9 天：技术文章

- [x] 主题：为什么“可验证”比“更智能”更重要 → [WHY_VERIFIABLE_BEATS_SMARTER.md](WHY_VERIFIABLE_BEATS_SMARTER.md)
- [x] 用 blocked handoff 与 HITL 做两个具体案例
- [x] 不放无法复跑的数字

### 第 10–12 天：5 位技术评审

- [ ] 每人 20 分钟：3 分钟演示 + 7 分钟追问 + 10 分钟反馈
- [ ] 只问三个问题：
  1. 你认为这个项目解决了什么别人没解决的问题？
  2. 哪一条证据你愿意相信？哪一条你不信？
  3. 如果只能保留一个能力，你保留哪个？

### 第 13–14 天：决策复核

- [ ] 5 人中至少 3 人能复述定位 → 路线 A 成立
- [ ] 有人问“能不能给我们团队用” → 记录为 C 的线索
- [ ] 有人给出具体异常处理场景 + 愿意共创 → 记录为 B 的线索
- [ ] 都没有 → 保持 A，不扩功能

## 7. 成功标准

路线 A 的成功不是用户量，而是：

- 5 位技术评审中，至少 3 位能在 10 分钟内说清“这是可信运行时，不是客服 demo”；
- 至少 1 位愿意自己复跑 CI / 证据链；
- 至少 1 个外部引用或技术讨论线索。

## 8. 停止清单

- 不再加通用客服功能
- 不再扩 Agent Run / 复合任务
- 不启动路线 B 自主循环
- 不启动 MCP
- 不为“像 Agent”而改 UI 话术

只允许：事实性 bug、安全/隔离/回归修复、证据维护。
