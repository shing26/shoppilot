业务中台与隔离

60 秒版：biz-mock 是独立进程的业务系统替身，用真实 HTTP 边界承载工具契约、租户隔离、退款幂等、改址历史和工单状态机。隔离取共享表上的行级逻辑隔离，不是物理隔离；最关键的一道防线是租户和买家只能来自网关注入的服务端上下文。

Decision

独立进程：业务调用经工具 API 跨 HTTP 边界，既能验证 schema 和错误映射，也能注入业务依赖故障来证明 fallback，而不是在网关里调用本地方法做假闭环。

租户隔离三道防线：身份从鉴权结果进入租户上下文；查询通过 Hibernate @TenantId 与仓储自动拼归属条件；跨租户越权进 CI 和活体验收。文档只称“租户隔离”，不能称“物理隔离”。

写操作先查后绝：退款先查同一订单与幂等 token，再由数据库唯一约束兜底；改址做状态与归属前置校验并保存版本历史；工单按显式状态机流转。

Reproduce

.\mvnw.cmd -B -ntp -pl shoppilot-biz-mock -am `
  -Dtest=TenantIsolationAndIdempotencyTest,TicketWorkflowTest,TicketIdTest `
  -Dsurefire.failIfNoSpecifiedTests=false test

# 需先起栈
pwsh -NoProfile -File scripts/verify-idempotency.ps1
pwsh -NoProfile -File scripts/verify-action-loop.ps1

重点观察：50 并发同 token 最终只有一条退款；换店或换买家查同一订单得到未归属，不泄露字段；非法工单状态迁移被拒绝；内部工具接口不能绕过内部 token。

Three questions

Q1：为什么把 biz-mock 做成独立进程？

因为“真的办成业务”需要文件、网络、事务和故障边界。独立进程能证明工具 schema、HTTP 错误、超时、幂等和 fallback 串在一起；如果只是网关内部的方法调用，面试官追问“业务依赖挂了怎么办”时没有真实故障面可演示。

Q2：为什么选行级逻辑隔离，而不是每租户一个库？

本轮目标是面试作品且数据规模为三租户，行级隔离能用共享表加强制谓词覆盖查询、种子和压测，不需要动态路由和 collection 爆炸。代价是隔离强度依赖代码纪律与自动化用例，所以文档明确不宣称物理隔离。

Q3：有 Redis 幂等守卫了，为什么还要数据库唯一约束？

Redis 可能不可用，网关进程也可能重试；内存状态不是最后真相。数据库唯一约束是完成写入后的最终防线，保证跨进程、跨重试和 Redis 故障时仍只有一条记录。两层分别降低常见冲突和封住不可恢复的重复写。

Failure symptom

症状含义
A 店通过订单号查到 B 店订单身份注入、@TenantId 谓词或归属双条件失效。
同一退款 token 在并发下写入多行数据库唯一约束或事务回查失效。
改变地址时不校验订单状态或覆盖历史业务前置条件与审计版本不成立。
工单能从任意状态跳到任意状态状态机退化，人工队列语义不可信。
