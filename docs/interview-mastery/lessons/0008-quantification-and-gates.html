量化与门禁

60 秒版：这一站回答“凭什么相信上面的结论”。证据地图把每个对外数字映射到报告和原始产物；压测报告由 CSV 生成，strict 模式缺证据就红；验收门禁把构建、活体脚本和演示固定成一个矩阵；CI 只承诺干净 runner 上的构建和 224 条 JVM 测试，不冒充全量环境。

Decision

报告从产物生成：scripts/build_loadtest_report.py --strict 从 loadtest/results/ 读取 CSV/JSON 并写出报告，避免手抄数字和原始数据漂移。

一条命令跑活体验收：scripts/run-acceptance.ps1 固定构建、起栈、所有 verify 脚本、浏览器检查与三条演示的顺序和日志；失败不丢步骤。

CI 边界写清：.github/workflows/ci-subset.yml 在干净 runner 执行 bash ./mvnw -B -ntp verify，覆盖 build + 224 条 JVM 测试；不含 Docker、Ollama、评测、压测和 17 步活体验收。

红值不洗绿：拦截率、吞吐、未命中 TTFT、分意图工具准确率都保留判据、实测、归因和限制。改分母、阈值或 gold 换绿不算修复。

Reproduce

# 当前基线：3 + 12 + 209 = 224 条 JVM 测试
.\mvnw.cmd -B -ntp verify

# 40 条评分器断言，全部在仓库外临时副本做
python scripts\verify_eval_judge.py

# 压测报告必须与入库产物一致，缺证据即失败
python scripts\build_loadtest_report.py --strict

# 95 项收口审计
python .scratch\shoppilot-mvp\round3-closeout-audit.py

# 完整活体验收矩阵，耗时远大于前三项
pwsh -NoProfile -File scripts\run-acceptance.ps1

当前基线固定为：JVM tests 224；acceptance audit 95 checks, 0 FAIL；CI build + 224 JVM tests；ADR 范围 0001-0031。如果任一数字与产物不符，先修报告或门禁，不在面试话术里手改。

Three questions

Q1：224 条 JVM 测试为什么还不能代表全量验收？

它们适合在干净 runner 上验证构建、单元、集成和架构约束，但不包含 Docker 中间件、Ollama、ES/Qdrant、真实评测、压测和浏览器演示。CI 的价值是可重复和零外部凭证；它能证明“代码能构建且 JVM 测试绿”，不能证明所有活体防线都成立。

Q2：为什么说 22 ms 时必须带条件？

22 ms 是 perf 模式、200 并发、命中路径、未饱和队列下的 P99，模型与远程 embedding 增量为 0；100 并发是 32 ms，400 并发进入排队后 P99 明显抬升。把 22 ms 单独当端到端指标会隐藏模式、路径和队列条件。

Q3：为什么同时保留 93.3% 和 95.6%？

93.3% 是旧 gold 下的历史实测，95.6% 是同一批明细换合格答案集后的离线重算，不是重跑。更有意义的是分意图门槛：新判据下仍有五行低于 95%，所以承诺项仍是未达成。并列两套读数既保留判据变更历史，也防止 95.6% 被单独引用成通过。

Failure symptom

症状含义
README 数字与报告不一致手工文档漂移，证据链断裂。
--strict 报缺文件结论没有原始产物支撑，不能作为对外证据。
CI 绿，但活体验收有步骤红正常：CI 只覆盖子集；需要把边界说清，不能误报全量通过。
聚合准确率大于 95%，但逐意图多行低于 95%聚合值遮住真正的承诺判据，结论仍应写未达成。
