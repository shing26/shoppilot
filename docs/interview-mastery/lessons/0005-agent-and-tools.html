Agent 编排与工具

60 秒版：这里不是无上限自主 Agent，而是显式 10 状态有界状态机。单请求工具循环最多 2 轮、缺槽位最多追问 1 次；工具 schema 来自独立契约模块，写操作有幂等守卫。工具失败被结构化回填成可解释回复，超预算则按枚举原因转人工。

Decision

把循环变成可预算状态机：INTAKE → TRIAGE → CACHE_READ → RETRIEVE → PLAN → TOOL_EXEC → SLOT_ASK → REPLY → CACHE_WRITE → FALLBACK，每次状态迁移产生 trace，SSE 事件直接由迁移驱动。

两轮覆盖真实链式调用：第一轮查订单列表，拿到订单号后第二轮查物流；三轮链式操作拆成多轮对话，避免无限循环击穿时延目标。缺槽位只追问一次，仍缺则降级。

工具契约独立：shoppilot-tool-api 定义意图、工具名、DTO 和 JSON schema；dispatcher 统一做参数校验、缺槽识别、写操作幂等和状态映射。

失败是状态，不是异常泄漏：模型超时、预算耗尽、工具不可用和槽位未决都有对应的 FallbackReason；工具失败事实会回填给模型组织用户可读回复。

活体脚本关注的不只是“工具被调用”，还包括缺槽时是否追问、跨店是否拒绝、写操作是否有幂等保护，以及事件序列是否证明 2 轮上限存在。

Three questions

Q1：为什么不用真正的无限 Agent 循环？

工具轮次直接决定模型调用、外部 IO 和尾延迟，最坏路径若不可预算，就无法承诺 TTFT 或吞吐。显式上限把“聪明”换成可验证的终止性；需要更多工具时，让产品把任务拆到下一轮对话。

Q2：为什么两轮足够？什么会被截断？

两轮覆盖常见的“先查订单列表、再查物流”链式读取。三层或更多动作链会被截断，这是有意选择：继续加轮次会把尾延迟和失败面同时放大。面试时要主动说出被截断的形态，不能只说好处。

Q3：小模型场景为什么还要网关派生工具和抽槽位？

本地 3B 和 mock 模式不能稳定完成工具选择与参数抽取，纯靠模型会让演示路径不可测。网关对高置信读取动作做确定性派生，模型仍负责计划与表达；写操作保留更严格的校验和幂等，避免“模型承诺办理但没调用工具”。

Failure symptom

症状含义
模型连续要求调用工具，状态机没有终止点工具轮次预算失效，尾延迟不可证明。
缺少订单号却猜一个参数执行槽位校验或追问路径失效，可能操作错误对象。
同一幂等 token 产生两次写操作写操作守卫或下游唯一约束失效。
工具失败直接冒泡成 500结构化失败没有映射到 fallback，用户拿不到可解释结果。
