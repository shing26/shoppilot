两级缓存与穿透合并

60 秒版：缓存不是链路最前面的万能加速器，而是意图判定之后的受控分支。可缓存的政策请求先查 L1 精确缓存，再查带租户/范围/意图/知识纪元过滤的 L2 语义缓存；命中还必须通过极性守卫。只有合格答案才异步写回，并用 singleflight 合并冷缓存并发穿透。

Decision

缓存后置且 fail-closed：业务办理、含实体请求和不确定意图不进入 L1/L2。这样做会牺牲一部分拦截率，但避免通用政策答案被错误复用到个性化订单问题。

L1 精确、L2 语义，键和过滤一起承担隔离：L1 key 含 tenant、scope、intent、kbEpoch、归一化问法；L2 使用 Qdrant payload 过滤，读回后再校验意图、租户和知识纪元。cosine 阈值是 0.95。

命中不等于可复用：同桶反义对可能越过阈值，因此命中后比较否定极性。历史条目没有归一化 query 时不能复用。

写回有资格，穿透有合并：只有政策意图、检索有命中、答案合格、未降级、未走工具时才异步写回；singleflight 让同一 key 的等待者复用一次计算结果，等待超时后自行穿透。

  -Dtest=CacheServiceTest,L2SemanticCacheTest,PolarityGuardTest,WriteBackPolicyTest,WriteBackPoolTest `

# 本机 bge-m3 标定；退出码会把越界样本交给具名防线核对
python scripts/calibrate_threshold.py

# 需先起栈；检查反义对不互命中

标定的关键事实不是“相似度够高就安全”：0.95 工作点的同意图改写召回实测为 0，而反义对最大余弦达到 0.9682。正确结论是阈值只做同桶内表述归一，串号由准入、分区、写回资格和极性守卫共同承担。

Three questions

Q1：为什么把缓存放在意图判定之后？

因为完全相同或高度相似的问题可能因租户、实体和意图不同而有不同正确答案。“我的订单发货了吗”不能复用别人的订单结论，“怎么退款”也不能复用“为什么不给退款”。缓存后置主动降低命中率，换取跨意图正确性。

Q2：既然 0.95 召回为 0，为什么不降阈值换命中率？

0.85 附近的 precision 只有 0.231，降阈值是拿误命中换召回；在这个 embedding 分布里，同意图改写最大值 0.9435 甚至低于反义对的 0.9682。项目保留 0.95，L1 与 singleflight 承担主要热点拦截，极性守卫封住同桶反义，不用“更绿”的数字掩盖串号风险。

Q3：singleflight 为什么不让等待者边收边转发？

流式 tee 给多个等待者需要引入多路流转发状态机，复杂度高。这里选择等待完整答案后一次性推送，等待上限 2 秒，超时自行穿透；节省的是重复模型与远程 embedding 工作，不承诺强一致，也不把等待无界放大。

Failure symptom

症状含义
“能退吗”和“不能退吗”共用同一答案L2 命中后没有极性守卫，或历史条目缺少归一化问法。
拦截率变高，但用户反复看到转人工道歉失败答案被无资格写回，缓存固化了降级状态。
冷缓存时远程 embedding 数接近请求数进程内向量缓存或 singleflight 失效，发生并发穿透。
跨店同文本问句互相命中tenant/scope 过滤或读时二次校验缺失，阈值不能承担隔离。
