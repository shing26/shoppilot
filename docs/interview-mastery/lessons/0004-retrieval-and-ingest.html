检索与入库

60 秒版：政策知识先离线切成稳定 ruleId 的 Markdown 块，再分别写入 Qdrant dense 索引和 Elasticsearch BM25 索引；运行时两路各召回 top-20，用 RRF 融合取 top-5 注入提示词。重点不是“用了两个向量库”，而是把召回、融合、降级和负缓存边界写清。

Decision

双引擎是链路形态选择：Qdrant 负责语义接近，ES 负责精确术语和可解释词法命中；RRF 按名次融合，k=60，fused top-5 进入上下文。

入库不重叠、可重跑：按 Markdown 二级标题切块，合并过短块，ruleId 由内容稳定派生；以同一 id 写 ES 与 Qdrant，重跑是幂等 upsert，不引入运行时双写一致性窗口。

“检索失败”不等于“没有结果”：单路异常时另一路继续工作，但结果必须带 degraded 标记；上层据此禁止把一次中间件抖动写成 60 秒负缓存。

对比报告的当前事实是 dense-only 与 hybrid 都是 16/16，不能宣称 hybrid 修复了当前语料上的召回问题。保留双引擎的理由是未来万级条款、相似命名和政策术语的链路形态与可解释性，报告把“没测出收益”也保留。

Three questions

Q1：既然 hit@5 打平，为什么还保留 ES？

当前只有 90 个块，任一路都能把语料排完，所以这不是“当前已收益”的证据。双引擎保证术语精确匹配和多路降级，在跨店条款命名相似、语料上万后更有意义；代价是 ES 内存和运维，因此以 512 MB 堆、单节点、离线同步控制成本。

Q2：为什么切块不重叠，ruleId 还要稳定？

重叠块会让同一条款在 RRF 中被计两次，自己抬高自己的排名。稳定 ruleId 则让重跑是同一 id 的 upsert，不需要维护“哪次写入更新”的一致性窗口，清空重建和增量重跑都更可预测。

Q3：为什么必须区分“失败”和“空结果”？

如果向量服务超时被当成“库里没有这条政策”，上层就会写负缓存，后续请求在 60 秒内直接转人工；一次依赖抖动被系统固化成服务中断。degraded 标记让负缓存只对真实空结果生效。

Failure symptom

症状含义
同一条款在 top-5 重复出现并挤掉其他块切块重叠或 ruleId 不稳定，RRF 被重复命中污染。
单路超时后所有政策问题都转人工 60 秒失败被误判为空结果，负缓存写错对象。
数字写法和中文写法被说成 hybrid 的收益使用了当前对比没有支持的结论。
