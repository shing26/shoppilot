# 两个能跑的场景：一份给业务侧的一页纸

> 面向客服主管 / 运营 / 产品。三分钟读完，能复述下面五件事：
> **一进、一出、哪一步转人、什么情况办不了、现在哪段没通**。
> 这一页只讲业务，不复述任何指标数字——数字在 [README](../README.md) 与
> [`EVIDENCE.md`](EVIDENCE.md) 维护，这里不做第二份。

## 30 秒版本

- **门面场景**：鲜果驿站（电商租户 T002）——买家收到的大闸蟹死了，来问「死蟹怎么赔」。
- **对照场景**：云栖酒店（非电商租户 T004）——客人问「几点能入住、订错了能不能免费取消」。
- **一句话结论**：同一套客服程序，**换一套知识库 + 显式登记行业维度，就换一个行业**——不是
  「只换知识库」（round33 补的那一维，漏了就会出现「换店铺问同一句、答案几乎一样」）。区别只有
  一个：卖货的店有「办事」能力（查订单、退款、改地址），酒店这套现在只有「答规则」能力。

## 场景一：鲜果驿站 · 死蟹理赔（有进有出）

### 谁 / 遇到什么

买家在鲜果驿站下单大闸蟹，签收后发现死蟹，进线问赔偿。

### 规则从哪来（店铺知识库）

- **六小时窗口**：签收后 6 小时内报损才受理。
- **按只折算**：按坏掉的数量折算赔付比例。
- **需订单核验**：要能对上本人这一单才办。
- **一条真实边界**：系统**不能看照片定责**——照片判责必须转人工。（2026-10-20 起由 **T002 专属 T0 规则**保证：定责诉求 → 人工 + 可查工单；JVM 覆盖，T002 活体探针未跑）

### 走哪几步

1. **进门**：买家说「我的死蟹怎么赔」。
2. **分流**：程序判断这是「只问规则」还是「要办我这一单」。
3. **只问规则**（没带订单、没带「我这单」）：直接答规则文本，不查任何订单。
4. **要办这一单**（带订单号或说「我这单」）：程序去店铺系统**核这笔订单**，看签收是否在
   6 小时窗口内。
5. **出**：窗口内 → 按只折算给出赔付口径；已超窗 → 明确告知「已超 6 小时，不受理」。
6. **转人**：一旦需要「看照片定责」，程序**不猜**，直接转人工并留一张可查工单。

### 哪一步转人

- 需要**看照片定责** → 转人工。
- 买家明确喊「**转人工**」→ 直接转人工，不查订单、不调模型。

### 什么情况办不了

- 订单号对不上本店 → 拒答（不猜、不跨店查别人的单）。
- 已超 6 小时 → 按政策拒绝，不破例。
- 只给照片、不给订单号 → 追问一次订单号；仍不给 → 转人工。

### 现在哪段没通

- 「按只折算」的**赔付金额由人工在工单里定**；程序只判「在不在窗口内 + 该不该转人」，
  不自动出赔偿数字。

## 场景二：云栖酒店 · 入住与退改（纯咨询对照）

### 谁 / 遇到什么

客人在云栖酒店预订后，问「几点入住」「订错了能不能免费取消」「能不能加床」。

### 走哪几步

1. **进门**：客人问规则。
2. **分流**：程序判断这是**酒店规则咨询**。
3. **答规则**：从酒店知识库取原文回答，并带上出处（引用）。
4. **零工具**：酒店这套**没有任何「办事」工具**——不会去查订单、不会去改预订。

### 哪一步转人

- 客人要人工、或问题超出知识库能答的范围 → 转人工。

### 什么情况办不了

- 一切**办理类**诉求：改期、取消下单、退押金、开发票——酒店是纯咨询对照，程序只会答规则、
  然后转人。

### 现在哪段没通

- 酒店只有「答规则」，**没有「办事」**。这不是缺陷，是本轮**故意**用来划边界的：
  **咨询域换知识库就能上；办理域必须新增工具和意图，不是换文档能解决的**。

## 换一个行业要改什么（本轮可对外讲的结论）

同一套程序换一个行业，**不是「只换知识库」**。round32 先把它说成「改四处」；round33 把跨行业隔离
补成一个**运行时行业维度（domain）**之后，接新行业的成本要按下面这些**显式登记**去数——每一处
漏了，都会在实机上表现成「换店铺/换行业问同一句、答案几乎一样」：

| # | 改哪里 | 本轮酒店的例子 |
| --- | --- | --- |
| 1 | 登记租户属于哪个行业 | 配置里加 `T004 → HOTEL`；未登记的租户按 fail-closed 只看本租户规则 |
| 2 | 语料标行业 | 酒店语料解析成 `HOTEL`，**不能挂平台级**（否则污染所有电商租户） |
| 3 | 意图清单加一个 | 新增 `POLICY_HOTEL` |
| 4 | 关键词表加一份 | T0 规则层加酒店词表 |
| 5 | 入库映射加一条 | `hotel-` 前缀 → 酒店意图 |
| 6 | 评测集加一个分区 | 酒店用例单独成列（不并入原来的 180 条） |
| 7 | 加知识库文档 | 挂在该租户名下 |
| 8 | 加租户行 | 云栖酒店 T004 |

**结论**：**咨询域换知识库 + 显式登记行业维度就能换行业；办理域换不了**，必须新增工具与意图
（扩状态机分支与判据），不是换一份文档能解决的。缓存与检索都按行业分桶，**同一问法在不同行业
不共享平台缓存、也检索不到对方行业的条款**——这是 round33 补上的隔离。

## 五个问题速答

1. **一进**——谁进来、为什么：电商买家（鲜果驿站，死蟹理赔）与酒店客人（云栖酒店，入住与退改规则）。
2. **一出**——最后给什么：死蟹理赔给「窗口内按只折算 / 超窗不受理」的口径；酒店给带出处的规则原文。
3. **哪一步转人**：需要看照片定责时、买家/客人明确喊「转人工」时、问题超出知识库时。
4. **什么情况办不了**：订单号对不上本店；死蟹已超 6 小时；酒店的任何办理类诉求（改期/取消/退押金/开票）。
5. **现在哪段没通**：赔付金额由人工定，程序不自动出数字；酒店只有咨询、没有办理能力。

## 诚实的能力边界

- 本页不宣称任何生产上线；它是**单机可复现的演示件**。
- 酒店是**纯咨询对照**，特意不带工具——请勿把「换个知识库能上酒店」读成「酒店业务已经能办」。
- 死蟹理赔的**定责**（谁的责任、赔多少）始终是人工结论，程序只做「判窗口 + 判该不该转人 + 留工单」。
- 一页纸只讲业务；所有指标、未达成项与复现命令见 [README](../README.md) 与
  [`EVIDENCE.md`](EVIDENCE.md)。
